Nguồn: memory layout, qualifier, padding/alignment, endianness, vtable đối chiếu tài liệu chuẩn (Barr Group, ESR “structure packing”, Wikipedia) — xem “Nguồn tham khảo” cuối bài.

1. Memory layout của chương trình

Bố cục bộ nhớ. Stack mọc xuống, heap mọc lên — gặp nhau là hết RAM. BSS không tốn dung lượng file nhị phân (chỉ zero-init lúc chạy); Data phải lưu giá trị trong flash rồi copy sang RAM.
Text
Mã máy; thường nằm ở flash (read-only) trong nhúng, có thể chia sẻ.
.rodata
Hằng & string literal — read-only, hay để ở flash.
Data
Global/static đã khởi tạo ≠0; copy từ flash → RAM lúc startup.
BSS
Global/static =0/không khởi tạo; startup code zero-init. “Block Started by Symbol”.
Heap
Cấp phát động; trong nhúng hạn chế dùng (phân mảnh, không tất định).
Stack
Biến cục bộ/khung hàm; tràn stack là lỗi nguy hiểm khó tìm.
⚠️

Trong embedded an toàn, người ta thường cấm malloc/heap sau init: cấp phát động không tất định và có thể phân mảnh. Dùng static/memory pool thay thế (MISRA cũng khuyến nghị).

2. volatile, const, static, extern

2.1 volatile — bắt buộc trong nhúng

Báo compiler “biến này có thể đổi ngoài luồng code” (thanh ghi HW, biến do ISR sửa) → không tối ưu/không cache trong thanh ghi, mỗi lần truy cập phải đọc/ghi thật từ bộ nhớ.

// Thanh ghi phần cứng: PHẢI volatile, nếu không compiler có thể bỏ vòng lặp
#define STATUS_REG (*(volatile uint32_t*)0x40001000)
while ((STATUS_REG & 0x1) == 0) { /* chờ cờ ready */ }

// Biến chia sẻ với ISR: PHẢI volatile
volatile uint8_t flag = 0;
void ISR(void) { flag = 1; }          // ISR sửa
void main_loop(void){ while(!flag){} } // không volatile -> có thể loop vô hạn

// const + volatile (độc lập nhau): con trỏ HẰNG tới thanh ghi BIẾN ĐỘNG
uint8_t volatile * const p_led = (uint8_t*)0x80000; // p cố định, *p do HW đổi
🐞

Bẫy kinh điển: quên volatile cho cờ ISR/thanh ghi → ở mức tối ưu -O2, compiler giả định biến không đổi và loại bỏ vòng lặp chờ. Lỗi “chạy debug ổn, release treo”. Lưu ý: const và volatile độc lập, không phải đối nghịch.

2.2 static, const, extern

Từ khoáỞ phạm vi file/hàmÝ nghĩa

static (biến trong hàm)HàmGiữ giá trị qua các lần gọi; khởi tạo 1 lần (nằm ở data/BSS, không stack)

3. Con trỏ nâng cao & function pointer

// Con trỏ hàm: nền tảng của callback/HAL/jump table
typedef void (*IsrHandler)(void);
IsrHandler vector_table[32];
void register_isr(uint8_t id, IsrHandler h) { vector_table[id] = h; }

// Mảng con trỏ hàm = dispatch table (thay switch lớn)
typedef int (*Cmd)(int);
int do_read(int a){ return a; }
int do_write(int a){ return a*2; }
Cmd table[] = { do_read, do_write };
int r = table[1](10);   // gọi do_write(10) -> 20

// const và con trỏ — đọc từ phải qua trái
const int *p;        // con trỏ tới int hằng (đổi p được, *p thì không)
int * const q = &x;  // con trỏ hằng (đổi *q được, q thì không)

4. ISR, re-entrancy & critical section

Quy tắc viết ISR

  • Ngắn & nhanh — chỉ set cờ/đẩy data vào queue, xử lý nặng để main.
  • Không gọi hàm chặn/không re-entrant (vd printf, malloc).
  • Biến chia sẻ phải volatile; truy cập đa byte cần bảo vệ.
  • Xoá cờ ngắt đúng cách để không lặp.

Re-entrancy

Hàm re-entrant có thể bị ngắt giữa chừng rồi gọi lại an toàn: không dùng biến static/global chia sẻ, không trạng thái ẩn. Quan trọng khi hàm dùng cả ở main & ISR.

4.1 Critical section — bảo vệ truy cập chia sẻ

// Đọc biến 32-bit chia sẻ với ISR trên MCU nhỏ có thể bị "xé" (torn read).
// volatile KHÔNG đảm bảo nguyên tử -> cần critical section.
volatile uint32_t g_ticks;

uint32_t read_ticks(void) {
    uint32_t t;
    uint32_t s = __get_PRIMASK();  // lưu trạng thái ngắt
    __disable_irq();               // vào critical section
    t = g_ticks;                   // đọc nguyên tử so với ISR
    __set_PRIMASK(s);              // khôi phục (tránh bật nhầm khi lồng nhau)
    return t;
}
💡

Giữ critical section cực ngắn để không tăng interrupt latency. Lưu/khôi phục trạng thái ngắt thay vì enable cứng (tránh bật nhầm khi đang lồng critical section). Hoặc dùng stdatomic.h nếu nền tảng hỗ trợ.

5. Bit manipulation trên thanh ghi

#define BIT(n)   (1u << (n))
reg |=  BIT(3);              // set bit 3
reg &= ~BIT(3);             // clear bit 3
reg ^=  BIT(3);              // toggle bit 3
if (reg & BIT(3)) { ... }    // test bit 3

// Ghi một field nhiều bit (vd field [6:4]) mà không đụng bit khác:
reg = (reg & ~(0x7u << 4)) | ((value & 0x7u) << 4);
//      └ xoá field cũ ─┘   └ ghi giá trị mới vào đúng vị trí ┘
⚠️

Luôn dùng hậu tố u (unsigned) khi dịch bit để tránh undefined behavior khi dịch vào bit dấu. Với thanh ghi → nhớ volatile.

6. Endianness & struct padding

6.1 Endianness

Thứ tự byte của số nhiều byte trong bộ nhớ. Little-endian: byte thấp (LSB) ở địa chỉ thấp (x86, đa số ARM, RISC-V); big-endian: MSB ở địa chỉ thấp (network byte order — TCP/IP).

Endianness của 0x12345678. Cùng giá trị, khác thứ tự byte trong RAM. Quan trọng khi map struct lên khung giao thức (thường network = big-endian) hoặc đọc dữ liệu nhị phân chéo nền tảng.
// Kiểm tra endianness lúc runtime:
uint16_t t = 1;
bool little = (*(uint8_t*)&t == 1);   // true trên x86/ARM

6.2 Struct padding & #pragma pack

Compiler chèn padding để mỗi field tự căn lề (địa chỉ là bội của kích thước field); alignment của struct = alignment của field rộng nhất. Sắp xếp field giảm dần kích thước giúp giảm padding.

Struct padding. Mặc định 12 byte (b phải bắt đầu ở bội số 4). Pack(1) còn 6 byte để khớp khung protocol/thanh ghi. Đừng memcmp struct — byte padding có giá trị bất định.

7. Linker script (cơ bản)

Quyết định section nào đặt ở vùng nhớ nào (flash/RAM) và địa chỉ. Startup code dựa vào các symbol này để copy .data và zero .bss.

MEMORY {
  FLASH (rx)  : ORIGIN = 0x08000000, LENGTH = 512K
  RAM   (rwx) : ORIGIN = 0x20000000, LENGTH = 128K
}
SECTIONS {
  .text : { *(.text*) }   > FLASH      /* code o flash */
  .data : { *(.data*) }   > RAM AT> FLASH  /* gia tri nam flash, chay o RAM */
  .bss  : { *(.bss*)  }   > RAM           /* zero-init luc startup */
}

8. C++ trong embedded

vtable. Mỗi object đa hình có một vptr trỏ tới vtable dùng chung của class; gọi virtual = tra bảng lúc runtime. Chi phí nhỏ nhưng cản inlining và (trên Cortex-M) tốn một lần đọc flash.
Tính năngDùng tốtCẩn trọng / tránh
Class/encapsulationTổ chức driver/HAL sạch—
RAIIQuản lý tài nguyên (lock, peripheral) tự động — ctor lấy, dtor trả khi ra scopeNhớ virtual destructor ở base đa hình
virtualTrừu tượng HAL (đa hình)Vtable tốn RAM/flash + gọi gián tiếp + cản inline; tránh ở hot path
Templates / CRTPĐa hình tĩnh zero-cost compile-timeCode bloat nếu lạm dụng
Exceptions / RTTI—Thường tắt (-fno-exceptions): tốn flash, không tất định
STL động (vector...)—Cấp phát heap → tránh; dùng container tĩnh/etl
⚖️

Nguyên tắc: dùng phần C++ “zero-cost” (class, RAII, template, constexpr, final) nhưng tránh phần không tất định (heap, exception, RTTI) trong code real-time/safety. Đây cũng là tinh thần của Adaptive (C++14, có coding guideline).

9. Build toolchain & debug vs release

  • Preprocess → Compile → Assemble → Link

    .c → (macro) → .s → .o → ELF/HEX. Cross-compile: chạy trên PC, sinh mã cho target (vd RH850).

  • Cross-compile

    Toolchain riêng cho kiến trúc target; cần đúng CPU flags, ABI, và linker script.

  • Debug vs Release

    Debug: -O0 -g, dễ debug, chậm. Release: -O2/-Os, nhanh/nhỏ nhưng lộ bug volatile/timing/UB — luôn test cả hai.

10. Trước (~2020) → Nay — C++ trong nhúng

➕ C++ hiện đại vào automotive
⏪ Trước (~2020)

Classic chủ yếu C + MISRA C; C++ bị dè dặt (sợ vtable/heap/exception); template ít dùng.

⏩ Nay

Adaptive dùng C++14 với AUTOSAR C++14 / MISRA C++ guideline; xu hướng constexpr, CRTP, final, std::array/etl để đạt zero-cost mà vẫn an toàn. C++17/20 dần xuất hiện ở tooling.

Vì sao quan trọng: trả lời được “dùng C++ nào trong nhúng an toàn và vì sao” cho thấy bạn hiểu trade-off, không chỉ cú pháp.

11. Tự kiểm tra

Vì sao biến chia sẻ với ISR phải volatile? Định nghĩa▾

Không có volatile, compiler có thể giữ biến trong thanh ghi/giả định không đổi và tối ưu bỏ lần đọc lại → main không thấy ISR đã đổi giá trị. volatile buộc đọc/ghi thật mỗi lần.

Interviewer đào tiếp
  • volatile có làm atomic không? (Không!)
  • Cho ví dụ bug khi quên volatile.
volatile có làm truy cập nguyên tử (atomic) không? Áp dụng▾

Không. volatile chỉ chống tối ưu (đảm bảo đọc/ghi thật), không đảm bảo nguyên tử. Truy cập đa byte trên CPU nhỏ vẫn có thể bị “xé” (torn) khi ISR chen vào giữa → cần critical section (disable/restore IRQ) hoặc stdatomic.

Interviewer đào tiếp
  • Vì sao nên lưu/khôi phục PRIMASK thay vì enable cứng?
Biến nằm ở BSS hay Data? static int x=0; vs static int y=5; Định nghĩa▾

x=0 → BSS (zero-init lúc startup, không chiếm chỗ trong ảnh nhị phân). y=5 → Data (giá trị lưu trong flash, copy sang RAM lúc startup).

Interviewer đào tiếp
  • Startup code (crt0) làm gì với .data và .bss?
Một struct {char,int,char} sizeof bằng mấy? Giảm padding sao? Áp dụng▾

Thường 12 (int phải căn 4 → padding sau char đầu, và padding cuối để struct là bội alignment rộng nhất). Giảm bằng cách sắp field giảm dần kích thước (int, char, char → 8) hoặc #pragma pack(1)/__attribute__((packed)) (6, nhưng chấp nhận unaligned). Không memcmp struct vì byte padding bất định.

Interviewer đào tiếp
  • Pack có rủi ro gì trên ARM? (unaligned access fault/chậm)
Khi nào tránh virtual? vtable hoạt động ra sao? Áp dụng▾

Mỗi object đa hình có vptr → vtable (bảng con trỏ hàm dùng chung/class); gọi virtual tra bảng lúc runtime. Tránh ở hot path/real-time và khi RAM/flash khan: tốn bộ nhớ, gọi gián tiếp, và cản inlining. Thay bằng template/CRTP (đa hình tĩnh) hoặc final.

Interviewer đào tiếp
  • Vì sao luôn cần virtual destructor ở base đa hình?
Tại sao “chạy ở Debug ổn nhưng Release lỗi”? Kinh nghiệm▾

Thường do thiếu volatile, phụ thuộc timing, hoặc undefined behavior. Ở -O0 compiler không tối ưu nên “may mà chạy”; -O2 phơi bày lỗi. Cũng có thể do biến chưa khởi tạo hoặc race với ISR.

Interviewer đào tiếp
  • Bạn cô lập kiểu lỗi này thế nào? (so sánh asm, bật cảnh báo, sanitizer/MISRA)

12. Cheat-sheet 1 trang

Memory layout

  • Text/.rodata (flash, RO) · Data (init≠0) · BSS (=0)
  • Heap ↑ · Stack ↓ (gặp nhau = hết RAM)
  • BSS không tốn dung lượng file
  • Embedded safety: cấm malloc sau init

Qualifiers

  • volatile = đọc/ghi thật (KHÔNG atomic)
  • static = internal linkage / giữ giá trị
  • const & volatile độc lập
  • const ptr to volatile reg: T volatile * const

ISR

  • Ngắn, nhanh, set cờ/queue
  • Shared = volatile + critical section
  • Re-entrant: không static/global shared
  • Lưu/khôi phục PRIMASK

Bit / padding / endian

  • set |=BIT · clear &=~BIT · toggle ^=
  • Struct align = field rộng nhất; sắp giảm dần
  • pack(1) khớp protocol, rủi ro unaligned
  • BE = MSB trước (network) · LE = x86/ARM

C++ nhúng

  • Dùng: class, RAII, template/CRTP, constexpr
  • Tránh: heap, exception, RTTI ở real-time
  • virtual = vptr+vtable, cản inline
  • Base đa hình → virtual destructor

Toolchain

  • Preprocess→Compile→Assemble→Link
  • Cross-compile: flags/ABI/linker script đúng
  • Debug -O0 -g · Release -O2/-Os
  • Test CẢ HAI để bắt bug volatile/UB
