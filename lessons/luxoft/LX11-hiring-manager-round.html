English answer

One of the hardest was a SENT timing and signal-behavior defect on ST and Infineon targets. Intermittently, a few frames were rejected with CRC errors, and sometimes a decoded sensor value jumped by one step. It happened more often with certain sensor samples, so at first it looked like a hardware problem.

First I made the issue reproducible. Then I narrowed it down: was it the sensor, the peripheral configuration, or the driver? Using the UDE debugger, I compared the pulse widths captured by the timer with the values the driver decoded. That showed the root cause: the driver converted each pulse width into ticks by truncating instead of rounding, and it used the nominal tick length instead of the one measured from the 56-tick calibration pulse. When a sensor's clock ran a few percent fast, a nibble that should be 18 ticks measured about 17.5 nominal ticks and was cut down to 17, which corrupted the data and the CRC.

We fixed it by deriving the tick length from each frame's calibration pulse and rounding to the nearest tick.

After the fix, I verified it on both targets with sensor clock deviations across the allowed range, including the edges, and made sure those cases were covered by tests so it wouldn't come back. The main lesson I took: for timing bugs, measure at the lowest level instead of guessing.
