➕ 2. VectorCAST

Giống Cantata về khái niệm. Tool sinh driver và stub từ code, bạn chỉ khai báo test case (input, expected, hành vi stub). Code dưới test được instrument để đo coverage.
Sản phẩm
VectorCAST (Vector, trước là Vector Software) có các phần chính: VectorCAST/C++ (unit/integration test cho C/C++), VectorCAST/QA (đo coverage cho test hệ thống/bench đang có), VectorCAST/Manage (quản lý nhiều environment, regression, xu hướng), cộng thêm tính năng change-based testing (chỉ chạy lại test bị ảnh hưởng bởi thay đổi).
Environment
Mỗi đơn vị test là một environment: chọn file nguồn (UUT), cách xử lý phụ thuộc (stub tất cả / stub theo chỉ định / dùng code thật), compiler và cờ biên dịch. Tạo bằng GUI hoặc file .env / script.
Test case
Nhập giá trị cho tham số, biến toàn cục, giá trị trả về của stub; đặt expected cho output. Có hỗ trợ test case kiểu range/list, test sinh tự động (basis path) để tăng coverage nhanh, và user code khi cần logic phức tạp.
Coverage
Statement, branch, MC/DC, function, function call. ISO 26262-6 khuyến nghị cao: statement (ASIL A–B), branch (B–D), MC/DC (D) ở mức unit.
Chạy trên target
Harness được biên dịch bằng cross-compiler, nạp qua debugger (ví dụ TRACE32) hoặc simulator, kết quả đọc về qua debugger hoặc UART. Phát hiện lỗi chỉ xuất hiện trên compiler/CPU thật (kích thước kiểu, căn chỉnh, tối ưu).
CLI & CI
clicast là giao diện dòng lệnh; manage cho project VectorCAST/Manage. Biến môi trường VECTORCAST_DIR trỏ tới thư mục cài đặt. Có Jenkins plugin sinh job từ project Manage, chạy song song các environment, và xuất báo cáo (JUnit XML cho kết quả, coverage report) lên Jenkins.
# Chạy regression VectorCAST trong CI (minh hoạ; tên project theo dự án)
export VECTORCAST_DIR=/opt/vcast
$VECTORCAST_DIR/manage -p TcuUnitTests --build-execute --level=HOST/GNU/UnitSuite
$VECTORCAST_DIR/manage -p TcuUnitTests --full-status=report.html
# Xuất JUnit XML + coverage cho Jenkins: dùng script đi kèm VectorCAST Jenkins plugin
# (tên script/tham số khác nhau theo phiên bản; tra tài liệu của phiên bản dự án đang dùng)

✅ 2.1 MC/DC nhắc nhanh

Mỗi điều kiện con trong một quyết định phải được chứng minh độc lập ảnh hưởng tới kết quả: có hai test chỉ khác nhau ở điều kiện đó mà kết quả quyết định đổi. Với n điều kiện cần tối thiểu n+1 test.

if ((regStatus == REG_HOME || regStatus == REG_ROAMING) && (signalDbm > -110))

/*   1   | 1 0 1 |   1       A: 1 vs 4                                                  */

✅ 3. MISRA C — bản cập nhật tới 2025

Phiên bảnNămĐiểm chính
MISRA C:20042004C90/C99 một phần; nhiều dự án legacy vẫn theo.
MISRA C:20122012Cấu trúc hiện đại: directive + rule, phân loại mandatory/required/advisory, decidable/undecidable. Amendment 1 (2016, bảo mật), Amendment 2 (2020, C11/C18), Amendment 3/4 (2023, đa luồng, atomics).
MISRA C:20232023Gộp C:2012 cùng các amendment thành một tài liệu (MISRA C:2012 third edition + AMD 1–4), hỗ trợ C11/C18.
MISRA C:20253/2025Bản mới nhất: khoảng 225 guideline. Thêm rule mới (ví dụ 8.18, 8.19, 11.11, 19.3), gỡ bỏ một số, và Rule 15.5 (single point of exit) bị bỏ. Dự án đang chạy thường giữ phiên bản đã chốt; dự án mới cân nhắc 2023/2025.
Mandatory
Bắt buộc tuân thủ, không được deviation. Ví dụ: không đọc biến tự động chưa khởi tạo (Rule 9.1).
Required
Phải tuân thủ, trừ khi có deviation chính thức được ghi và phê duyệt.
Advisory
Khuyến nghị; có thể bỏ qua mà không cần deviation chính thức (nhưng nên ghi lại), hoặc dự án nâng lên required.
Decidable / undecidable
Decidable: tool xác định chắc chắn đúng/sai. Undecidable: phụ thuộc giá trị lúc chạy (ví dụ tràn số, con trỏ null) nên tool có thể báo sai hoặc bỏ sót; cần review bổ sung.
Deviation
Ghi: rule nào, vị trí, lý do kỹ thuật, biện pháp bù đắp, người duyệt. Deviation lặp lại có thể thành deviation permit áp dụng rộng. Code vendor (MCAL/BSW) thường đi kèm danh sách deviation của vendor.
Compliance
MISRA Compliance:2020 quy định cách tuyên bố tuân thủ: GEP (Guideline Enforcement Plan: tool nào kiểm rule nào), GRP (re-categorization), danh sách deviation, và Guideline Compliance Summary.

✅ 3.1 Rule hay bị hỏi (ví dụ quen thuộc)

/* 10.4 – toán hạng của phép toán số học phải cùng essential type category */
uint8  u8 = 5u;  sint16 s16 = -3;
x = u8 + s16;                         /* vi phạm: unsigned + signed */
x = (sint16)u8 + s16;                 /* ok: ép tường minh */

/* 14.4 – điều kiện if phải có kiểu essentially Boolean */
if (ptr)          { }                  /* vi phạm */
if (ptr != NULL)  { }                  /* ok */

/* 16.4 – mọi switch phải có default; 16.3 – mỗi clause kết thúc bằng break */
/* 17.7 – giá trị trả về của hàm non-void phải được dùng */
(void)memcpy(dst, src, len);           /* bỏ tường minh */

/* 21.3 – không dùng malloc/free của stdlib */
/* 11.3 – không ép con trỏ sang kiểu con trỏ đối tượng khác (thường gặp khi đọc buffer CAN) */
📝

Rule 15.5 bị bỏ trong C:2025: trước đây advisory "một hàm chỉ nên có một điểm thoát". Bỏ vì early return thường làm code rõ hơn. Nếu được hỏi, trả lời: dự án theo phiên bản nào thì theo phiên bản đó; không tự ý áp rule của bản mới vào dự án đã chốt bản cũ.

✅ 4. Static analysis như một gate trong CI

Tool phổ biến
Helix QAC (Perforce), Polyspace Bug Finder / Code Prover (MathWorks), Coverity, Klocwork, PC-lint Plus, Parasoft C/C++test, Axivion, cppcheck (miễn phí, MISRA addon một phần). Polyspace Code Prover dùng abstract interpretation để chứng minh không có một số loại lỗi runtime.
Cấu hình giống build
Tool phải thấy đúng define, include path, kích thước kiểu của target. Thường lấy từ compile commands (compile_commands.json) hoặc bọc lệnh build.
Baseline + chặn mới
Codebase cũ có hàng nghìn cảnh báo. Chiến lược thực tế: chốt baseline, chặn cảnh báo mới ở từng change (quality gate "no new violations"), giảm nợ cũ dần theo kế hoạch.
Tách theo nguồn gốc
Code vendor (MCAL, BSW, thư viện modem) và code sinh ra (tresos, RTE) được phân tích riêng hoặc loại trừ, dựa vào deviation của vendor. Chỉ gate chặt code do team viết.
Nhanh cho pre-merge
Phân tích incremental file thay đổi ở gate pre-merge; full analysis chạy nightly.
Compiler warnings
Bật -Wall -Wextra (hoặc tương đương compiler thương mại) và coi warning mới là lỗi. Rẻ nhất và bắt nhiều lỗi thật.

✅ 5. Test pyramid trong pipeline TCU

  • Pre-merge (vài phút)

    Build các biến thể chính, compiler warning, static analysis incremental, unit test VectorCAST liên quan tới thay đổi (change-based), pytest cho tool/script.

  • Gate (Zuul, mười mấy phút)

    Build đầy đủ, toàn bộ unit test, smoke test trên vECU hoặc một bench: boot, CAN alive, UDS đọc version, modem trả lời AT.

  • Nightly

    Full static analysis + báo cáo MISRA, regression bench/HIL đầy đủ, coverage tổng, đo kích thước ROM/RAM, xu hướng trên Grafana.

  • Release

    Toàn bộ test theo requirement, bằng chứng truy vết (requirement → test → kết quả), báo cáo MISRA compliance và deviation, coverage đạt mục tiêu, lưu artifact đã promote.

6. Trước (~2020) → Nay

🔁 Test cuối dự án → shift-left, gate liên tục
⏪ Trước (~2020)

Unit test chạy thủ công trên máy test engineer trước mốc release; MISRA check chạy cuối sprint, xuất báo cáo PDF hàng nghìn dòng; bench test lên lịch tay. MISRA C:2012 + amendment rời rạc.

⏩ Nay

Unit test và static analysis chạy mỗi change, change-based testing để nhanh; "no new violations" là gate; bench tự động qua CI và resource lock; SIL/vECU để test integration sớm. MISRA C:2023 gộp, rồi C:2025. Công cụ AI hỗ trợ sinh test case và giải thích vi phạm đang xuất hiện, nhưng bằng chứng vẫn phải từ tool đã qualified.

Vì sao quan trọng: Người phỏng vấn CI lead muốn nghe bạn đặt test ở đâu trong pipeline và làm sao để nhanh mà không bỏ bằng chứng chất lượng.

7. Tự kiểm tra

White-box, grey-box, black-box khác nhau thế nào? Cho ví dụ trong TCU. Định nghĩa▾

White-box dựa vào cấu trúc code, đo coverage (unit test AT parser). Grey-box biết kiến trúc và interface, có thể quan sát trạng thái nội bộ (integration test: gửi CAN, đọc biến qua TRACE32/XCP). Black-box chỉ dựa vào requirement và input/output ngoài (bench: bấm nút SOS, kiểm tra cuộc gọi và MSD).

Mandatory, required, advisory trong MISRA khác nhau thế nào? Deviation cần gì? Định nghĩa▾

Mandatory: không được deviation. Required: tuân thủ trừ khi có deviation chính thức. Advisory: khuyến nghị, không cần deviation chính thức. Deviation ghi rule, vị trí, lý do kỹ thuật, rủi ro và biện pháp bù đắp, người phê duyệt, và được lưu để truy vết. Phiên bản mới nhất là MISRA C:2025 (khoảng 225 guideline, bỏ Rule 15.5).

Dự án có 8.000 cảnh báo MISRA cũ. Làm sao đưa static analysis vào CI mà không chặn mọi change? Áp dụng▾

Chốt baseline hiện tại; gate chỉ fail khi change thêm vi phạm mới (so với baseline, theo file/hàm). Loại code vendor và code sinh ra khỏi gate, dựa vào deviation của vendor. Mandatory rule chặn tuyệt đối. Lập kế hoạch giảm nợ cũ theo module ưu tiên (code an toàn trước), theo dõi xu hướng trên dashboard. Phân tích incremental ở pre-merge, full ở nightly.

Unit test pass trên host nhưng fail trên target. Nguyên nhân có thể? Áp dụng▾

Kích thước kiểu khác (int 16/32/64-bit, long), endianness, căn chỉnh và padding struct, hành vi undefined/implementation-defined (dịch bit số âm, tràn signed), tối ưu compiler (thiếu volatile), stack nhỏ trên target, thư viện chuẩn khác. Vì thế nên chạy ít nhất một phần test trên target hoặc simulator với đúng compiler, và dùng Platform_Types thay kiểu trần.

Làm sao để unit test nhanh trong pre-merge mà vẫn đủ? Áp dụng▾

Change-based testing (VectorCAST chỉ chạy lại environment bị ảnh hưởng), chạy song song nhiều environment trên nhiều agent, tách host test (nhanh, mỗi change) và target test (chậm, gate/nightly), cache kết quả build harness. Full regression vẫn chạy nightly để bắt ảnh hưởng gián tiếp.

Kinh nghiệm test và coverage của bạn? Kinh nghiệm▾

Bám CV: tôi thiết kế và chạy MCAL unit/component validation cho các nhóm driver digital I/O, analog, timer, communication, watchdog trên cả target và VECU; viết test logic và automation với Pytest, Cantata và ECU-Test, gồm cô lập phụ thuộc, mocking/stubbing, fault injection, giá trị biên và test hướng coverage. Tôi chịu trách nhiệm phân tích requirement, truy vết requirement-to-test, bằng chứng test và sẵn sàng review theo ASPICE. VectorCAST là tool mới với tôi nhưng cùng mô hình với Cantata. Không nhận đã dùng VectorCAST hay Helix QAC nếu chưa dùng.
