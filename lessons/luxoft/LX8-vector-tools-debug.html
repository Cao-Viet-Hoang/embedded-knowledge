🎯 2. CAPL — viết được bằng tay

Là gì
CAN Access Programming Language: ngôn ngữ giống C, hướng sự kiện, chạy trong CANoe/CANalyzer. Không có main; code nằm trong các handler on ....
Sự kiện chính
on start, on preStart, on stopMeasurement, on message X, on signal X, on timer t, on key 'a', on sysvar, on diagResponse, on linFrame, on errorFrame, on busOff.
Hàm hay dùng
output(msg) gửi; setTimer(t, ms) / setTimerCyclic / cancelTimer; write() in ra Write window; timeNow() (đơn vị 10 µs); this là message vừa nhận; $Signal đọc/ghi giá trị signal; @sysvar biến hệ thống.
Test module
Trong test module có testcase, testWaitForMessage(id, timeout), testWaitForSignalMatch, testStepPass/Fail, và MainTest() gọi các testcase. Kết quả xuất XML/HTML report, đưa vào CI được.
/*@!Encoding:1252*/
variables
{
  message TCU_Status  msgStatus;          // định nghĩa trong DBC
  msTimer tCycle;
  msTimer tTimeout;
  int     aliveCnt = 0;
}

on start
{
  setTimer(tCycle, 100);                  // gửi TCU_Status mỗi 100 ms (mô phỏng TCU khi ECU thật chưa có)
  setTimer(tTimeout, 500);
}

on timer tCycle
{
  msgStatus.AliveCounter = aliveCnt;
  aliveCnt = (aliveCnt + 1) % 16;
  output(msgStatus);
  setTimer(tCycle, 100);                  // timer một lần → đặt lại
}

on message Gateway_Ignition               // ECU khác gửi trạng thái khoá điện
{
  cancelTimer(tTimeout);
  setTimer(tTimeout, 500);                // timeout monitoring
  if (this.IgnitionState == 0)
    write("Ignition OFF at %.3f s", timeNow() / 100000.0);
}

on timer tTimeout
{
  write("ERROR: Gateway_Ignition timeout");
}
// Test module: kiểm tra TCU trả lời UDS ReadDataByIdentifier F189 (SW version)
testcase TC_ReadSwVersion()
{
  message DiagReq_TCU req;
  req.dlc = 8;
  req.byte(0) = 0x03; req.byte(1) = 0x22; req.byte(2) = 0xF1; req.byte(3) = 0x89;
  output(req);
  if (testWaitForMessage(DiagResp_TCU, 100) == 1)
    testStepPass("Resp", "Positive response received");
  else
    testStepFail("Resp", "No response within 100 ms");
}

void MainTest()
{
  TC_ReadSwVersion();
}
📝

Thực tế dự án dùng Diagnostic API của CANoe (diagRequest, diagSendRequest) với CDD/ODX thay vì ghép byte như trên, và thường viết test trong vTESTstudio. Ví dụ ghép byte để bạn nhớ cơ chế (single frame ISO-TP: byte 0 = độ dài).

➕ 2.1 CANoe trong CI

Tự động hoá
CANoe có COM interface (Windows) và API Python (thư viện của Vector hoặc gói cộng đồng như py_canoe) để mở config, start measurement, chạy test module, lấy kết quả. Có bản CANoe Server Edition / chế độ không GUI cho máy CI.
License
License CANoe (dongle hoặc network) là tài nguyên khan hiếm giống bench: phải lock trong CI (lock() Jenkins, resource_group GitLab, semaphore Zuul).
Kết quả
Test report XML của CANoe chuyển sang JUnit để Jenkins/Zuul hiển thị; log BLF lưu làm artifact để debug sau.

➕ 4. XCP & A2L (nền của CANape)

XCP
Universal Measurement and Calibration Protocol (ASAM MCD-1 XCP), kế thừa CCP. Chạy trên CAN, CAN FD, Ethernet (UDP/TCP), FlexRay, SPI/SCI. Master (CANape) – slave (ECU có XCP driver).
Polling vs DAQ
Polling: master hỏi từng biến (chậm). DAQ: master cấu hình danh sách biến gắn với sự kiện trong ECU (ví dụ task 10 ms); ECU tự gửi đồng bộ, có timestamp. STIM là chiều ngược lại (bơm dữ liệu vào ECU).
Calibration
Ghi tham số vào RAM lúc chạy; cơ chế page switching (working page RAM / reference page flash) để thử rồi mới ghi flash.
A2L
File ASAM MCD-2 MC mô tả biến đo (MEASUREMENT) và tham số (CHARACTERISTIC): địa chỉ, kiểu, công thức đổi đơn vị (COMPU_METHOD), giới hạn. Địa chỉ phải khớp đúng ELF; CI nên cập nhật A2L từ ELF/map mỗi build, nếu không CANape đọc sai địa chỉ.
Bảo mật
XCP có seed & key; trên xe sản xuất thường tắt hoặc khoá. Với TCU (cửa ngõ ra internet) đây là điểm nhạy cảm cybersecurity.

✅ 5. Lauterbach TRACE32 & iSystem

TRACE32 (CV có)
Phần cứng PowerDebug + đầu JTAG/Nexus/Aurora cho từng kiến trúc (RH850, TriCore, Arm). Chức năng: flash, breakpoint (phần mềm/phần cứng), đọc/ghi register và memory, trace (on-chip hoặc off-chip), đo thời gian, phân tích OS-aware (hiển thị task của OSEK/AUTOSAR OS qua ORTI/ARTI).
PRACTICE (.cmm)
Ngôn ngữ script của TRACE32: tự động hoá chuỗi thao tác (reset, flash, chạy tới điểm, đọc biến, so sánh, ghi log). Là cách đưa debugger vào CI.
Remote API
TRACE32 mở cổng Remote API (cấu hình trong config.t32, ví dụ RCL=NETASSIST PORT=20000); điều khiển từ Python qua gói lauterbach-trace32-rcl (pyrcl) hoặc C API. CI job: khởi động T32 headless, flash, chạy test, đọc kết quả từ memory.
iSystem (nay là TASKING)
iSystem được TASKING mua lại (2022); debugger phần cứng BlueBox, IDE winIDEA, API isystem.connect (Python/C++) và testIDEA cho test trên target. Khái niệm tương tự TRACE32: flash, breakpoint, trace, profiling, script hoá.
; flash_and_smoke.cmm  — PRACTICE script (minh hoạ)
RESet
SYStem.CPU R7F701Z03              ; chọn CPU (tên ví dụ)
SYStem.Up
FLASH.ReProgram ALL
Data.LOAD.Elf "build/tcu_app.elf"
FLASH.ReProgram OFF
Go main
WAIT !STATE.RUN() 2.s
Go
WAIT 3.s
Break
&cnt=Var.VALUE(Os_Cyclic10msCounter)
IF &cnt<250.
(
  PRINT %ERROR "Smoke FAIL: cyclic counter=" &cnt
  ENDDO FALSE()
)
PRINT "Smoke PASS: cyclic counter=" &cnt
ENDDO TRUE()
# Điều khiển TRACE32 từ Python trong CI (gói lauterbach-trace32-rcl)
import lauterbach.trace32.rcl as t32

dbg = t32.connect(node="localhost", port=20000, protocol="TCP")
dbg.cmd('CD.DO "flash_and_smoke.cmm"')                  # chạy script PRACTICE
ok = dbg.fnc("PRACTICE.CoMmanD.AVAILable(ENDDO)")        # tuỳ cách script trả kết quả
counter = dbg.variable.read("Os_Cyclic10msCounter").value
print(f"cyclic counter = {counter}")
assert counter >= 250, "smoke test failed"
⚠️

Tên lệnh/API trong hai ví dụ là để minh hoạ cơ chế; tra tài liệu phiên bản TRACE32 của dự án trước khi dùng. Khi phỏng vấn, nói cơ chế: "PRACTICE script for the sequence, Remote API from Python to drive it from Jenkins, results read from memory or returned by the script, debugger locked as a resource."

6. Trước (~2020) → Nay

🔁 Tool trên bàn kỹ sư → tool trong pipeline
⏪ Trước (~2020)

CANoe và TRACE32 là tool tương tác trên laptop kỹ sư; test CAPL chạy tay; CAN 500 k là chính, CAN FD mới bắt đầu. Debug nghĩa là ngồi cạnh bench.

⏩ Nay

CANoe/TRACE32/winIDEA điều khiển qua API trong CI, bench chia sẻ và lock tự động; CANoe4SW và vECU cho test trước khi có phần cứng. CAN FD phổ biến, CAN XL (tới ~20 Mbit/s, payload 2048 byte) và 10BASE-T1S đang xuất hiện; Ethernet + SOME/IP/DoIP cho zonal architecture.

Vì sao quan trọng: Vai trò này cần người biết dùng tool và biết tự động hoá tool; câu hỏi "làm sao đưa TRACE32/CANoe vào Jenkins" rất có thể xuất hiện.

7. Tự kiểm tra

CANalyzer, CANoe, CANape khác nhau thế nào? Định nghĩa▾

CANalyzer phân tích và quan sát bus. CANoe mô phỏng rest-bus, chạy test tự động và diagnostics. CANape đo lường và hiệu chuẩn biến trong ECU qua XCP/CCP với file A2L.

CAN FD khác CAN cổ điển ở đâu? Định nghĩa▾

Payload tới 64 byte (DLC 9–15 ánh xạ 12, 16, 20, 24, 32, 48, 64); bit BRS cho phép data phase chạy tốc độ cao hơn (thường 2–5 Mbit/s) với sample point riêng; ESI báo node đang error passive; CRC dài hơn (17/21 bit) và stuff bit count; không có remote frame. Arbitration giữ nguyên nên cùng tồn tại được, nhưng controller CAN cũ sẽ báo lỗi khi thấy frame FD.

Viết CAPL gửi một message chu kỳ 100 ms và báo lỗi nếu message phản hồi không tới trong 500 ms. Áp dụng▾

Hai msTimer: timer chu kỳ gửi output(msg) rồi setTimer lại (hoặc setTimerCyclic); timer timeout được đặt lại mỗi khi on message Resp tới; nếu on timer tTimeout chạy thì write lỗi hoặc testStepFail. Xem ví dụ ở mục 2.

Làm sao đưa TRACE32 vào pipeline Jenkins cho smoke test trên bench? Áp dụng▾

Agent gắn với bench có TRACE32 cài sẵn và cấu hình Remote API; job lock bench; khởi động T32 không GUI; Python (pyrcl) chạy PRACTICE script: reset, flash ELF, chạy, đọc biến kiểm tra (counter task, trạng thái init, DET error); kết quả thành JUnit XML; luôn thu log và đóng T32 trong khối post; phân biệt lỗi hạ tầng (không kết nối được debugger) với lỗi sản phẩm để không đổ lỗi sai cho change. Tôi đã dùng TRACE32 để đọc register/memory, breakpoint và trace khi điều tra lỗi integration; phần script hoá qua Remote API là bước tiếp theo tự nhiên.

CANape đọc sai giá trị biến sau khi build mới. Nghi gì? Áp dụng▾

A2L không được cập nhật theo ELF mới nên địa chỉ biến đã dịch chuyển. Sửa: bước CI cập nhật địa chỉ A2L từ ELF/map mỗi build và lưu A2L cùng artifact với đúng version. Kiểm tra thêm COMPU_METHOD và kiểu dữ liệu nếu biến đổi kiểu.

Kinh nghiệm của bạn với CANoe và debugger? Kinh nghiệm▾

Bám CV: CANoe và ECU-Test là tool trong kinh nghiệm test của tôi; Lauterbach TRACE32 để điều tra mức thấp (register, memory, breakpoint, trace/log) trên RH850 D3/D4/D5 khi tích hợp BSW; UDE Debugger để chẩn đoán và sửa lỗi timing SENT trên target ST và Infineon. CANape, iSystem/winIDEA và viết CAPL nâng cao: nói trung thực là mức hiểu khái niệm hoặc đang ôn, và nối với kinh nghiệm tương đương (XCP ≈ đọc biến qua debugger; winIDEA ≈ TRACE32).
