✅ 1. Luồng ARXML end-to-end

Hai nửa gặp nhau ở RTE. AUTOSAR Builder mô tả phía ứng dụng (SWC, port, runnable). EB tresos cấu hình phía nền tảng (BSW, MCAL, OS). RTE generator đọc cả hai và sinh code nối chúng. Một số dự án dùng RTE generator của tresos, số khác dùng tool RTE riêng; tuỳ bộ công cụ được mua.

➕ 1.1 AUTOSAR Builder (Dassault Systèmes)

Vai trò
Tool Eclipse-based để thiết kế SWC và mô hình hoá hệ thống AUTOSAR: tạo SWC type, port (sender/receiver, client/server, mode), interface, data type, runnable và RTE event, composition và connector. Có trình soạn thảo ARXML, kiểm tra tính hợp lệ theo schema, so sánh/merge ARXML, và thành phần sinh RTE/cấu hình (tuỳ gói bản quyền).
Kết quả
ARXML của SWC (SWC description), có thể sinh contract header Rte_<Swc>.h để developer viết code runnable trước khi có RTE thật.
Import từ ngoài
DBC/LDF/FIBEX của mạng xe được import thành signal, PDU, frame trong ARXML hệ thống.

🎯 1.2 EB tresos Studio (Elektrobit)

Vai trò
Tool cấu hình, kiểm tra và sinh code cho BSW (gói EB tresos AutoCore) và MCAL (nhiều hãng chip giao MCAL kèm plugin tresos). Mỗi module là một plugin có BSWMD (mô tả tham số) và generator.
Project & module config
Một project chứa danh sách module (Can, CanIf, PduR, Com, EcuM, BswM, Os, Dcm, Dem, NvM, Port, Dio, Mcu…) và giá trị tham số (ECUC values). Lưu dưới dạng XDM/ARXML trong repo.
Importer
Nhập ECU extract/DBC/LDF để tạo sẵn cấu hình COM stack (I-PDU, signal, CanIf Rx/Tx PDU, PduR routing path) thay vì nhập tay hàng trăm signal.
Verify
Chạy check rule của từng plugin: tham số bắt buộc bị trống, tham chiếu sai (ví dụ PduR trỏ tới PDU không tồn tại), giá trị ngoài miền, xung đột giữa module. Lỗi phải hết trước khi generate.
Generate
Sinh <Mod>_Cfg.h, <Mod>_Lcfg.c (link-time), <Mod>_PBcfg.c (post-build), cộng file MemMap và SchM. Code sinh ra không được sửa tay.
Command line / CI
tresos có chế độ dòng lệnh (tresos_cmd) để import, verify, generate trong pipeline không cần GUI. Đây là điểm nối trực tiếp với vai trò CI: job "config verify + generate" chạy mỗi change có sửa cấu hình, lỗi verify làm fail sớm.
Variant
Hỗ trợ biến thể (post-build selectable, predefined variant) để một bản build phục vụ nhiều cấu hình xe/thị trường. TCU bán nhiều thị trường nên có biến thể theo vùng (eCall EU / ERA-GLONASS / không có eCall).
# Job CI: verify + generate cấu hình tresos (tham số minh hoạ, xem tài liệu tresos của dự án)
tresos_cmd.sh -data ws legacy import  cfg/TcuProject  ecu_extract.arxml
tresos_cmd.sh -data ws legacy verify  TcuProject     || exit 1      # fail sớm nếu cấu hình sai
tresos_cmd.sh -data ws legacy generate TcuProject
git diff --exit-code gen/ || echo "Generated code khác bản đã commit → cần commit lại"

✅ 2. Configuration class & các lớp code

Pre-compile
Tham số trở thành #define trong _Cfg.h. Hiệu quả nhất (compiler tối ưu được, dead code bị loại) nhưng đổi là phải biên dịch lại. Ví dụ: số kênh, bật/tắt tính năng, development error detection.
Link-time
Tham số là hằng const trong _Lcfg.c. Đổi thì biên dịch lại file cấu hình và link lại, không cần build lại code module (hữu ích khi module giao dạng object/lib).
Post-build
Tham số nằm trong vùng flash riêng (_PBcfg.c), có thể nạp lại mà không đổi code (post-build loadable) hoặc chọn một trong nhiều bộ lúc khởi động (post-build selectable). Truyền con trỏ bộ cấu hình qua <Mod>_Init(ConfigPtr). Dùng cho định tuyến CAN theo biến thể xe.
Static vs generated code
Code tĩnh của module (do vendor giao, không đổi theo dự án) + code sinh ra (theo cấu hình). Integration là ghép đúng phiên bản của cả hai: plugin generator phải cùng version với code tĩnh.
BSW Scheduler (SchM)
Gọi <Mod>_MainFunction theo chu kỳ cấu hình (map vào OS task) và cung cấp exclusive area (SchM_Enter/Exit_<Mod>_<EA>), thực hiện bằng tắt ngắt hoặc OS resource tuỳ cấu hình.
MemMap
Mỗi module bọc biến/hằng/code bằng #define <MOD>_START_SEC_VAR_INIT_32 rồi #include "<Mod>_MemMap.h". File MemMap chuyển thành #pragma section của compiler cụ thể để đặt vào đúng vùng nhớ (RAM nhanh, RAM giữ qua reset, flash hằng). Sai MemMap là nguồn lỗi integration rất phổ biến.
#define CANIF_START_SEC_VAR_CLEARED_8
#include "CanIf_MemMap.h"
static uint8 CanIf_ControllerMode[CANIF_NUM_CONTROLLERS];
#define CANIF_STOP_SEC_VAR_CLEARED_8
#include "CanIf_MemMap.h"

/* CanIf_MemMap.h (một phần) – đổi sang pragma của compiler đích */
#if defined(CANIF_START_SEC_VAR_CLEARED_8)
  #undef  CANIF_START_SEC_VAR_CLEARED_8
  #pragma section ".bss.canif_8"       /* cú pháp pragma khác nhau giữa GHS / Tasking / GCC */
#elif defined(CANIF_STOP_SEC_VAR_CLEARED_8)
  #undef  CANIF_STOP_SEC_VAR_CLEARED_8
  #pragma section
#endif

✅ 3. Tích hợp component non-AUTOSAR

JD ghi rõ "Autosar/Non-Autosar components". Trong TCU, driver modem/AT, stack GNSS, thư viện TLS, bootloader, hoặc code legacy thường không phải SWC chuẩn.

Complex Device Driver (CDD)
Lối vào chính thức cho code non-AUTOSAR: CDD được truy cập trực tiếp phần cứng (hoặc qua MCAL) và có thể cung cấp port cho SWC qua RTE. AT driver của modem thường được làm thành CDD.
Wrapper SWC
Bọc thư viện legacy trong một SWC: runnable gọi hàm legacy, dữ liệu đi qua port. Giữ ranh giới rõ ràng, test được.
Tích hợp vào OS
Hàm cyclic của legacy được gọi từ một runnable hoặc từ task OS riêng; ISR của nó phải được khai báo trong cấu hình OS (cat1/cat2) chứ không cài vector trực tiếp.
Tài nguyên dùng chung
Legacy có thể tự cấu hình lại peripheral mà MCAL đang dùng (clock, pin mux, DMA). Phải thống nhất ai sở hữu peripheral nào, nếu không sẽ có lỗi "chạy riêng thì được, ghép vào thì hỏng".
Kiểu dữ liệu và biên dịch
Legacy dùng int, unsigned long, cờ compiler khác; AUTOSAR dùng uint8/uint16/uint32 (Platform_Types.h). Kiểm tra kích thước kiểu, căn chỉnh, endianness, và các warning MISRA sẽ tăng vọt.

✅ 5. Tối ưu code theo target & compiler

Mức tối ưu
-O0 (debug), -O1/-O2 (cân bằng), -Os (kích thước, thường chọn cho MCU flash nhỏ), -O3 (tốc độ, có thể phình code vì unroll/inline). Compiler thương mại (Green Hills, TASKING, Wind River Diab) có tuỳ chọn riêng; có thể tối ưu theo từng file/hàm (ví dụ ISR theo tốc độ, phần còn lại theo kích thước). Luôn test lại ở mức tối ưu sẽ ship: lỗi thiếu volatile chỉ lộ ra ở -O2.
Đọc map file
Map file cho biết kích thước từng section, từng object, địa chỉ symbol. Dùng để tìm ai chiếm nhiều flash/RAM nhất, kiểm tra biến đặt đúng vùng, và theo dõi tăng trưởng kích thước qua từng build (có thể đưa thành metric trong CI).
Đặt dữ liệu và code vào vùng nhớ nhanh
Code nóng (ISR, vòng lặp tính toán) vào RAM/cache-able region hoặc local RAM của core; bảng tra cứu hằng vào flash. Trên RH850: phân biệt local RAM của core với global RAM, và độ trễ truy cập flash (wait state).
Kiểu dữ liệu
Dùng kích thước tự nhiên của CPU (32-bit) cho biến đếm/vòng lặp; tránh uint8 cho biến lặp (compiler phải thêm lệnh cắt/mở rộng). Fixed-point thay float khi không có FPU, hoặc để tránh chi phí đổi ngữ cảnh FPU trong ISR.
Inline và hàm nhỏ
static inline cho hàm truy cập ngắn (ví dụ đọc thanh ghi) bỏ chi phí gọi hàm. Quá nhiều inline làm tăng kích thước và giảm hiệu quả cache.
Tránh chi phí ẩn
Chia/modulo số không phải luỹ thừa 2 (trên core không có lệnh chia phần cứng rất chậm), memcpy kích thước lớn trong ISR, sao chép struct lớn theo giá trị, switch thưa khiến compiler không sinh jump table.
Stack
Phân tích stack tĩnh (compiler/linker có call-graph, hoặc tool như StackAnalyzer) cộng đo động (tô pattern rồi đọc mức cao nhất bằng TRACE32). Stack task trong OS phải đủ cho đường gọi sâu nhất cộng ngữ cảnh ngắt.
Tối ưu có đo
Đo trước và sau bằng cycle counter, GPIO toggle + oscilloscope, hoặc trace của debugger. Tối ưu không có đo thường tối ưu nhầm chỗ.
/* Ví dụ: modulo cho ring buffer */
idx = (idx + 1u) % 100u;                 /* chia phần mềm nếu core không có lệnh chia nhanh */
idx = (idx + 1u) & (128u - 1u);           /* kích thước luỹ thừa 2 → một lệnh AND */

/* Ví dụ: fixed-point Q8.8 thay float cho nhiệt độ */
typedef sint16 q8_8_t;                   /* 1 LSB = 1/256 °C */
static inline q8_8_t temp_from_adc(uint16 raw)
{
    return (q8_8_t)(((sint32)raw * TEMP_GAIN_Q8) >> 8) - TEMP_OFFSET_Q8;   /* dùng sint32 trung gian để không tràn */
}

✅ 6. Chiến lược integration (vai trò Lead)

  • Baseline có kiểm soát

    Mỗi đợt integration bắt đầu từ baseline đã xanh: version cụ thể của từng component (BSW vendor release, MCAL release, SWC), ghi trong manifest. Không tích hợp "nhánh đang phát triển" của component khác.

  • Tích hợp từng bước

    Thêm một component hoặc một thay đổi lớn mỗi lần, build và smoke test ngay, để khi hỏng biết ngay do cái gì. Thứ tự thường: MCAL + OS + EcuM (boot được) → communication stack → diagnostics → memory → ứng dụng.

  • Tự động hoá kiểm tra

    Pipeline: verify config → generate → build tất cả biến thể → static analysis → unit test → smoke trên bench. Người tích hợp không làm tay những việc máy làm được.

  • Integration test theo interface

    Test hướng vào ranh giới giữa component: signal đi đúng từ CAN tới SWC, DTC được ghi khi lỗi, mode chuyển đúng. Liên hệ ASPICE SWE.5 (LX7).

  • Release note & truy vết

    Mỗi bản tích hợp có release note: component version, lỗi đã sửa, lỗi còn tồn (known issues), kết quả test. Artifact lưu trong Artifactory kèm build info.

8. Tự kiểm tra

Pre-compile, link-time, post-build khác nhau thế nào? Ví dụ khi nào dùng post-build? Định nghĩa▾

Pre-compile: #define, tối ưu nhất, đổi là build lại. Link-time: hằng const trong file cấu hình riêng, đổi thì compile file đó và link lại. Post-build: bảng cấu hình ở vùng flash riêng, truyền qua con trỏ lúc Init, có thể chọn/nạp lại mà không đổi code. Dùng post-build khi một phần mềm phục vụ nhiều biến thể xe có ma trận CAN khác nhau, hoặc khi nhà cung cấp giao library mà OEM vẫn muốn đổi routing.

EB tresos Verify báo lỗi tham chiếu PduR tới PDU không tồn tại sau khi import DBC mới. Bạn làm gì? Áp dụng▾

DBC mới đã đổi tên hoặc xoá frame/PDU, nhưng routing path cũ vẫn trỏ tới. Bước: so sánh DBC cũ/mới (frame nào đổi), xác nhận với người quản lý communication matrix xem thay đổi có chủ ý không, cập nhật hoặc xoá routing path trong PduR, và kiểm tra các SWC còn dùng signal đó không. Đưa verify vào CI để lỗi kiểu này bị chặn ngay ở change sửa DBC, không phải lúc build tổng.

Một message CAN có trên bus nhưng SWC không nhận được giá trị. Debug từng bước? Áp dụng▾

Đi từ dưới lên, mỗi lớp có bằng chứng: (1) CANoe xác nhận frame, ID, DLC, chu kỳ. (2) Can driver: controller STARTED, filter/HRH khớp ID (standard hay extended). (3) Breakpoint CanIf_RxIndication: có gọi không, HRH/PDU ID đúng không, DLC check. (4) PduR có routing path tới Com. (5) Com_RxIndication: I-PDU group đã start chưa, deadline monitoring có đang báo timeout. (6) Unpack signal: byte order, start bit. (7) RTE: port nối chưa, runnable có chạy không. Đây đúng là việc tôi làm khi là BSW integrator trên RH850 với TRACE32.

Đào tiếp
  • Nếu chỉ lỗi ở extended ID thì nghi gì trước?
Tích hợp một thư viện modem non-AUTOSAR vào ECU AUTOSAR. Cách làm? Áp dụng▾

Làm thành CDD: thư viện dùng UART qua MCAL (hoặc trực tiếp nếu MCAL không hỗ trợ tính năng cần), ISR khai báo trong OS config là cat2, hàm cyclic được gọi từ task OS hoặc runnable, dữ liệu với ứng dụng đi qua port RTE. Thống nhất quyền sở hữu peripheral (pin, clock, DMA) với cấu hình MCAL. Bọc kiểu dữ liệu theo Platform_Types, đặt biến qua MemMap. Viết test ở ranh giới CDD (có thể mock UART trên host). Chạy MISRA và ghi deviation cho phần code vendor không sửa được.

"Optimize code for target hardware and compiler": bạn làm gì cụ thể? Áp dụng▾

Đo trước bằng trace/cycle counter và map file. Sau đó: chọn mức tối ưu theo file (ISR theo tốc độ, còn lại -Os), đặt code/dữ liệu nóng vào RAM nhanh qua MemMap/linker script, dùng kiểu 32-bit cho biến lặp, fixed-point khi không có FPU, tránh chia không phải luỹ thừa 2 trong đường nóng, inline hàm ngắn. Kiểm tra stack bằng phân tích tĩnh và tô pattern. Theo dõi kích thước ROM/RAM mỗi build trong CI để phát hiện phình to sớm. Luôn test lại ở cấu hình compiler sẽ ship.
