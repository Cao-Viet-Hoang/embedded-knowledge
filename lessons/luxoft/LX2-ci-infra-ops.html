✅ 1. Kiến trúc một hệ CI embedded điển hình

Hai loại tài nguyên rất khác nhau. Build agent là gia súc (cattle): giống hệt nhau, dựng từ image, hỏng thì vứt đi tạo cái mới, co giãn trên cloud. Bench agent là thú cưng (pet): phần cứng thật, có trạng thái, khan hiếm, phải giữ gìn và giám sát. Chiến lược CI tốt đẩy tối đa việc sang loại thứ nhất.

➕ 2. Ansible — Infrastructure as Code

Agentless
Không cần cài daemon trên máy đích. Ansible SSH (Linux) hoặc WinRM/SSH (Windows) vào, đẩy module Python sang chạy, lấy kết quả JSON về. Chỉ cần Python trên máy đích (Linux). Lợi thế so với Puppet/Chef (cần agent).
Inventory
Danh sách máy và nhóm ([build_agents], [bench_pcs]), dạng INI/YAML tĩnh hoặc dynamic inventory (plugin aws_ec2 tự liệt kê instance theo tag). Biến theo nhóm trong group_vars/, theo máy trong host_vars/.
Playbook · play · task
Playbook (YAML) gồm các play; mỗi play áp một danh sách task lên một nhóm host. Mỗi task gọi một module (apt, copy, template, service, win_package…).
Idempotent
Chạy lại nhiều lần cho cùng kết quả; task chỉ báo changed khi thật sự thay đổi. Module khai báo trạng thái mong muốn (state: present) thay vì lệnh. Đây là tính chất quan trọng nhất và là câu hỏi hay gặp. shell/command không tự idempotent, phải thêm creates: hoặc changed_when:.
Role
Gói tái sử dụng có cấu trúc chuẩn: tasks/, handlers/, templates/ (Jinja2), defaults/, vars/, files/. Ví dụ role trace32, ghs_compiler, jenkins_agent. Chia sẻ qua Ansible Galaxy hoặc collection nội bộ.
Handler
Task chỉ chạy khi được notify và chạy một lần ở cuối play, ví dụ restart service khi file cấu hình đổi.
Check / diff mode
--check --diff: chạy thử, cho biết sẽ đổi gì mà không đổi thật. Dùng trong CI của chính repo hạ tầng trước khi áp lên bench thật.
Vault
ansible-vault mã hoá biến bí mật (token Artifactory, license key) để commit an toàn vào Git.
Liên hệ Zuul
Mọi job Zuul là Ansible playbook chạy từ executor. Biết Ansible nghĩa là đọc và viết được job Zuul.
# site.yml — cấu hình bench PC
- hosts: bench_pcs
  become: true
  vars:
    t32_version: "2025.09"
  roles:
    - role: trace32          # cài TRACE32, copy config.t32, bật API port
    - role: vector_driver    # driver VN1630/VN1640
  tasks:
    - name: Cài python deps cho bench test
      ansible.builtin.pip:
        requirements: /opt/bench/requirements.txt
        virtualenv: /opt/bench/venv
    - name: Đặt udev rule cho debugger USB
      ansible.builtin.copy:
        src: files/99-lauterbach.rules
        dest: /etc/udev/rules.d/99-lauterbach.rules
      notify: reload udev
  handlers:
    - name: reload udev
      ansible.builtin.command: udevadm control --reload-rules

✅ 3. Docker — đóng gói toolchain

Vì sao dùng trong embedded CI
Build tái lập (reproducible): compiler, Python, CMake, tool generate được đóng băng vào image có tag. Máy nào chạy image đó cũng ra cùng ELF. Build 2 năm trước (release đã ship) vẫn dựng lại được bằng image cũ, điều cần cho truy vết an toàn chức năng.
Image vs container
Image: template chỉ đọc, gồm nhiều layer. Container: instance chạy của image, có layer ghi tạm thời, mất khi xoá.
Layer cache
Mỗi lệnh trong Dockerfile tạo một layer; Docker dùng lại layer nếu lệnh và các layer trước không đổi. Đặt thứ ít thay đổi (cài OS package, compiler) lên trên, thứ hay đổi (requirements của dự án) xuống dưới.
Multi-stage build
Stage 1 cài/biên dịch tool, stage cuối chỉ copy kết quả sang image gọn. Giảm kích thước và bề mặt tấn công.
Tag & digest
Không dùng latest trong pipeline. Dùng tag có version (build-ghs:2026.2) hoặc pin bằng digest @sha256:… để chắc chắn bất biến.
Giới hạn
Compiler thương mại cần license server (FlexLM) truy cập qua mạng. Tool chỉ có trên Windows (một số version tresos, CANoe) cần Windows container hoặc VM. Truy cập USB (debugger, VN interface) từ container phức tạp, nên bench thường chạy trên host trực tiếp.
Volume & bind mount
Mount workspace từ host vào container; mount thư mục ccache bền để giữ cache giữa các lần build.
# Dockerfile (rút gọn)
FROM ubuntu:24.04 AS base
RUN apt-get update && apt-get install -y --no-install-recommends \
      cmake ninja-build python3 python3-venv ccache git && rm -rf /var/lib/apt/lists/*
COPY toolchains/arm-gnu-14.2 /opt/arm-gnu            # layer ít đổi
ENV PATH=/opt/arm-gnu/bin:$PATH CCACHE_DIR=/cache/ccache
COPY requirements.txt /tmp/                          # layer hay đổi, đặt cuối
RUN python3 -m venv /opt/venv && /opt/venv/bin/pip install -r /tmp/requirements.txt

# build & push lên Artifactory với tag có version
docker build -t artifactory.local/tcu/build-arm:2026.2 .
docker push  artifactory.local/tcu/build-arm:2026.2

➕ 4. JFrog Artifactory — kho artifact & thăng hạng

Loại repository
Local: lưu artifact do mình tạo. Remote: proxy/cache nguồn ngoài (PyPI, Docker Hub, ConanCenter), tăng tốc và giữ được khi nguồn ngoài sập hoặc bị xoá gói. Virtual: gộp nhiều local + remote dưới một URL duy nhất.
Package type
Docker, Conan (C/C++), PyPI, Maven, npm, và Generic (file tuỳ ý: ELF, HEX, A2L, report). Firmware TCU thường vào generic repo, library C vào Conan.
Promotion
Không build lại để release. Cùng một binary được chuyển (move/copy) từ tcu-dev-local → tcu-test-local → tcu-release-local khi qua từng cổng chất lượng. Nguyên tắc "build once, promote many": binary đã test chính là binary được ship.
Build info
Metadata gắn với mỗi build: commit, pipeline, dependency đã dùng (và checksum), môi trường. Trả lời được "binary này build từ đâu, dùng lib nào" → truy vết cho ASPICE SUP.8 và ISO 26262.
Properties & AQL
Gắn thuộc tính key-value (git.commit, test.bench=passed) lên artifact, truy vấn bằng AQL (Artifactory Query Language) để tìm "bản release mới nhất đã pass bench".
Retention / cleanup
Artifact dev sinh ra mỗi change làm đầy đĩa rất nhanh. Chính sách xoá theo tuổi/số lượng cho repo dev, giữ vĩnh viễn repo release.
Checksum dedup
Artifactory lưu theo checksum SHA-1/SHA-256: cùng nội dung chỉ lưu một bản vật lý, nên copy/promote gần như không tốn dung lượng.
🎤

Nối với CV: đã tích hợp Conan vào pipeline để quản lý package C/C++ và artifact trên Azure. Conan remote trỏ vào Artifactory là cấu hình phổ biến nhất, nên có thể nói: "Tôi đã dùng Conan để version hoá và tái sử dụng package. Trong setup của các bạn, remote đó có lẽ là Artifactory."

➕ 6. Grafana + VictoriaMetrics — đo sức khoẻ CI

VictoriaMetrics
CSDL time-series tương thích Prometheus (nhận remote-write, hỗ trợ PromQL và mở rộng MetricsQL), nén tốt và tốn ít RAM hơn. "Victoria" trong JD nhiều khả năng là nó, dùng làm datasource cho Grafana. Nếu hỏi, xác nhận lại với interviewer.
Luồng dữ liệu
Exporter (Jenkins Prometheus plugin, Zuul statsd metrics, node_exporter trên agent, script đọc trạng thái bench) → scrape/push → VictoriaMetrics → Grafana dashboard + alert.
Metric kiểu counter/gauge/histogram
Counter chỉ tăng (tổng build), xem bằng rate(). Gauge lên xuống (độ dài queue, số agent rảnh). Histogram phân phối (thời gian build) → xem p50/p95 bằng histogram_quantile().
KPI của CI
  • Queue time: thời gian chờ agent. Tăng → thiếu tài nguyên.
  • Build/test duration p50/p95: xu hướng chậm dần.
  • Success rate theo job, tách lỗi do code và lỗi hạ tầng.
  • Flaky rate: test fail rồi pass khi chạy lại cùng commit.
  • Gate throughput: số change merge/ngày, số lần gate reset.
  • Bench utilization & availability: bench offline bao lâu.
  • Feedback time: từ push tới Verified vote.
Alert
Ví dụ: queue > 30 phút trong 15 phút liên tục, bench không phản hồi health check, đĩa agent > 90%, success rate một job tụt dưới ngưỡng.
# PromQL/MetricsQL ví dụ
# p95 thời gian job build trong 1 ngày
histogram_quantile(0.95, sum(rate(ci_job_duration_seconds_bucket{job="tcu-build"}[1d])) by (le))
# tỉ lệ fail do hạ tầng
sum(rate(ci_job_result_total{result="infra_error"}[1h])) / sum(rate(ci_job_result_total[1h]))

✅ 7. HIL bench trong vòng CI

Bench job đáng tin. Điểm khác biệt của người làm CI giỏi: tách được "code sai" khỏi "bench hỏng". Nếu không, developer mất niềm tin, bấm recheck liên tục, và gate bị tắc.
# conftest.py — fixture bench (rút gọn)
import pytest, subprocess, time

@pytest.fixture(scope="session")
def tcu(request):
    psu = Psu("/dev/ttyUSB0")
    psu.cycle(off_s=2)                                    # trạng thái sạch
    rc = subprocess.run(["t32", "-s", "flash.cmm", request.config.getoption("--elf")],
                        timeout=300).returncode
    if rc != 0:
        pytest.exit("INFRA_ERROR: flash failed", returncode=3)  # mã riêng cho lỗi hạ tầng
    ecu = Ecu(can_channel=0)
    assert ecu.wait_boot(timeout_s=10), "TCU không boot sau khi flash"
    yield ecu
    ecu.close(); psu.off()

@pytest.mark.smoke
def test_modem_registers(tcu):
    at = tcu.at_port()
    assert at.send("AT+CEREG?", timeout_s=2).stat in (1, 5)   # home / roaming

✅ 8. Playbook tối ưu: tốc độ · ổn định · hiệu quả · khả năng mở rộng

Câu hỏi mở hay gặp: "CI hiện mất 2 tiếng và hay fail ngẫu nhiên. Bạn sẽ làm gì trong 3 tháng đầu?" Trả lời theo cấu trúc: đo trước → sửa chỗ tốn nhất → chống tái phát.

  • Đo trước (tuần 1–2)

    Dựng dashboard: thời gian từng stage, queue time, success rate, flaky rate. Tìm 20% job chiếm 80% thời gian. Không tối ưu theo cảm tính.

  • Tốc độ

    Cache: ccache/sccache cho compile, layer Docker, remote cache Conan. Song song: -j, parallel stage, sharding test (pytest -n, chia theo thời gian lịch sử). Incremental: chỉ generate lại BSW khi ARXML đổi; chỉ chạy test liên quan file thay đổi ở check. Phân tầng: check nhanh (<15 phút), gate vừa, nightly đầy đủ.

  • Ổn định

    Phân loại lỗi PASS/FAIL/INFRA. Quarantine flaky test: phát hiện bằng chạy lại cùng commit, đưa vào danh sách cách ly (vẫn chạy, không chặn gate), tạo ticket có owner và hạn. Health check bench, auto offline. Pin mọi version tool (image digest). Timeout ở mọi bước.

  • Hiệu quả

    Retention artifact, spot instance cho build, tắt agent ngoài giờ, gom license (compiler license là chi phí lớn và hay là nút cổ chai).

  • Mở rộng

    Agent dựng hoàn toàn bằng Ansible/Docker → thêm máy trong vài phút. Template pipeline dùng chung cho các biến thể TCU. Chuyển bớt test từ bench sang SIL/vECU để không bị giới hạn bởi số bench.

  • Chống tái phát

    Postmortem ngắn cho sự cố CI lớn, runbook cho lỗi hay gặp, on-call luân phiên trong team, báo cáo KPI hằng tuần.

9. Trước (~2020) → Nay

🔁 Từ "máy build thủ công" → hạ tầng như code, đo được
⏪ Trước (~2020)

Máy build cài tay, mỗi máy khác nhau ("chạy trên máy A mà không chạy trên máy B"). Artifact để trên share drive. Bench chạy script tay, kết quả gửi email. Không có số liệu, CI chậm thì không biết vì sao.

⏩ Nay

Agent dựng bằng Ansible + Docker image có version, co giãn trên cloud. Artifactory với promotion và build info để truy vết. Bench là một node trong CI, có lock, health check, phân loại lỗi hạ tầng. Metric vào time-series DB, dashboard Grafana, alert. Xu hướng tiếp theo: vECU/SIL giảm phụ thuộc bench.

Vì sao quan trọng: "Lead CI operations" nghĩa là chịu trách nhiệm cả độ tin cậy của hệ thống, không chỉ viết pipeline.

10. Tự kiểm tra

Idempotent trong Ansible là gì? Viết task không idempotent thì hậu quả thế nào? Định nghĩa▾

Chạy playbook nhiều lần cho cùng trạng thái cuối, lần sau không đổi gì nếu đã đúng. Module khai báo trạng thái mong muốn nên tự kiểm tra trước khi làm. Task shell: echo x >> file sẽ nối thêm mỗi lần chạy → file hỏng dần, và luôn báo changed nên không phát hiện được drift. Sửa bằng module phù hợp (lineinfile) hoặc creates:/changed_when:.

"Build once, promote many" là gì và vì sao quan trọng cho automotive? Định nghĩa▾

Binary chỉ build một lần; qua mỗi cổng test thì được promote (move/copy) sang repo mức cao hơn trong Artifactory, không build lại. Nếu build lại cho release thì binary ship khác binary đã test (compiler, timestamp, dependency có thể khác) → bằng chứng test không còn giá trị. Build info cho truy vết commit, dependency, môi trường, phục vụ SUP.8 (configuration management) và audit.

CI mất 2 giờ và hay fail ngẫu nhiên. Kế hoạch của bạn? Áp dụng▾

(1) Đo: dashboard thời gian từng stage và tỉ lệ lỗi theo loại. (2) Phân loại lỗi: code / flaky test / hạ tầng. (3) Ổn định trước khi tăng tốc: quarantine flaky test có owner, health check bench, pin version tool, timeout. (4) Tăng tốc chỗ tốn nhất: cache compile, song song hoá, sharding test, chỉ regenerate khi config đổi, tách check nhanh / gate / nightly. (5) Theo dõi KPI hằng tuần để chứng minh cải thiện. Lấy ví dụ thật: kinh nghiệm tự động hoá SENT debugging và giảm effort qua Python script cho thấy cách làm "đo → tự động hoá → chuẩn hoá".

Đào tiếp
  • Làm sao phát hiện flaky test tự động?
  • Nếu quarantine quá nhiều test thì sao?
Bench job fail vì debugger không kết nối. Developer bị chặn merge. Xử lý thế nào? Áp dụng▾

Ngắn hạn: job phải báo INFRA_ERROR (không phải FAIL), tự thử lại trên bench khác nếu có, và đánh dấu bench lỗi offline để job khác không vào. Có alert tới người on-call. Dài hạn: health check trước mỗi job (power cycle, ping debugger), thống kê availability từng bench, runbook khôi phục, cân nhắc relay USB để reset debugger từ xa. Nguyên tắc: lỗi hạ tầng không được đẩy sang developer.

Vì sao không chạy bench test trong Docker container như build? Áp dụng▾

Bench cần truy cập phần cứng: USB debugger, VN interface, serial của PSU, driver nhân (kernel module) của nhà cung cấp, và một số tool chỉ chạy trên Windows. Có thể pass-through thiết bị vào container nhưng phức tạp và dễ vỡ. Thực tế: bench PC được cấu hình bằng Ansible (vẫn là IaC), còn phần Python test có thể đóng gói trong venv có version. Build và static analysis thì container hoá hoàn toàn.

Kinh nghiệm của bạn với hạ tầng CI là gì? Kinh nghiệm▾

Trung thực, bám CV: đã tích hợp build, package và test workflow với Azure Pipelines và Conan, và ở vai trò AI Platform Engineer đang deploy/vận hành hạ tầng trên Azure và GCP bằng Terraform (IaC), Docker, Kubernetes. Chưa dùng AWS, Ansible, Artifactory, Grafana trong dự án; nói rõ Terraform → Ansible và Azure → AWS là cùng tư duy IaC/cloud, và đã tìm hiểu nguyên lý (idempotent, promotion, KPI CI) và sẽ tiếp nhận nhanh vì khái niệm tương đồng. Nhấn mạnh tư duy vận hành: đo trước, phân loại lỗi, tự động hoá.
