✅ 1. OSEK là gì và vì sao "tĩnh"

Nguồn gốc
OSEK (Đức, 1993) + VDX (Pháp) hợp nhất thành chuẩn OSEK/VDX, bản OS cuối cùng là 2.2.3 (2005), sau đó chuẩn hoá thành ISO 17356-3. Bộ chuẩn gồm OS, COM (giao tiếp), NM (network management) và OIL (ngôn ngữ cấu hình). AUTOSAR OS lấy OSEK OS làm nền và mở rộng.
Tĩnh hoàn toàn
Mọi đối tượng (task, resource, alarm, event, ISR) được khai báo lúc cấu hình trong file OIL; generator sinh bảng hằng. Không có tạo task lúc chạy, không cấp phát động. Kết quả: RAM/ROM biết trước, thời gian API xác định, phân tích được thời gian đáp ứng xấu nhất. Đây là lý do nó hợp với ECU chạy trên MCU vài trăm KB RAM.
Ưu tiên cố định
Mỗi task có priority cố định (số lớn = ưu tiên cao trong OSEK). Scheduler luôn chạy task ready có priority cao nhất; cùng priority thì FIFO theo thứ tự kích hoạt.
Stack
Basic task có thể dùng chung stack (vì chúng chạy xong mới nhường, không bao giờ "đợi giữa chừng"), nên tiết kiệm RAM. Extended task cần stack riêng vì có thể dừng ở trạng thái waiting với ngữ cảnh còn trên stack.

✅ 2. Trạng thái task và API chuyển trạng thái

4 trạng thái. Basic task chỉ có 3 trạng thái (không có WAITING). Chú ý: task không thể tự chuyển RUNNING → READY trừ khi bị preempt hoặc gọi Schedule(); và task phải kết thúc bằng TerminateTask() hoặc ChainTask(), return khỏi hàm task là lỗi (hành vi không xác định trong OSEK, AUTOSAR OS bắt lỗi).
APIÝ nghĩaBẫy
ActivateTask(t)SUSPENDED → READY. Nếu t đang chạy và class cho phép multiple activation → xếp hàng thêm.Vượt số activation tối đa → E_OS_LIMIT. Gọi từ task thấp kích hoạt task cao → preempt ngay (full-preemptive).
TerminateTask()Kết thúc task đang chạy.Không được gọi khi đang giữ resource (E_OS_RESOURCE) hoặc trong ISR (E_OS_CALLEVEL). Không return về nơi gọi.
ChainTask(t)Kết thúc task hiện tại và kích hoạt t (nguyên tử).Chain chính mình = kích hoạt lại, dùng để lặp.
Schedule()Điểm nhường tự nguyện: nếu có task ready cao hơn thì nhường.Chỉ có ý nghĩa với non-preemptive task. Giữ resource thì không được gọi.
GetResource / ReleaseResourceVào/ra critical section theo Priority Ceiling.Phải release theo thứ tự LIFO. Không được WaitEvent khi đang giữ.
SetEvent(t, mask)Set event cho extended task t; nếu t đang chờ event đó → READY.Gọi được từ ISR cat2. Event chưa được clear thì vẫn còn set.
WaitEvent(mask)Chờ một trong các event trong mask.Nếu event đã set sẵn → không chờ, chạy tiếp. Chỉ extended task.
ClearEvent(mask)Xoá event của chính task.Quên clear → vòng lặp chạy liên tục không chờ (busy loop).
GetEvent(t, &m)Đọc event hiện tại để biết event nào đánh thức.Mẫu chuẩn: Wait → Get → Clear → xử lý.
 
TASK(ModemTask)                                  /* extended task, ECC1 */
{
    EventMaskType ev;
    for (;;) {
        (void)WaitEvent(EV_RX | EV_TIMEOUT | EV_CMD);
        (void)GetEvent(ModemTask, &ev);
        (void)ClearEvent(ev);                    /* clear đúng các event đã nhận */
        if ((ev & EV_RX) != 0u)      { At_ProcessRx(); }
        if ((ev & EV_TIMEOUT) != 0u) { At_HandleTimeout(); }
        if ((ev & EV_CMD) != 0u)     { At_SendNextQueued(); }
    }
    /* không bao giờ tới: extended task vòng lặp vô hạn là mẫu hợp lệ */
}

TASK(Cyclic10ms)                                 /* basic task, kích bởi alarm */
{
    (void)GetResource(RES_SignalBuf);
    Signal_Update();                             /* dữ liệu chung với task khác */
    (void)ReleaseResource(RES_SignalBuf);
    (void)TerminateTask();                       /* bắt buộc */
}

ISR(Uart0_Rx)                                    /* ISR category 2 */
{
    Uart_RxIsr(UART0_DATA);
    (void)SetEvent(ModemTask, EV_RX);            /* cat2 mới được gọi OS API */
}

✅ 3. Conformance class & chính sách preemption

Extended task không bao giờ có multiple activation, kể cả ở ECC2. ECC1 vẫn cho phép nhiều task cùng priority trong OSEK 2.2.3. Chi tiết số lượng tối thiểu (ví dụ ≥ 8 task, ≥ 8 event/task) nằm trong spec.

Full preemptive
Task ready cao hơn chiếm CPU ngay lập tức. Đáp ứng tốt nhất cho task ưu tiên cao, nhưng dữ liệu chung phải được bảo vệ ở mọi chỗ.
Non-preemptive
Task chạy tới khi terminate, chờ event, hoặc gọi Schedule(). Ít race condition, tốn ít stack hơn, nhưng task dài làm trễ task cao. ISR vẫn ngắt được.
Mixed preemptive
Mỗi task tự khai báo SCHEDULE = FULL | NON. Phổ biến: task dài và ít quan trọng để NON, task thời gian thực để FULL.
Nhóm task bằng internal resource
Gán một internal resource cho nhóm task: task tự động giữ resource khi chạy, nên các task trong nhóm không preempt lẫn nhau, nhưng task ngoài nhóm có priority cao hơn ceiling vẫn preempt được. Đây là cách làm "non-preemptive cục bộ". Non-preemptive task thực chất là task giữ internal resource RES_SCHEDULER.

✅ 4. Priority Ceiling (OSEK PCP)

Vấn đề
Priority inversion: task H chờ resource do L giữ; M (không liên quan) preempt L → H chờ không giới hạn (vụ Mars Pathfinder 1997 là ví dụ kinh điển với VxWorks). Và deadlock khi hai task giữ và chờ chéo resource.
Cơ chế
Mỗi resource có ceiling = priority cao nhất trong các task (và ISR) có dùng nó, tính lúc cấu hình. GetResource nâng priority task lên ceiling ngay lập tức (immediate ceiling, khác với priority inheritance chỉ nâng khi có tranh chấp).
Kết quả
(1) H bị chặn tối đa một critical section, thời gian chặn tính được. (2) Không deadlock: khi task giữ R, không task nào có thể dùng R được chạy, nên không có chờ chéo. (3) Không cần hàng đợi chờ resource: GetResource không bao giờ block.
Resource dùng chung với ISR
Ceiling khi đó cao hơn mọi task, bằng mức ngắt của ISR, nên GetResource thực chất che ngắt đến mức đó. Tính năng này là tuỳ chọn trong OSEK; AUTOSAR OS hỗ trợ cho ISR cat2.
So với mutex của RTOS động
FreeRTOS mutex dùng priority inheritance (chỉ nâng khi task cao đang chờ), có thể block, có thể deadlock nếu lồng sai thứ tự, và không chặn được chuỗi inversion lồng nhau hoàn toàn. Ceiling tĩnh đơn giản hơn nhưng cần biết trước ai dùng resource, điều mà OSEK có sẵn nhờ cấu hình tĩnh.

✅ 5. Counter, Alarm, ISR, Hook

Counter
Bộ đếm tick (thường từ timer phần cứng). Thuộc tính: MAXALLOWEDVALUE (giá trị tối đa trước khi quay vòng), TICKSPERBASE, MINCYCLE (chu kỳ nhỏ nhất cho phép với alarm).
Alarm
Gắn với một counter. Khi hết hạn thực hiện một hành động: ACTIVATETASK, SETEVENT, hoặc ALARMCALLBACK (hàm ngắn, chạy ở mức ISR). API: SetRelAlarm(a, offset, cycle) (tương đối, offset 0 không hợp lệ trong OSEK), SetAbsAlarm(a, start, cycle), CancelAlarm, GetAlarm (còn bao nhiêu tick). cycle = 0 là one-shot. Có thể autostart theo application mode.
Jitter và offset
Nhiều alarm cùng chu kỳ kích hoạt cùng tick làm CPU dồn tải. Đặt offset khác nhau để rải tải. AUTOSAR dùng schedule table để cố định mẫu thời gian và đồng bộ với thời gian toàn cục (xem B5).
ISR category 1
Không gọi OS API (trừ một số API bật/tắt ngắt). Nhanh nhất, overhead nhỏ nhất, nhưng không thể kích hoạt task. Sau khi ISR cat1 kết thúc, OS không reschedule.
ISR category 2
Có khung OS bao quanh, được gọi một tập API (ActivateTask, SetEvent, GetResource…). Khi ISR kết thúc, OS kiểm tra và chuyển sang task ưu tiên cao nhất nếu cần. Không được gọi TerminateTask, WaitEvent, Schedule.
Quy tắc priority
Mọi ISR luôn cao hơn mọi task. ISR cat1 thường được đặt ở mức ngắt cao hơn cat2, vì OS che ngắt cat2 khi vào vùng tới hạn của nó; nếu cat1 thấp hơn thì cat1 cũng bị che.
Tắt ngắt
DisableAllInterrupts/EnableAllInterrupts (không lồng được), SuspendAllInterrupts/ResumeAllInterrupts (lồng được, có đếm), SuspendOSInterrupts/ResumeOSInterrupts (chỉ che cat2). Trong vùng này không được gọi OS API khác.
Hooks
StartupHook (sau khi OS khởi tạo, trước task đầu tiên), ShutdownHook, ErrorHook(StatusType) (mọi API trả lỗi đều gọi vào đây, là chỗ log lỗi tập trung), PreTaskHook/PostTaskHook (đo thời gian chạy task, debug). AUTOSAR thêm ProtectionHook.
Standard vs extended status
Extended status (dùng lúc phát triển): API kiểm tra đầy đủ tham số, trả E_OS_ID, E_OS_STATE, E_OS_CALLEVEL, E_OS_RESOURCE… Standard status (production): ít kiểm tra hơn, nhanh hơn. Cấu hình bằng STATUS = EXTENDED | STANDARD.
Application mode
StartOS(mode) chọn mode (ví dụ normal, diagnostic, flash) → mỗi mode có tập task/alarm autostart khác nhau. OS không trở về từ StartOS.

➕ 6. OIL — file cấu hình

OIL (OSEK Implementation Language, bản 2.5) mô tả mọi đối tượng. Generator của nhà cung cấp OS đọc OIL và sinh ra code C. AUTOSAR thay OIL bằng ARXML (container Os), nhưng khái niệm giữ nguyên, và OIL vẫn gặp trong dự án OSEK thuần.

CPU tcu_mcu {
  OS StdOS { STATUS = EXTENDED; STARTUPHOOK = TRUE; ERRORHOOK = TRUE;
             PRETASKHOOK = FALSE; USERESSCHEDULER = TRUE; };
  APPMODE AppNormal {};

  COUNTER SysCounter { MAXALLOWEDVALUE = 65535; TICKSPERBASE = 1; MINCYCLE = 1; };

  TASK Cyclic10ms { PRIORITY = 10; SCHEDULE = FULL; ACTIVATION = 1;
                    AUTOSTART = FALSE; RESOURCE = RES_SignalBuf; };
  TASK ModemTask  { PRIORITY = 8;  SCHEDULE = FULL; ACTIVATION = 1;
                    AUTOSTART = TRUE { APPMODE = AppNormal; };
                    EVENT = EV_RX; EVENT = EV_TIMEOUT; EVENT = EV_CMD;
                    RESOURCE = RES_SignalBuf; };       /* có event → extended */

  ALARM Alarm10ms { COUNTER = SysCounter;
                    ACTION = ACTIVATETASK { TASK = Cyclic10ms; };
                    AUTOSTART = TRUE { ALARMTIME = 3; CYCLETIME = 10; APPMODE = AppNormal; }; };

  RESOURCE RES_SignalBuf { RESOURCEPROPERTY = STANDARD; };   /* ceiling = 10 (tự tính) */
  EVENT EV_RX { MASK = AUTO; };  EVENT EV_TIMEOUT { MASK = AUTO; };  EVENT EV_CMD { MASK = AUTO; };

  ISR Uart0_Rx { CATEGORY = 2; RESOURCE = RES_SignalBuf; };   /* nếu ISR dùng chung dữ liệu */
};

✅ 8. Bẫy hay gặp (dạng "đoạn code này sai gì?")

OSEK: hành vi không xác định. AUTOSAR OS: phát hiện, gọi ErrorHook với E_OS_MISSINGEND rồi tự terminate. Luôn kết thúc task bằng TerminateTask()/ChainTask().

Trả E_OS_RESOURCE (extended status). Task không kết thúc, priority vẫn ở ceiling → hệ thống chạy sai. Mỗi GetResource phải có ReleaseResource trên mọi đường thoát, kể cả nhánh lỗi.

Không được phép: OS không biết đang ở trong ngắt nên không reschedule, trạng thái kernel có thể hỏng. Cần OS API thì khai báo ISR là cat2.

WaitEvent trả về ngay vì event vẫn set → task quay vòng chiếm CPU, task thấp hơn bị đói. Triệu chứng: CPU load 100%, watchdog reset.

Get A, Get B thì phải Release B trước rồi mới Release A. Sai thứ tự → E_OS_NOFUNC, và priority trả về sai mức.

Task chu kỳ 10 ms chạy lâu hơn 10 ms (overrun) → alarm kích hoạt khi task còn chạy → E_OS_LIMIT, mất một chu kỳ. Là dấu hiệu CPU quá tải hoặc task bị chặn; dùng PreTaskHook/PostTaskHook hoặc trace TRACE32 để đo.

Compiler có thể giữ giá trị trong thanh ghi (thiếu volatile), và đọc/ghi 32-bit trên MCU có thể không nguyên tử (ví dụ biến 64-bit trên core 32-bit) → cần resource hoặc suspend ngắt. Volatile không thay thế được bảo vệ critical section.

9. Trước (~2020) → Nay

🔁 Từ OSEK lõi đơn → AUTOSAR OS multicore + bảo vệ
⏪ Trước (~2020)

Nhiều ECU (kể cả TCU đời cũ) chạy OSEK thuần hoặc AUTOSAR OS SC1 trên một core, cấu hình OIL. Không có bảo vệ bộ nhớ giữa các phần mềm.

⏩ Nay

AUTOSAR OS multicore với spinlock và IOC, SC3/SC4 (MPU, timing protection) cho mixed-ASIL. TCU hiện đại kết hợp MCU (AUTOSAR OS) với SoC chạy Linux/QNX hoặc hypervisor. OSEK thuần vẫn còn trong legacy và là nền để hiểu mọi thứ phía trên.

Vì sao quan trọng: JD ghi OSEK; interviewer có thể đang duy trì codebase OSEK. Nói được cả OSEK thuần và phần AUTOSAR mở rộng là an toàn nhất.

10. Tự kiểm tra

Basic task và extended task khác nhau thế nào? Khi nào chọn cái nào? Định nghĩa▾

Basic: 3 trạng thái, chạy từ đầu đến cuối rồi terminate, không chờ giữa chừng, dùng chung stack được. Extended: thêm trạng thái WAITING qua WaitEvent, cần stack riêng. Chọn basic cho công việc chu kỳ ngắn (đa số task). Chọn extended khi có luồng xử lý phải chờ nhiều loại sự kiện, ví dụ task modem chờ RX/timeout/lệnh mới.

Priority Ceiling chống priority inversion và deadlock thế nào? Định nghĩa▾

Ceiling của resource = priority cao nhất trong các user, tính tĩnh. Get → priority task nhảy lên ceiling ngay. Task trung gian không chen được nên thời gian chặn task cao bị giới hạn ở một critical section. Không deadlock vì khi đã giữ R thì không task nào khác dùng R được chạy, nên không có vòng chờ. Get không bao giờ block.

Đào tiếp
  • Khác priority inheritance ở đâu?
  • Resource dùng chung với ISR thì sao?
ISR category 1 và 2 khác nhau? Vì sao cat1 đặt mức ưu tiên cao hơn? Định nghĩa▾

Cat1 không gọi OS API, không reschedule sau khi xong, overhead thấp nhất. Cat2 có khung OS, gọi được API như SetEvent/ActivateTask, OS reschedule khi kết thúc. Cat1 đặt cao hơn vì OS che các ngắt cat2 trong vùng tới hạn của kernel; nếu cat1 thấp hơn thì cũng bị che và mất lợi thế độ trễ thấp.

Task 10 ms thỉnh thoảng báo E_OS_LIMIT. Điều tra thế nào? Áp dụng▾

E_OS_LIMIT = kích hoạt khi task chưa xong. Nghĩa là task (cộng thời gian bị preempt) vượt 10 ms. Bước: (1) ErrorHook log thời điểm và task. (2) Đo thời gian thực thi bằng PreTaskHook/PostTaskHook hoặc trace TRACE32 (task/ISR timeline). (3) Tìm nguyên nhân: đường code dài bất thường (retry, vòng chờ), ISR bão (ví dụ UART nhận liên tục), task cao hơn chiếm CPU, resource bị giữ lâu. (4) Sửa: tách việc dài sang task thấp hơn, dời offset alarm để rải tải, giới hạn tần suất ISR. Cách làm giống debug timing SENT: đo trước, kết luận sau.

OSEK khác FreeRTOS thế nào? Nếu phải chọn cho TCU? Áp dụng▾

OSEK tĩnh hoàn toàn, PCP không block, không deadlock, phân tích thời gian được, là nền của AUTOSAR OS nên phù hợp với phía MCU cần CAN, chẩn đoán, an toàn. FreeRTOS linh hoạt (tạo task động, queue, semaphore), hệ sinh thái lớn, nhưng không có sẵn stack AUTOSAR và mutex có thể deadlock nếu dùng sai. Với MCU của TCU: AUTOSAR OS/OSEK. FreeRTOS hợp với MCU phụ không AUTOSAR hoặc module IoT.

11. Cheat-sheet 1 trang

Task

  • SUSPENDED · READY · RUNNING · WAITING
  • basic (3 state, chung stack) · extended (event)
  • kết thúc bằng Terminate/ChainTask
  • priority cố định, cùng mức FIFO

Class & sched

  • BCC1/BCC2/ECC1/ECC2
  • extended: không multiple activation
  • FULL · NON · mixed
  • internal resource = nhóm non-preempt

Resource

  • ceiling tĩnh, nâng ngay khi Get
  • không block, không deadlock
  • release LIFO · RES_SCHEDULER

Thời gian & ngắt

  • counter → alarm: task / event / callback
  • SetRelAlarm(offset, cycle), cycle 0 = one-shot
  • ISR cat1 không API · cat2 có API
  • Disable/Suspend/SuspendOS

Lỗi & hook

  • E_OS_LIMIT · RESOURCE · CALLEVEL · STATE · ID
  • ErrorHook · Pre/PostTaskHook · Startup/Shutdown
  • EXTENDED (dev) · STANDARD (prod)
  • OIL 2.5 → ARXML trong AUTOSAR

12. Nguồn tham khảo

  • OSEK/VDX Operating System Specification 2.2.3 (2005); OSEK/VDX OIL 2.5; ISO 17356-3.
  • AUTOSAR — Specification of Operating System (SWS OS), Classic Platform.
  • FreeRTOS documentation — mutexes and priority inheritance; Zephyr kernel docs.
  • Bài nội bộ: B5 — AUTOSAR OS (schedule table, protection, multicore).
