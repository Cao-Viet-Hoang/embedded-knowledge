✅ 1. Linux troubleshooting trên target

Câu hỏi hay gặp: "Service trên target không chạy / chết sau vài giây. Bạn làm gì?". Người phỏng vấn không cần bạn thuộc hết lệnh. Họ muốn thấy bạn đi có thứ tự, từ ngoài vào trong, và thu hẹp vùng nghi ngờ bằng bằng chứng.

Đi từ ngoài vào trong. Bốn bước đầu chỉ tốn vài phút nhưng loại được phần lớn nguyên nhân (thiếu file cấu hình, sai quyền, port bị chiếm, hết bộ nhớ). Chỉ khi đó mới cần gdb.
Trình tự boot
Boot ROM → bootloader (U-Boot trên R-Car/RPi, hoặc firmware của RPi) → kernel + device tree → init (thường là systemd, PID 1) → các service theo dependency. Service không lên có thể do chính nó, hoặc do một service/mount/network mà nó phụ thuộc chưa sẵn sàng.
systemd
Quản lý service qua unit file. systemctl status/start/stop/restart/enable, systemctl --failed liệt kê unit lỗi, systemctl list-dependencies xem phụ thuộc, systemd-analyze blame xem service nào làm boot chậm.
journald
Log tập trung. journalctl -u app.service -b (log của service trong lần boot này), -f theo dõi trực tiếp, -p err lọc theo mức, -b -1 lần boot trước (cần journal persistent), --since "10 min ago".
Kernel log
dmesg -T hoặc journalctl -k: driver probe fail, "Out of memory: Killed process", segfault kèm địa chỉ, lỗi CAN/Ethernet link. Service bị kill không để lại log của chính nó thì thường phải nhìn ở đây.
Process & signal
ps aux, top/htop, /proc/<pid>/status, lsof -p (file/socket đang mở). SIGTERM (15) xin dừng lịch sự, SIGKILL (9) không bắt được, SIGSEGV (11) truy cập bộ nhớ sai, SIGABRT (6) do abort()/assert. Exit code 128+N nghĩa là chết bởi signal N (137 = SIGKILL, thường do OOM).
Mạng
ip addr, ip route, ss -tulpn (port nào đang listen, bởi process nào), ping, tcpdump -i eth0 port 30490 (bắt gói, ví dụ SOME/IP-SD). Mở file pcap bằng Wireshark trên máy host.
Remote debug
ssh/scp vào target; trên target gdbserver :2345 ./app, trên host gdb-multiarch app rồi target remote <ip>:2345 với binary có symbol. strace -f -p <pid> xem system call (file không mở được, connect bị từ chối).
Core dump
Bật bằng ulimit -c unlimited hoặc systemd-coredump (coredumpctl list, coredumpctl gdb). Mở core bằng gdb với đúng binary và symbol để xem backtrace tại thời điểm crash.
# Service "app" chết sau vài giây. Đi theo thứ tự:
systemctl status app.service          # Active: failed? exit code? số lần restart?
journalctl -u app.service -b --no-pager | tail -50
dmesg -T | tail -30                   # OOM killer? segfault at ...?
free -h; df -h                        # hết RAM / đầy phân vùng log
ss -tulpn | grep 8080                 # port đã bị process khác chiếm?
# Tái hiện bằng tay với đúng user và biến môi trường của unit
systemctl cat app.service             # xem ExecStart, User, Environment
sudo -u appuser env $(cat /etc/app.env | xargs) /usr/bin/app --config /etc/app.conf
strace -f -e trace=openat,connect /usr/bin/app 2>&1 | grep -E "ENOENT|EACCES|ECONNREFUSED"

✅ 1.1 Unit file systemd: đọc được và sửa được

# /etc/systemd/system/app.service
[Unit]
Description=Telematics app
After=network-online.target someip-daemon.service   # chỉ là THỨ TỰ
Wants=network-online.target                          # kéo theo, không bắt buộc
Requires=someip-daemon.service                       # phụ thuộc cứng: cái kia fail thì cái này dừng

[Service]
Type=simple
User=appuser
EnvironmentFile=/etc/app.env
ExecStart=/usr/bin/app --config /etc/app.conf
Restart=on-failure
RestartSec=2
WatchdogSec=5          # app phải gọi sd_notify("WATCHDOG=1") định kỳ

[Install]
WantedBy=multi-user.target
⚠️

Bẫy hay hỏi: After= chỉ quy định thứ tự, không kéo service kia lên. Requires=/Wants= mới kéo lên. Service chạy tay thì được nhưng chạy qua systemd thì fail: gần như luôn do khác user, biến môi trường, thư mục làm việc hoặc chạy quá sớm khi mạng/phụ thuộc chưa sẵn sàng. Sau khi sửa unit file phải chạy systemctl daemon-reload.

✅ 2. Git hằng ngày của người tích hợp

CV có Git và công cụ Pullogic (review pull request, tích hợp Jira, được giải thưởng nội bộ). Người phỏng vấn CI lead sẽ hỏi nhanh: merge hay rebase, đưa bản sửa sang release branch thế nào, xử lý conflict ra sao.

Fix vào main trước, rồi cherry-pick xuống release. Làm ngược lại (sửa trên release rồi quên đưa lên main) là nguồn gốc kinh điển của lỗi "đã sửa rồi lại xuất hiện" ở bản sau.

Conflict khi tích hợp
Người hiểu code nhất (tác giả change) giải quyết, không phải người tích hợp đoán. Sau khi giải quyết phải build và chạy lại test. Với file generated (code sinh từ tresos/RTA-CAR, ARXML sinh tự động) thì không sửa tay phần conflict mà sinh lại từ cấu hình đã merge.
Tag
Dùng annotated tag (git tag -a) cho baseline/release: có người tạo, ngày, thông điệp. Tag release không bao giờ bị di chuyển.
Commit message
Có ID ticket (Jira) để truy vết requirement/defect ↔ commit (nối với ASPICE SUP.8/9/10 ở LX7). Hook hoặc CI có thể từ chối commit thiếu ID.

🎯 2.1 git bisect và chiến lược release branch

Tình huống: baseline tuần trước pass, baseline hôm nay fail test bench, giữa hai bản có 200 commit. git bisect tìm kiếm nhị phân: khoảng 8 lần build/test (log₂200 ≈ 7,6) là ra commit gây lỗi.

git bisect start
git bisect bad  HEAD                 # bản hôm nay: fail
git bisect good TCU_SW_R2.3.0        # baseline tuần trước: pass
git bisect run ./ci/build_and_smoke.sh
#   exit 0      -> good
#   exit 1..127 -> bad   (trừ 125)
#   exit 125    -> skip  (commit không build được, bỏ qua)
git bisect log > bisect.txt          # bằng chứng cho ticket
git bisect reset

# Đưa fix xuống release branch
git switch release/2.3
git cherry-pick -x 4f2a9c1
git log --oneline release/2.3..main  # cái gì có ở main mà release chưa có

  • Trunk-based + gating

    Mọi người đẩy change nhỏ vào main qua review và gate (test chạy trước khi merge). Main luôn build được.

  • Cắt release branch

    Khi chốt phạm vi một bản giao khách hàng: tạo release/X.Y, từ đây chỉ nhận bug fix có ticket và được duyệt.

  • Tag mỗi bản giao

    R2.3.0, R2.3.1… kèm artifact bất biến và release note.

  • Bảo trì

    Fix vào main trước, cherry-pick -x xuống các release còn hỗ trợ; báo cáo định kỳ những fix còn thiếu trên từng branch.

🎯 3. Bootloader và flash ECU qua UDS

CV có "UDS diagnostic services" và module Diag. Bài B4 đã liệt kê service 0x34/36/37. Mục này ghép chúng thành trình tự flash hoàn chỉnh, câu hỏi rất hay gặp với TCU.

Bố cục bộ nhớ
Flash chia thành: vùng bootloader (không bị ghi đè khi cập nhật, thường được bảo vệ), vùng ứng dụng, vùng dữ liệu (NvM/EEPROM emulation). Một số ECU có thêm vùng dự phòng (A/B hoặc dual bank).
Quyết định lúc reset
Bootloader chạy trước. (1) Có cờ yêu cầu lập trình không (ứng dụng ghi vào RAM không khởi tạo hoặc NvM khi nhận 0x10 02)? Có thì ở lại bootloader. (2) Ứng dụng có hợp lệ không (cờ valid, CRC, chữ ký)? Hợp lệ thì đặt lại vector table và stack rồi nhảy vào ứng dụng; không thì ở lại bootloader chờ flash.
Vì sao an toàn khi mất điện
Cờ "ứng dụng hợp lệ" chỉ được ghi sau cùng, khi đã tải xong và kiểm tra CRC/chữ ký thành công. Mất điện giữa chừng thì lần khởi động sau bootloader thấy ứng dụng không hợp lệ và ở lại chờ flash lại. ECU không bị "brick".
Security Access 0x27
Sub-function lẻ xin seed, chẵn gửi key (27 01 → seed, 27 02 + key). NRC hay gặp: 0x35 invalidKey, 0x36 exceededNumberOfAttempts, 0x37 requiredTimeDelayNotExpired. Thuật toán seed-key do OEM quy định; xe mới có xu hướng dùng xác thực dựa trên chứng chỉ (0x29 Authentication).
0x34 / 0x36 / 0x37
34 RequestDownload: địa chỉ, kích thước, định dạng; phản hồi cho biết maxNumberOfBlockLength. 36 TransferData: từng block, block sequence counter bắt đầu 0x01, tăng dần và quay vòng 0xFF → 0x00; lặp lại block cũ (do mất phản hồi) thì ECU không ghi lại. 37 RequestTransferExit kết thúc.
Thời gian
Xoá flash lâu nên ECU trả NRC 0x78 (responsePending) rồi mới trả kết quả; tester chuyển sang chờ theo P2*server (thường 5 s) thay vì P2 (thường 50 ms). Giữ session bằng TesterPresent 3E 80 để S3 (khoảng 5 s) không hết hạn.

🎯 3.1 Trình tự flash điển hình (3 pha)

Khung này theo cách làm phổ biến trong ngành; chi tiết (routine ID kiểm điều kiện, DID fingerprint, cách kiểm chữ ký) do spec của OEM quy định. RoutineControl 0xFF00 (eraseMemory) và 0xFF01 (checkProgrammingDependencies) là routine ID được ISO 14229-1 định nghĩa sẵn.
🔑

Ba ý người phỏng vấn muốn nghe: (1) chia 3 pha, và vì sao tắt DTC/communication trước khi flash; (2) cơ chế an toàn: security access, kiểm CRC/chữ ký, cờ valid ghi sau cùng nên mất điện không làm hỏng ECU; (3) với CI: flash bench tự động bằng script (Python + thư viện UDS, hoặc TRACE32 cho lần đầu khi chưa có bootloader), đọc lại version bằng 0x22 để xác nhận đúng bản.

➕ 3.2 OTA và vai trò của TCU

TCU trong OTA
TCU có kết nối di động nên thường là OTA client / update master: tải gói cập nhật từ backend, kiểm chữ ký, rồi (a) tự cập nhật chính nó, và (b) đóng vai tester flash các ECU khác qua CAN hoặc DoIP bằng đúng trình tự UDS ở trên.
A/B (dual bank)
Có 2 bản phần mềm: chạy bản A trong khi ghi bản B ở nền; reboot sang B; nếu B không khởi động được hoặc không báo "healthy" thì tự quay về A (rollback). Trên Linux thường dùng A/B rootfs với các framework như SWUpdate, RAUC, Mender. Trên MCU dùng flash dual bank.
Quy định
UN R156 (Software Update Management System) và UN R155 (Cyber Security Management System): bắt buộc với loại xe mới từ 07/2022 và mọi xe mới từ 07/2024 tại các nước áp dụng quy định UNECE (EU, Nhật, Hàn…). ISO 24089 (2023) về kỹ thuật cập nhật phần mềm; ISO/SAE 21434 về cybersecurity.
Bảo mật
Gói cập nhật được ký; ECU kiểm chữ ký bằng khoá công khai lưu trong HSM/secure storage; chống hạ cấp (anti-rollback) bằng số version đơn điệu. Uptane là một framework mở phổ biến cho bảo mật OTA ô tô.

4. Trước (~2020) → Nay

🔁 Flash ở xưởng, log qua serial → OTA có quy định, log và debug từ xa
⏪ Trước (~2020)

Cập nhật phần mềm chủ yếu ở xưởng qua cổng OBD với tester. ECU một bank, mất điện giữa chừng thì phải flash lại. Nhiều target Linux vẫn dùng init script, debug bằng console serial. Tìm commit gây lỗi thường bằng cách hỏi quanh team.

⏩ Nay

OTA qua TCU là chuẩn, có UN R155/R156 và ISO 24089 bắt buộc quy trình. A/B và rollback phổ biến; xác thực bằng chứng chỉ (0x29) bên cạnh seed-key. systemd/journald là mặc định trên Embedded Linux. CI tự động bisect khi baseline đỏ và gắn kết quả vào ticket.

Vì sao quan trọng: người tích hợp TCU không chỉ build ra binary mà còn phải chứng minh binary đó flash an toàn, truy vết được và cập nhật được từ xa.

5. Tự kiểm tra

Linux và QNX khác nhau cơ bản ở đâu? Định nghĩa▾

Linux là kernel nguyên khối, driver chạy trong kernel. QNX là microkernel: kernel chỉ lo scheduling, IPC, interrupt, timer; driver, file system, network là process ở user space (resource manager), giao tiếp bằng message passing. Nhờ vậy QNX cô lập lỗi tốt hơn (driver chết có thể khởi động lại), là hard real-time và có bản chứng nhận an toàn. Công cụ: pidin, slog2info, pdebug thay cho ps, journalctl, gdbserver.

Đào tiếp
  • Vì sao TCU/cluster hay chọn QNX cho phần an toàn và Linux cho phần infotainment/kết nối?
Merge và rebase khác nhau thế nào? Khi nào không được rebase? Định nghĩa▾

Merge giữ nguyên lịch sử và tạo merge commit. Rebase viết lại commit của bạn lên đỉnh nhánh đích nên lịch sử thẳng nhưng hash đổi. Không rebase nhánh đã chia sẻ (main, release, nhánh người khác đang dựa vào) vì sẽ làm lệch lịch sử của mọi người. Rút change khỏi nhánh chung thì dùng revert, không reset + force push.

Service trên target Linux chạy tay thì được, chạy qua systemd thì chết sau 2 giây. Bạn làm gì? Áp dụng▾

systemctl status xem exit code/signal và số lần restart; journalctl -u … -b xem log; dmesg xem có OOM/segfault không. Sau đó so khác biệt giữa hai cách chạy: systemctl cat xem User, EnvironmentFile, WorkingDirectory, ExecStart. Nguyên nhân hay gặp: khác user nên không có quyền file/device, thiếu biến môi trường, đường dẫn tương đối, chạy trước khi mạng hoặc daemon phụ thuộc sẵn sàng (chỉ có After= mà thiếu Wants/Requires=), hoặc WatchdogSec mà app không gửi sd_notify. Tái hiện bằng tay với đúng user và env, dùng strace nếu cần.

Đào tiếp
  • Exit code 137 nghĩa là gì?
  • Log không có gì cả thì tìm ở đâu tiếp?
Baseline tuần trước pass, hôm nay fail, giữa hai bản 200 commit. Tìm thủ phạm thế nào? Áp dụng▾

Trước hết loại trừ hạ tầng: chạy lại baseline cũ trên cùng bench, nếu nó cũng fail thì lỗi ở bench/môi trường, không phải code. Nếu baseline cũ vẫn pass thì git bisect giữa tag cũ và HEAD, tự động bằng bisect run với script build + flash + smoke test (exit 125 để bỏ qua commit không build được); khoảng 8 vòng là ra. Với lỗi chập chờn, script phải chạy lặp nhiều lần mới kết luận good. Có commit thì revert trên main để gate xanh lại, mở ticket kèm bisect log cho tác giả.

Kể trình tự flash một ECU qua UDS. Mất điện giữa lúc flash thì sao? Áp dụng▾

Pre: 10 03, kiểm điều kiện bằng 31, tắt DTC (85 02) và communication (28). Programming: 10 02 vào bootloader, 27 security access, ghi fingerprint, 31 FF00 erase, 34/36/37 tải dữ liệu, 31 kiểm CRC/chữ ký, 31 FF01 check dependencies, 11 01 reset. Post: bật lại communication và DTC, xoá DTC, về default session, đọc version bằng 22. Mất điện: cờ "ứng dụng hợp lệ" chỉ ghi sau khi kiểm tra thành công, nên lần khởi động sau bootloader thấy ứng dụng không hợp lệ, ở lại bootloader và chờ flash lại. Với A/B thì ECU vẫn chạy bản cũ.

  • Block sequence counter dùng để làm gì?
