🎯 1. Bức tranh tổng: từ git push đến merge

Hai cửa. Check chạy mỗi patchset mới để cho reviewer biết change có build/test được không. Gate chỉ chạy khi change đã được duyệt, test nó trên nền các change đang xếp hàng trước, và chính Zuul là người bấm merge. Không ai merge tay được, nên nhánh chính luôn ở trạng thái đã test.
🔑

Ý tưởng cốt lõi để nói với interviewer: CI thông thường test change trước khi merge nhưng trên nền main tại thời điểm tạo nhánh. Nếu hai change cùng xanh riêng lẻ nhưng xung đột ngữ nghĩa, merge cả hai thì main đỏ. Gating giải quyết bằng cách test đúng trạng thái main sẽ có sau khi merge, theo thứ tự merge.

➕ 2. Gerrit — code review theo từng commit

Vai trò: server Git + hệ thống review. Khác GitHub/GitLab (review theo nhánh/merge request), Gerrit review từng commit. Một commit là một đơn vị review.

Change & Change-Id
Mỗi commit đẩy lên review tạo một change. Git hook commit-msg tự thêm dòng footer Change-Id: I<40 hex>. Gerrit dùng Change-Id (không dùng SHA) để nhận ra "đây là bản sửa của cùng một change", vì SHA đổi mỗi lần amend.
Patchset
Sửa theo review: git commit --amend (giữ nguyên Change-Id) rồi push lại → change có thêm patchset mới (PS1, PS2…). Reviewer so sánh diff giữa hai patchset. Đây là lý do developer quen Gerrit không tạo commit "fix review" mà amend.
Push để review
git push origin HEAD:refs/for/main. refs/for/ là namespace ảo: Gerrit nhận commit vào hàng chờ review thay vì cập nhật nhánh main. Có thể kèm option như %topic=x, %r=reviewer@…, %wip.
Relation chain
Đẩy nhiều commit nối tiếp nhau → mỗi commit là một change, xếp thành chuỗi phụ thuộc. Change con không merge được nếu change cha chưa merge.
Label Code-Review
Mặc định từ −2 tới +2. +1 = "trông ổn nhưng cần người khác duyệt", +2 = approve (chỉ người có quyền), −1 = "nên sửa", −2 = chặn (veto; change không submit được cho tới khi chính người đó gỡ).
Label Verified
Từ −1 tới +1, thường do CI bot vote (Zuul hoặc Jenkins Gerrit Trigger). Verified +1 = build/test pass.
Submit requirements
Điều kiện để nút Submit hoạt động, ví dụ "có Code-Review +2, không có −2, Verified +1". Từ Gerrit 3.6 cấu hình bằng submit requirements (thay cho Prolog submit rules cũ). Nhiều dự án thêm label riêng (ví dụ Workflow +1 ở OpenStack) làm tín hiệu "đưa vào gate".
Submit type
Cách Gerrit ghép change vào nhánh: Merge if necessary, Fast-forward only, Rebase if necessary, Rebase always, Cherry pick, Merge always. Dự án muốn lịch sử thẳng thường chọn rebase/cherry-pick.
Stream events
Gerrit phát sự kiện (patchset-created, comment-added, change-merged, ref-updated) qua SSH gerrit stream-events hoặc plugin (webhook, Kafka). Zuul và Jenkins lắng nghe các sự kiện này để kích hoạt pipeline.
Quyền (ACL)
Cấu hình theo project/nhánh trong refs/meta/config (project.config): ai được push, ai được vote +2, ai được submit. Integration lead thường giữ quyền cấu hình ACL cho nhánh release.
# Quy trình developer trên Gerrit
git clone ssh://user@gerrit:29418/tcu/app && cd app
scp -p -P 29418 user@gerrit:hooks/commit-msg .git/hooks/   # cài hook sinh Change-Id
git commit -m "CanIf: fix Rx indication for extended ID"   # footer Change-Id được thêm tự động
git push origin HEAD:refs/for/main%topic=canif-extid         # tạo change, PS1
# ... reviewer góp ý ...
git commit --amend                                           # giữ Change-Id
git push origin HEAD:refs/for/main                           # PS2 của cùng change

➕ 3. Zuul — project gating

Vai trò: hệ thống CI mã nguồn mở (xuất phát từ OpenStack) chuyên gating: đảm bảo không change nào được merge nếu chưa test trên đúng trạng thái sau merge. Automotive dùng nhiều: Volvo Cars dựng ECM CI chain trên Zuul (2018), BMW có instance CI/CD tập trung dựa trên Zuul v3 (theo danh sách user của Zuul).

3.1 Kiến trúc

zuul-scheduler
Não của hệ thống: nhận event từ Gerrit/GitLab/GitHub, quyết định change vào pipeline nào, job nào chạy, và report kết quả. Trạng thái được lưu trong ZooKeeper nên có thể chạy nhiều scheduler (HA).
zuul-merger
Chuẩn bị trạng thái Git dự kiến: ghép change đang test lên nhánh đích cùng các change phía trước trong queue. Nếu ghép lỗi (merge conflict) thì báo ngay, không cần chạy job.
zuul-executor
Chạy job. Job trong Zuul là Ansible playbook (pre-run / run / post-run) chạy trên node được cấp. Đây là lý do JD ghi Ansible cạnh Zuul.
Nodepool / launcher
Cấp node (VM cloud, container, hoặc máy tĩnh như máy nối bench) cho job, dọn sau khi xong. Các bản Zuul mới đang tích hợp chức năng này vào Zuul (zuul-launcher), nhưng khái niệm vẫn là "pool node theo label".
zuul-web
API + dashboard: xem pipeline trực tiếp (status page), lịch sử build, log, cấu hình job. "Zuul Web" trong JD chính là thành phần này.

3.2 Pipeline và các loại manager

Independent (check)
Mỗi change được test độc lập trên nhánh đích hiện tại. Không có thứ tự, không ảnh hưởng nhau. Trigger thường là patchset-created. Report: vote Verified ±1. Mục đích: cho reviewer biết sớm.
Dependent (gate)
Các change được xếp vào shared queue theo thứ tự được duyệt, test speculatively (mục 3.3). Trigger thường là khi đủ approval (ví dụ Code-Review +2 cộng label approve). Report thành công: Zuul submit change.
Post / periodic
post: chạy sau khi merge (ref-updated), ví dụ publish artifact lên Artifactory, build docs. periodic: theo lịch (timer), ví dụ full regression hằng đêm trên bench, long-run test.
Serial / supercedent
serial: chạy từng item một (hữu ích cho deploy). supercedent: chỉ giữ item mới nhất cho mỗi nhánh, bỏ item cũ đang chờ (ví dụ build tài liệu).

3.3 Speculative execution — trái tim của gate

Speculative execution. Zuul giả định các change phía trước sẽ pass nên test tất cả cùng lúc, mỗi change trên nền "main + mọi change phía trước". Nếu một change fail, những change phía sau bị test lại mà không có nó. Kết quả: vừa nhanh như chạy song song, vừa đúng như chạy tuần tự.
Vì sao không chạy tuần tự?
Nếu mỗi gate run mất 1 giờ, tuần tự chỉ merge được khoảng 24 change/ngày. Với song song speculative, thông lượng gần bằng số change được duyệt, miễn tỉ lệ fail thấp.
Chi phí khi fail
Mỗi change fail làm các change phía sau phải chạy lại. Vì vậy flaky test là kẻ thù số 1 của gate: một test chập chờn làm hỏng cả queue. Đây là câu hỏi hay gặp cho integration lead.
Window
Zuul giới hạn số change được test đồng thời trong một queue (window) và điều chỉnh động: tăng khi liên tục pass, giảm khi có fail. Mục đích là không lãng phí tài nguyên khi queue đang "xấu".
Shared queue
Nhiều repo có thể dùng chung một queue (ví dụ repo app + repo BSW config + repo tool). Change trong các repo đó được xếp chung thứ tự, nên thay đổi liên repo cũng được gate đúng.

3.4 Depends-On — thay đổi xuyên nhiều repo

Cú pháp
Thêm vào footer commit message: Depends-On: <URL của change> (các bản cũ dùng Change-Id đầy đủ). Có thể có nhiều dòng Depends-On, và có thể trỏ sang hệ thống khác (ví dụ change Gerrit phụ thuộc merge request GitLab).
Hành vi
Nếu A phụ thuộc B: trong gate, B được xếp trước A. Nếu B fail thì cả B và A bị loại khỏi queue. A không thể merge trước B. Trong check, Zuul test A trên nền có sẵn B (chưa merge).
Ví dụ automotive
Thay đổi signal trong ARXML (repo config) cần sửa code SWC (repo app) cùng lúc. Change app ghi Depends-On change config → cả hai được test chung, merge đúng thứ tự, không có khoảnh khắc main bị lệch.
Điều kiện
Để hai change được enqueue cùng nhau trong gate, hai repo phải cùng shared queue. Nếu không, change đầu phải merge xong thì change sau mới vào queue.

3.5 Cấu hình: tất cả là YAML trong repo

Config project vs untrusted project
Config project (được tin cậy) định nghĩa pipeline, connection, secret, base job; thay đổi chỉ có hiệu lực sau khi merge. Untrusted project (repo thường) tự khai báo job trong .zuul.yaml hoặc thư mục zuul.d/.
Speculative config
Sửa .zuul.yaml trong một change thì chính change đó chạy với cấu hình mới. Developer thử job mới mà không cần quyền admin CI, và job hỏng không ảnh hưởng người khác vì chưa merge.
Job inheritance
Job kế thừa parent (ví dụ base lo checkout và thu log), có nodeset (node label), vars, timeout, required-projects, và dependencies giữa các job (job B chỉ chạy sau khi job A pass).
# zuul.d/pipelines.yaml (config project)
- pipeline:
    name: check
    manager: independent
    trigger:
      gerrit:
        - event: patchset-created
        - event: comment-added
          comment: (?i)^recheck$
    success:
      gerrit: { Verified: 1 }
    failure:
      gerrit: { Verified: -1 }

- pipeline:
    name: gate
    manager: dependent
    require:
      gerrit:
        approval:
          - Code-Review: 2
    trigger:
      gerrit:
        - event: comment-added
          approval:
            - Code-Review: 2
    success:
      gerrit: { Verified: 2, submit: true }
    failure:
      gerrit: { Verified: -2 }

# .zuul.yaml (trong repo tcu/app)
- job:
    name: tcu-build-rh850
    parent: base
    nodeset: { nodes: [ { name: builder, label: docker-ghs } ] }
    run: playbooks/build.yaml
    timeout: 3600

- job:
    name: tcu-bench-smoke
    nodeset: { nodes: [ { name: bench, label: hil-bench-tcu } ] }
    run: playbooks/flash_and_smoke.yaml
    dependencies: [ tcu-build-rh850 ]

- project:
    check: { jobs: [ tcu-build-rh850, tcu-misra, tcu-unit ] }
    gate:  { jobs: [ tcu-build-rh850, tcu-misra, tcu-unit, tcu-bench-smoke ] }

Tên label Verified: 2 và điều kiện approval ở trên chỉ là ví dụ; mỗi Gerrit instance cấu hình phạm vi label khác nhau.

➕ 4. Jenkins — Jenkinsfile declarative

Controller / agent
Controller giữ cấu hình, lịch sử, UI, và phân việc. Agent (node) thực sự chạy build, được gắn label (ví dụ windows-ghs, bench-tcu-01). Không nên build trên controller (bảo mật và tải).
Pipeline as code
Jenkinsfile nằm trong repo, dạng declarative (pipeline { agent; stages; post }) hoặc scripted (Groovy tự do). Multibranch pipeline tự tạo job cho mỗi nhánh/change.
Shared library
Logic dùng chung (flash ECU, parse report MISRA, upload Artifactory) đặt trong repo riêng, nạp bằng @Library('tcu-ci') _. Là cách chuẩn hoá pipeline cho nhiều repo. Tương đương template trong Azure Pipelines.
Gerrit Trigger plugin
Nghe stream-events của Gerrit, chạy job khi có patchset, vote Verified. Là phương án khi không có Zuul. Khi có Zuul, Jenkins thường được Zuul gọi hoặc chỉ làm job dài hạn (nightly, release).
Lockable Resources
lock('bench-tcu'): chỉ một build dùng bench tại một thời điểm. Quan trọng với HIL bench, vốn là tài nguyên khan hiếm và có trạng thái (xem LX2).
Kết quả
junit (đọc report JUnit XML từ pytest/VectorCAST), archiveArtifacts, stash/unstash (chuyển file giữa các stage chạy trên agent khác nhau), recordIssues (Warnings NG, hiển thị finding static analysis).
@Library('tcu-ci') _
pipeline {
  agent none
  options { timeout(time: 90, unit: 'MINUTES'); timestamps() }
  stages {
    stage('Build') {
      agent { docker { image 'artifactory.local/tcu/build-ghs:2026.2'; label 'linux' } }
      steps {
        sh 'python tools/generate.py --tresos-project cfg/'   // BSW/RTE generation
        sh 'cmake --preset rh850 && cmake --build --preset rh850 -j8'
        stash name: 'elf', includes: 'build/**/*.elf,build/**/*.map'
      }
    }
    stage('Quality') {
      parallel {
        stage('MISRA')  { agent { label 'linux' } steps { sh 'tools/run_qac.sh' } }
        stage('Unit')   { agent { label 'vcast' } steps { sh 'tools/run_vcast.sh'; junit 'reports/vcast/*.xml' } }
      }
    }
    stage('Bench smoke') {
      agent { label 'bench-tcu' }
      steps {
        lock('bench-tcu-01') {
          unstash 'elf'
          sh 't32 -s flash.cmm build/tcu.elf'                  // TRACE32 flash qua PRACTICE script
          sh 'pytest tests/bench -m smoke --junitxml=reports/bench.xml'
        }
      }
      post { always { junit 'reports/bench.xml' } }
    }
  }
  post { failure { notifyOwners() } }                          // hàm trong shared library
}

➕ 5. GitLab CI — .gitlab-ci.yml

Stages & jobs
Job cùng stage chạy song song, stage sau chờ stage trước xong. Dùng needs: để tạo DAG: job chạy ngay khi job nó cần xong, không chờ cả stage.
Runner & tags
Runner (shell, docker, kubernetes executor) nhận job có tags khớp. Máy nối bench là một runner shell có tag bench.
rules
Quyết định job có chạy không: theo nhánh, loại pipeline (merge_request_event), file thay đổi (changes:). Tránh chạy bench test cho change chỉ sửa tài liệu.
artifacts vs cache
artifacts: output của job (ELF, report) được truyền sang job sau và lưu để tải về. cache: tăng tốc (thư mục pip, ccache), không đảm bảo có mặt. Nhầm hai cái này là lỗi phổ biến.
resource_group
Chỉ một job trong group chạy tại một thời điểm, tương đương lock của Jenkins. Dùng cho bench.
include / extends
Tái sử dụng template giữa các repo, tương đương shared library và template của Azure.
Merge trains
Tính năng của GitLab gần giống gate của Zuul: xếp các MR thành đoàn, mỗi MR được test trên nền main + các MR phía trước. Nhắc tới để thể hiện bạn hiểu gating không phải khái niệm riêng của Zuul.
stages: [build, quality, bench]

build:rh850:
  stage: build
  image: artifactory.local/tcu/build-ghs:2026.2
  script:
    - cmake --preset rh850 && cmake --build --preset rh850 -j8
  artifacts: { paths: [build/tcu.elf, build/tcu.map], expire_in: 1 week }
  cache: { key: ccache-rh850, paths: [.ccache/] }

misra:
  stage: quality
  needs: [build:rh850]
  script: [tools/run_qac.sh]
  artifacts: { reports: { codequality: reports/qac.json } }

bench:smoke:
  stage: bench
  needs: [build:rh850]
  tags: [bench-tcu]
  resource_group: bench-tcu-01
  rules:
    - changes: [src/**/*, cfg/**/*]
  script:
    - t32 -s flash.cmm build/tcu.elf
    - pytest tests/bench -m smoke --junitxml=bench.xml
  artifacts: { reports: { junit: bench.xml } }

7. Trước (~2020) → Nay

🔁 Từ "Jenkins job bấm tay + nightly" → gating as code
⏪ Trước (~2020)

Jenkins job cấu hình qua UI (freestyle), không version control. CI chủ yếu build đêm; developer merge xong mới biết gãy. Gerrit Trigger vote Verified nhưng test trên nền cũ, nên main vẫn đỏ khi hai change xung đột.

⏩ Nay

Pipeline là code trong repo (Jenkinsfile, .gitlab-ci.yml, .zuul.yaml), review như code thường. Gating (Zuul gate, GitLab merge train) test đúng trạng thái sau merge. Thay đổi liên repo dùng Depends-On. Agent chạy trong container dựng từ image có version, hạ tầng dựng bằng Ansible.

Vì sao quan trọng: interviewer của một dự án dùng Zuul muốn nghe bạn hiểu vì sao họ chọn gating, chứ không chỉ biết viết một pipeline YAML.

8. Tự kiểm tra

Patchset và Change-Id trong Gerrit là gì? Vì sao Gerrit không dùng SHA? Định nghĩa▾

Một commit đẩy lên refs/for/<branch> tạo một change. Mỗi lần amend và push lại tạo một patchset mới của cùng change. Gerrit nhận ra hai lần push là cùng change nhờ footer Change-Id (do hook commit-msg sinh ra), vì SHA thay đổi mỗi lần amend. Nhờ vậy review diễn ra trên từng commit sạch, không có commit "fix review".

Đào tiếp
  • Code-Review −2 khác −1 thế nào?
  • Relation chain là gì?
Check pipeline và gate pipeline trong Zuul khác nhau thế nào? Định nghĩa▾

Check dùng manager independent: test mỗi patchset riêng lẻ trên nhánh hiện tại, report Verified cho reviewer. Gate dùng manager dependent: chỉ nhận change đã được duyệt, xếp vào queue theo thứ tự, test mỗi change trên nền main cộng các change phía trước (speculative), và khi pass thì Zuul tự merge. Check trả lời "change này có ổn không", gate đảm bảo "main sau khi merge vẫn ổn".

Đào tiếp
  • Vì sao phải chạy lại ở gate khi đã pass check?
  • Post pipeline dùng để làm gì?
Giải thích speculative execution. Chuyện gì xảy ra khi change giữa queue fail? Áp dụng▾

Queue A → B → C. Zuul lạc quan giả định A và B sẽ pass, nên chạy đồng thời: A trên "main+A", B trên "main+A+B", C trên "main+A+B+C". Nếu B fail: A (không phụ thuộc B) vẫn merge; B bị loại và báo lỗi; C bị huỷ kết quả và test lại trên "main+A". Lợi ích là thông lượng gần như song song. Chi phí phát sinh chỉ khi có fail, nên flaky test làm hỏng cả queue. Zuul còn dùng window động để giới hạn số change chạy song song khi queue đang fail nhiều.

Đào tiếp
  • Bạn xử lý flaky test trong gate thế nào?
Một thay đổi signal cần sửa cả repo ARXML config và repo SWC. Làm sao merge an toàn? Áp dụng▾

Tạo hai change, change SWC ghi Depends-On: <URL change config> trong commit message. Ở check, Zuul test SWC trên nền có sẵn change config chưa merge. Ở gate, nếu hai repo cùng shared queue, change config được xếp trước. Nếu config fail thì SWC cũng bị loại. Main không bao giờ có trạng thái config mới mà code cũ. Không có Zuul thì phải dùng cách thủ công: merge đồng thời, hoặc thiết kế tương thích ngược (feature flag) rồi merge từng bên.

Chỉ có một HIL bench mà nhiều pipeline muốn dùng. Cấu hình thế nào? Áp dụng▾

Khoá độc quyền: Jenkins lock('bench-01') (Lockable Resources), GitLab resource_group, Zuul semaphore hoặc node tĩnh có label riêng. Phân tầng để giảm tải bench: check chỉ build + static + unit (không cần bench), gate chạy smoke ngắn trên bench, full regression trên bench chạy đêm (periodic). Thêm health-check và reset bench trước mỗi lần dùng để lỗi của run trước không làm fail run sau. Dài hạn: chuyển bớt test sang SIL/vECU (bài K).

Bạn chưa dùng Jenkins. Làm sao chứng minh sẽ bắt nhịp nhanh? Kinh nghiệm▾

Map khái niệm (bảng mục 6): tôi đã tích hợp build, package và test workflow với Azure Pipelines và Conan, giúp các bước kỹ thuật lặp lại được và chạy theo CI/CD. Jenkinsfile declarative có cùng cấu trúc: agent/label, stages, parallel, post, shared library. Điểm khác là hệ plugin và Groovy, và tôi đã đọc qua cú pháp. Kèm một chi tiết cụ thể như lock() cho bench hoặc stash giữa agent để cho thấy đã tìm hiểu thật.
