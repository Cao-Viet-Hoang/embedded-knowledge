B6 Core AUTOSAR — Module (đào sâu)

Mode Management — EcuM & BswM

Hai module Services Layer điều phối “ECU đang ở trạng thái nào & phải làm gì”. EcuM (ECU State Manager) lo vòng đời nguồn — startup, sleep, wakeup, shutdown & thứ tự init driver. BswM (BSW Mode Manager) là engine rule → action: gom “mode request” từ khắp stack, so điều kiện, thực thi hành động (bật/tắt PDU group, đổi schedule, Rte_Switch…). Từ AUTOSAR 4.0, phần điều phối pha UP tách khỏi EcuM và chuyển sang BswM — đây là điểm mấu chốt khi phỏng vấn.

Độ ưu tiên: 🟠 Core Gắn: NvM_ReadAll (bài B2), StartOS (B5), ComM (B3), RTE (B) Cùng nhóm: module B1a–B5
📌

Nguồn: đối chiếu AUTOSAR Classic SWS — EcuM (Flexible ECU Management: startup/shutdown/sleep/wakeup, RUN request, wakeup validation) & SWS — BswM (mode request port, logical expression, rule, action list, immediate/deferred). Xem cuối bài.

1. EcuM — ECU State Manager

Vai trò: là “bộ điều phối vòng đời” của ECU — từ lúc reset dứt cho tới off. EcuM (1) init & de-init BSW theo thứ tự cố định, (2) khởi động OS, (3) quản lý wakeup source & sleep (low-power), (4) chọn & thực thi shutdown target (OFF/RESET/SLEEP). EcuM không chứa logic ứng dụng — nó cung cấp khung trạng thái, còn hành vi theo mode do BswM quyết.

EcuM state machine (Flex). OFF →reset→ STARTUP →init OK→ UP. Từ UP có thể go down → SHUTDOWN (chọn target OFF/RESET) hoặc vào SLEEP (MCU low-power). Trong SLEEP, một wakeup event → WAKEUP → validate (lọc nhiễu) → nếu hợp lệ quay lại UP. Pha UP (RUN/POST-RUN) do BswM điều phối.

1.1 Khái niệm cốt lõi

EcuM Fixed vs EcuM Flexible
Fixed (kiểu cũ, ≤ AUTOSAR 3.x): EcuM chứa toàn bộ state machine kể cả pha UP (RUN/POST_RUN) & tự quản RUN request — cứng, khó tuỳ biến. Flexible (Flex) (từ 4.0, mặc định hiện nay): EcuM chỉ định nghĩa các sequence STARTUP/SHUTDOWN/SLEEP/WAKEUP; còn arbitration pha UP giao cho BswM. Đây là điểm phỏng vấn hay hỏi — “ai quản RUN/POST_RUN?” → BswM (Flex).
Các pha
STARTUP (I: trước StartOS · II: sau StartOS) → init driver theo list. UP: chạy bình thường (RUN có ứng dụng, POST_RUN dọn dẹp) — do BswM điều khiển. SHUTDOWN: đi tới OFF hoặc RESET. SLEEP: low-power. WAKEUP: xử lý & xác thực nguồn đánh thức.
Thứ tự init driver
EcuM gọi callout theo giai đoạn: EcuM_AL_DriverInitZero (driver không cần config post-build, chạy trước khi biết cấu hình), EcuM_DeterminePbConfiguration (chọn post-build config), EcuM_AL_DriverInitOne (phần lớn MCAL/BSW), rồi StartOS. Sau OS: EcuM_StartupTwo → NvM_ReadAll (bài B2), chờ NvM xong rồi mới init phần còn lại. Thứ tự tất định vì driver phụ thuộc nhau (clock/PLL trước, rồi mới tới module dùng clock).
Wakeup source & validation
Mỗi nguồn đánh thức (CAN, pin, WDG, timer…) có một wakeup source ID. Luồng 2 bước chống nhiễu: EcuM_SetWakeupEvent (phát hiện thô, vd cạnh trên bus) → EcuM_ValidateWakeupEvent (xác thực trong một cửa sổ thời gian, vd nhận được frame CAN hợp lệ). Không validate kịp → coi là nhiễu, quay lại SLEEP. Nguồn có thể polling (EcuM đọc định kỳ) hoặc interrupt.
Sleep: HALT vs POLL
SLEEP gắn với một MCU mode giảm nguồn (bài B1c). HALT: CPU dừng hẳn, chỉ ngắt (wakeup) đánh thức — tiết kiệm nhất. POLL: CPU chạy chậm, chủ động đọc các wakeup source không có ngắt riêng. Cấu hình qua EcuMSleepMode.
Shutdown target & cause
3 target: OFF (cắt nguồn), RESET (reset MCU), SLEEP. Chọn bằng EcuM_SelectShutdownTarget, đọc lại EcuM_GetShutdownTarget/GetLastShutdownTarget. Kèm shutdown cause (EcuM_SelectShutdownCause) để log lý do (vd lỗi, yêu cầu diag). RESET có thể có nhiều reset mode cấu hình được.
RUN / POST_RUN request
Cơ chế “ai đó cần ECU tiếp tục chạy”: module/SWC gọi EcuM_RequestRUN(user) giữ RUN; EcuM_ReleaseRUN(user) nhả. Khi mọi RUN request nhả hết → chuyển POST_RUN (làm việc dọn dẹp: ghi NvM, lưu DTC) → nhả nốt POST_RUN request → mới đi SHUTDOWN/SLEEP. Ở Flex, việc chuyển RUN↔POST_RUN do BswM rule điều khiển dựa trên các request này.
Alarm Clock (Flex)
EcuM Flex cho phép hẹn “đồng hồ báo thức”: ECU đang SLEEP tự dậy sau một khoảng thời gian đặt trước (vd wake định kỳ để đo cảm biến rồi ngủ lại) — không cần nguồn đánh thức ngoài.
Multicore
Flex hỗ trợ đa lõi: một master core chạy state machine chính; các lõi khác đồng bộ startup/shutdown qua cơ chế EcuM multicore (barrier). Quan trọng để tất cả lõi cùng ngủ/dậy nhất quán.

1.2 Container cấu hình (ARXML)

EcuMCommonConfiguration
Chứa EcuMDriverInitListZero / EcuMDriverInitListOne (danh sách & thứ tự gọi init driver), EcuMDriverRestartList, và tham chiếu các module BSW.
EcuMWakeupSource
EcuMWakeupSourceId, EcuMWakeupSourcePolling (polling hay interrupt), EcuMValidationTimeout (cửa sổ validate), EcuMComMChannelRef (nối wakeup ↔ kênh ComM để đánh thức giao tiếp).
EcuMSleepMode
EcuMSleepModeId, tham chiếu McuMode (mức nguồn), tập wakeup source cho phép trong mode ngủ đó.
EcuMFlexConfiguration / EcuMDefaultShutdownTarget
Cấu hình riêng cho Flex: shutdown target/cause mặc định, cấu hình Alarm Clock, danh sách user của RUN request.

1.3 API & pseudo-code

/* --- STARTUP (do khung khởi động gọi, thường trong main()) --- */
int main(void) {
    EcuM_Init();          /* DriverInitZero -> DeterminePbConfiguration
                             -> DriverInitOne -> StartOS(app_mode) */
    /* StartOS không trả về; task khởi động gọi tiếp: */
    /* EcuM_StartupTwo(): NvM_ReadAll(), chờ xong, init BSW còn lại */
    return 0;
}

/* --- Giữ ECU chạy khi còn việc --- */
EcuM_RequestRUN(ECUM_USER_APP);      /* app cần chạy */
/* ... làm việc ... */
EcuM_ReleaseRUN(ECUM_USER_APP);      /* nhả -> khi hết request => POST_RUN */

/* --- Ngủ & thức --- */
EcuM_SelectShutdownTarget(ECUM_STATE_SLEEP, sleepModeId);
/* Khi có sự kiện trên bus (ISR/polling): */
EcuM_SetWakeupEvent(ECUM_WKSOURCE_CAN);        /* phát hiện thô */
EcuM_ValidateWakeupEvent(ECUM_WKSOURCE_CAN);   /* xác thực -> nếu ok, lên UP */

/* --- Tắt máy --- */
EcuM_SelectShutdownTarget(ECUM_STATE_OFF, 0);
EcuM_SelectShutdownCause(ECUM_CAUSE_ECU_STATE);
/* EcuM_GoDown()/Shutdown chạy sequence SHUTDOWN */

2. BswM — BSW Mode Manager

Vai trò: trung tâm điều phối hành vi theo mode cho toàn stack, hiện thực bằng một engine “rules → actions” hoàn toàn cấu hình được (không cần sửa code). Trước 4.0, logic “khi X thì làm Y” nằm rải rác & hard-code trong EcuM/ComM/Com… BswM gom hết lại: nhận “mode request” từ mọi nơi → so rule (biểu thức logic) → chạy action list.

BswM = engine rule→action. Trái: các nguồn “mode request”. Giữa: mỗi rule là một biểu thức logic trên tập mode đang lưu; đúng → chạy true action list, sai → false action list. Phải: hành động cụ thể (bật/tắt PDU group, schedule table, Rte_Switch, PduR, NvM, EcuM). Toàn bộ là cấu hình, không sửa code.

2.1 Khái niệm cốt lõi

Mode Request Source / Port
“Đầu vào” của BswM. Mỗi nguồn có một request port & hàm callback riêng do module kia gọi: BswM_EcuM_CurrentState, BswM_ComM_CurrentMode, BswM_Dcm_CommunicationMode_CurrentState, BswM_NvM_CurrentJobMode, BswM_CanSM_CurrentState, BswM_RequestMode (generic từ SWC/RTE)… BswM lưu giá trị mode mới nhất của mỗi nguồn.
Logical Expression & Mode Condition
Mode condition: so một mode đang lưu với hằng (vd ComM == FULL_COM). Logical expression: ghép nhiều condition bằng toán tử AND/OR/NOT (và biến thể NAND/NOR), có thể lồng (nested) — biểu diễn điều kiện phức tạp mà vẫn khai báo thuần cấu hình.
Rule
Đơn vị quyết định: gắn một logical expression với hai action list — BswMRuleTrueActionList (khi biểu thức đúng) & BswMRuleFalseActionList (khi sai). Có init state để xử lý lần đánh giá đầu. Rule có thể tham chiếu rule khác (nested expression) để tái dùng.
Action & Action List
Action = một thao tác nguyên tử; action list = chuỗi action chạy theo thứ tự. Action có sẵn (available actions), tiêu biểu: PDU group switch (Com_IpduGroupControl), schedule table switch, Rte mode switch (Rte_Switch), PduR routing path group enable/disable, NvM single-block / write RAM block, EcuM state switch / go-down, trigger IPDU send, partial-networking state, và user callout (gọi hàm tự viết).
Action List Execution Type: CONDITION vs TRIGGER
CONDITION: action list chỉ chạy khi kết quả rule đổi so với lần trước (level-based — tránh chạy lặp mỗi chu kỳ). TRIGGER: chạy mỗi lần rule đúng, kể cả kết quả không đổi (edge/event-based, vd mỗi request là một sự kiện cần phản ứng).
Immediate vs Deferred processing
Cấu hình trên request port. Immediate: request tới → arbitration + action chạy ngay trong ngữ cảnh lời gọi (độ trễ thấp, dùng cho phản ứng gấp như tắt comm khi bus-off). Deferred (queued): chỉ lưu request; arbitration chạy ở chu kỳ BswM_MainFunction kế tiếp — gộp nhiều request, tải CPU đều hơn, nhưng có độ trễ tới 1 chu kỳ main function.
Khởi tạo & MainFunction
BswM_Init nạp mode ban đầu & chạy rule init. BswM_MainFunction (gọi định kỳ bởi BSW Scheduler) xử lý các request deferred. Chu kỳ main function ảnh hưởng trực tiếp độ trễ của mode deferred.
Quan hệ với RTE
SWC có thể yêu cầu mode (qua port ⇒ BswM_RequestMode) và nhận mode qua Rte_Switch (một action của BswM) → SWC chạy đúng runnable theo mode. Nhờ đó ứng dụng & BSW đồng bộ trạng thái mà không gọi trực tiếp nhau.

2.2 Container cấu hình (ARXML)

BswMModeRequestPort
Khai báo từng nguồn request (EcuM/ComM/Dcm/NvM/CanSM/Generic…) + cờ immediate hay không. Là nơi map callback → biến mode nội bộ.
BswMLogicalExpression / BswMModeCondition
BswMArgumentRef (mode nào), BswMLogicalOperator (AND/OR/NOT…), điều kiện so sánh. Ghép thành biểu thức của rule.
BswMRule
BswMRuleTrueActionList, BswMRuleFalseActionList, BswMRuleInitState, tham chiếu logical expression / nested rule.
BswMActionList / BswMAction
BswMActionListItem (thứ tự), BswMActionListExecutionType (CONDITION/TRIGGER), và từng BswMAction chọn từ tập available actions (PduGroupSwitch, ScheduleTableSwitch, RteModeRequest, PduRoutingPathGroupSwitch, NvMSingleBlockRequest, EcuMStateSwitch, UserCallout…).

2.3 Ví dụ rule + API

/* Ví dụ khái niệm một rule (biểu diễn logic, thực tế cấu hình bằng ARXML):

   RULE "Enable app Tx when full comm + NvM ready"
     EXPR = (ComM_Ch0 == FULL_COMMUNICATION) AND (NvM_ReadAll == DONE)
     TRUE  action list:
        - Com_IpduGroupControl(TX_APP_GROUP, ENABLE)   // bật gửi
        - Rte_Switch(mode_app, RUN)                    // báo SWC
     FALSE action list:
        - Com_IpduGroupControl(TX_APP_GROUP, DISABLE)  // tắt gửi
     ExecutionType = CONDITION   // chỉ chạy khi kết quả rule đổi
*/

/* --- Các module BSW "đẩy" mode vào BswM (callback) --- */
BswM_EcuM_CurrentState(ECUM_STATE_APP_RUN);   /* EcuM báo state */
BswM_ComM_CurrentMode(0, COMM_FULL_COMMUNICATION);
BswM_NvM_CurrentJobMode(NVM_READ_ALL, NVM_REQ_OK);

/* --- SWC/ứng dụng yêu cầu mode chung --- */
BswM_RequestMode(BSWM_USER_APP, MY_APP_MODE_ACTIVE);

/* --- BSW Scheduler gọi định kỳ để xử lý request deferred --- */
void BswM_MainFunction(void) { /* arbitrate queued requests -> run action lists */ }

3. EcuM ↔ BswM ↔ ComM — phối hợp lúc startup

Ba module chia vai rõ: EcuM lo trình tự nguồn/init; BswM quyết “khi trạng thái thế này thì bật/tắt gì”; ComM (bài B3) gom nhu cầu giao tiếp & điều CanSM bật bus. Sơ đồ dưới là chuỗi khởi động điển hình.

Chuỗi startup. EcuM điều phối init & StartOS; NvM_ReadAll nạp cấu hình/hiệu chỉnh; BswM_Init đặt mode khởi đầu; RTE chạy SWC. Vào pha UP, BswM đảm nhận arbitration — vd khi ComM báo FULL_COM thì bật Tx PDU group, khi tất cả RUN request nhả thì cho EcuM go-down.
Ai làm gì (một câu)
EcuM = “bật/tắt & ngủ/dậy ECU + thứ tự init”. BswM = “luật: trạng thái nào thì bật/tắt cái gì”. ComM = “gom yêu cầu giao tiếp của user (App/Dcm/NM) → điều CanSM bật/tắt bus”. BswM có thể phản ứng theo mode của ComM (vd bật PDU group), còn ComM lo mức bus/network.
Ví dụ dòng chảy “tắt giao tiếp để ngủ”
App nhả mọi ComM request → ComM chuyển No Communication → gọi BswM_ComM_CurrentMode(NO_COM) → rule BswM tắt Tx/Rx PDU group, dừng schedule table, cho phép EcuM go-down → EcuM chọn target SLEEP/OFF.

4. Bẫy thường gặp & cách test

Nhầm EcuM Fixed vs Flex
Nói “EcuM quản RUN/POST_RUN” là kiểu Fixed. Với Flex (mặc định 4.x) phần đó là BswM. Trả lời sai điểm này lộ ngay là chưa nắm kiến trúc hiện đại.
Quên wakeup validation
Chỉ SetWakeupEvent mà không ValidateWakeupEvent → ECU tỉnh vì nhiễu rồi ngủ lại liên tục (ping-pong), hao pin. Luôn có bước validate trong cửa sổ timeout.
Immediate vs Deferred đặt sai
Phản ứng an toàn/gấp (bus-off, tắt comm) mà để deferred → trễ tới 1 chu kỳ MainFunction. Ngược lại để immediate quá nhiều → arbitration chạy trong ngữ cảnh caller, dễ tăng latency/độ phức tạp. Chọn đúng theo yêu cầu thời gian.
CONDITION vs TRIGGER nhầm
Dùng CONDITION cho việc cần chạy mỗi sự kiện (vd mỗi request gửi 1 frame) → chỉ chạy khi mode đổi, bỏ lỡ sự kiện lặp. Và ngược lại TRIGGER cho việc set-once → chạy dư mỗi chu kỳ.
Cách test
State transition testing (bài C): liệt kê state EcuM & kiểm tra transition hợp lệ/không hợp lệ, wakeup/sleep. Với BswM: bảng quyết định (decision table) map tổ hợp mode-input → action mong đợi; test cả immediate & deferred (kiểm tra sau 1 chu kỳ MainFunction). Dùng đo schedule/latency để xác nhận thời điểm bật comm đúng.

5. Trước (~2020) → Nay

🔀 Mode management: từ EcuM đơn khối → EcuM Flex + BswM
⏪ Trước

EcuM “Fixed” ôm cả state machine lẫn logic pha UP (RUN/POST_RUN); hành vi theo mode hard-code, rải rác trong nhiều module → sửa hành vi = sửa & build lại code.

⏩ Nay

EcuM Flex chỉ lo sequence startup/shutdown/sleep/wakeup; BswM gom toàn bộ arbitration theo mode thành rule→action cấu hình được. Đổi hành vi = đổi ARXML, không đụng code. Thêm partial networking, alarm clock, multicore.

Vì sao quan trọng: nói được “Flex tách UP-arbitration sang BswM để cấu hình hành vi mà không sửa code, EcuM chỉ còn lo vòng đời nguồn” cho thấy hiểu tại sao AUTOSAR tách hai module, không chỉ thuộc tên.

6. Tự kiểm tra

EcuM và BswM khác nhau chỗ nào? Ai quản pha UP (RUN/POST_RUN)? Định nghĩa▾

EcuM lo vòng đời nguồn: startup (thứ tự init driver), sleep/wakeup, shutdown target. BswM là engine rule→action điều phối hành vi theo mode. Ở EcuM Flex (mặc định 4.x), pha UP (RUN/POST_RUN) do BswM quản qua rule dựa trên RUN request; còn EcuM Fixed (cũ) tự ôm phần này.

Đào tiếp
  • Vì sao AUTOSAR tách UP-arbitration sang BswM?
  • RUN request/POST_RUN hoạt động thế nào?
Mô tả cơ chế rule → action của BswM. Immediate vs deferred? Áp dụng▾

BswM nhận mode request từ nhiều nguồn (EcuM/ComM/Dcm/NvM/generic), lưu lại, rồi đánh giá các rule = biểu thức logic (AND/OR/NOT) trên tập mode; đúng → chạy true action list, sai → false action list (Com PDU group, schedule table, Rte_Switch, PduR, NvM, EcuM…). Immediate: arbitration + action chạy ngay khi request tới (độ trễ thấp). Deferred: chỉ lưu, xử lý ở BswM_MainFunction kế (gộp request, đều tải, trễ tới 1 chu kỳ).

Đào tiếp
  • ExecutionType CONDITION vs TRIGGER?
  • Khi nào bắt buộc immediate?
Wakeup validation là gì, vì sao cần? Áp dụng▾

Hai bước: EcuM_SetWakeupEvent phát hiện thô (vd cạnh trên bus), rồi EcuM_ValidateWakeupEvent xác thực trong cửa sổ timeout (vd nhận được frame CAN hợp lệ). Cần để lọc nhiễu: nếu không có tín hiệu thật, ECU ngủ lại thay vì tỉnh giả rồi ping-pong tốn pin.

Đào tiếp
  • Nguồn polling vs interrupt?
  • SLEEP HALT vs POLL?
Kể chuỗi startup của EcuM đến khi lên UP. Kinh nghiệm▾

EcuM_Init → EcuM_AL_DriverInitZero (driver không cần post-build) → EcuM_DeterminePbConfiguration → EcuM_AL_DriverInitOne (phần lớn MCAL/BSW) → StartOS. Sau OS, task khởi động gọi EcuM_StartupTwo → NvM_ReadAll (chờ nạp cấu hình/hiệu chỉnh) → BswM_Init đặt mode ban đầu → RTE chạy SWC → pha UP, BswM tiếp quản arbitration. Thứ tự tất định vì driver phụ thuộc nhau (clock/PLL trước).

Ví dụ: “khi ComM kênh 0 = FULL_COM VÀ NvM_ReadAll = DONE → bật Tx app PDU group + Rte_Switch(RUN); ngược lại tắt Tx” (ExecutionType CONDITION để chỉ chạy khi kết quả đổi). 7. Cheat-sheet 1 trang

EcuM — pha

  • STARTUP (I→StartOS→II) · UP · SHUTDOWN · SLEEP · WAKEUP
  • Init: DriverInitZero → PbConfig → DriverInitOne → StartOS → StartupTwo(NvM_ReadAll)
  • Fixed (ôm UP) vs Flex (UP → BswM)

EcuM — nguồn/ngủ

  • Wakeup: SetWakeupEvent → ValidateWakeupEvent (lọc nhiễu)
  • Sleep: HALT (CPU dừng) / POLL (chạy chậm) — MCU mode
  • Shutdown target: OFF / RESET / SLEEP (+ cause)
  • RUN/POST_RUN request → hết request thì go-down

BswM — engine

  • Mode request source → lưu mode → rule → action list
  • Rule = logical expr (AND/OR/NOT) → true/false action list
  • Action: PDU group · schedule table · Rte_Switch · PduR · NvM · EcuM
  • Cấu hình ARXML, không sửa code

BswM — timing

  • Immediate (ngay) vs Deferred (BswM_MainFunction)
  • ExecType: CONDITION (khi đổi) vs TRIGGER (mỗi lần)
  • BswM_Init đặt mode ban đầu

Phối hợp

  • EcuM = vòng đời nguồn · BswM = luật mode · ComM = nhu cầu giao tiếp
  • ComM NO_COM → BswM tắt PDU group → EcuM go-down
  • SWC: BswM_RequestMode (yêu cầu) / Rte_Switch (nhận)

Bẫy phỏng vấn

  • Ai quản UP? → BswM (Flex), không phải EcuM
  • Quên wakeup validation → ping-pong hao pin
  • Immediate/Deferred & CONDITION/TRIGGER đặt đúng

8. Nguồn tham khảo

  • AUTOSAR Classic SWS — EcuM (Flexible ECU Management): pha STARTUP/UP/SHUTDOWN/SLEEP/WAKEUP, driver init list, wakeup source & validation, RUN/POST_RUN request, shutdown target/cause, alarm clock, multicore.
  • AUTOSAR Classic SWS — BswM (Basic Software Mode Manager): mode request port, logical expression, rule, action & action list, execution type CONDITION/TRIGGER, immediate/deferred, available actions.
  • AUTOSAR Layered Software Architecture & SWS ComM — quan hệ EcuM/BswM/ComM/CanSM (đối chiếu bài B3).
