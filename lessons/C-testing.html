Testing Methodology & Tools

Phần lớn công việc thực tế của bạn là test. Phải nắm chắc test levels, test design techniques (ISTQB), coverage (đặc biệt MC/DC), mocking/stubbing, fault injection, gắn với ASPICE và các tool bạn dùng: Cantata, ECU-Test, Pytest, VECU, CANoe.

Độ ưu tiên: 🔴 Cao Trọng tâm: MC/DC, mocking, fault injection Tools: Cantata · ECU-Test · Pytest · VECU
📌

Nguồn: các định nghĩa test design (ISTQB), coverage/MC-DC và yêu cầu ASIL (ISO 26262 / DO-178C), tên process ASPICE đều đối chiếu nguồn chuẩn — xem mục “Nguồn tham khảo” cuối bài.

1. Test levels — ranh giới rõ ràng

Interviewer hay hỏi “phân biệt unit và integration test”. Trả lời bằng phạm vi cô lập và cái gì được test. Mô hình kim tự tháp: càng xuống dưới càng nhiều test, nhanh, cô lập; càng lên trên càng ít, chậm, thực tế.

Test pyramid. Nhiều unit (bắt lỗi logic sớm, rẻ) → ít system (bắt lỗi tương tác, đắt). Trả lời phỏng vấn nên bám trục cô lập và cái gì được test.
LevelĐối tượngCô lậpTool bạn dùng
Unit1 hàm/đơn vị nhỏMock/stub mọi phụ thuộcCantata, Pytest
Component1 module (vd 1 driver MCAL)Stub bên ngoài moduleCantata, ECU-Test
IntegrationNhiều module ghép nhauÍt/không mock, test interfaceECU-Test, CANoe
SystemToàn ECU/stack (ARA)Môi trường thật/gần thậtECU-Test, target + VECU
🎯

Câu chốt: “Càng xuống thấp càng cô lập và rẻ; càng lên cao càng thực tế nhưng đắt. Unit bắt lỗi logic sớm, system bắt lỗi tương tác. Theo ASPICE: unit ↔ SWE.4, integration ↔ SWE.5, qualification ↔ SWE.6.”

2. Test design techniques (ISTQB black-box)

Cách chọn test case sao cho ít ca nhất mà bao phủ tốt nhất. Bốn kỹ thuật specification-based (black-box) kinh điển của ISTQB:

Chia input thành các lớp tương đương — mọi giá trị trong một lớp cho hành vi giống nhau → chỉ cần test 1 đại diện/lớp, giảm số ca test. Lớp thường suy từ requirement. Vd hàm nhận 0–100: lớp hợp lệ [0–100], lớp dưới (<0), lớp trên (>100). Áp dụng cho cả input lẫn (hiếm hơn) output.

Lỗi hay nằm ở biên giữa các lớp tương đương. Với dải [0–100], test các giá trị quanh biên: -1, 0, 1, 99, 100, 101. BVA luôn đi cùng EP (EP chọn lớp, BVA chọn biên của lớp).

Khi output phụ thuộc tổ hợp nhiều điều kiện (business/logic phức tạp). Liệt kê tổ hợp condition → action thành bảng, đảm bảo không sót tổ hợp quan trọng. Mỗi cột = một rule = một test.

Khi hệ có trạng thái (vd state machine của EcuM/BswM/CanSM). Test các chuyển trạng thái hợp lệ & không hợp lệ, sự kiện kích hoạt, và hành vi ở mỗi state. Phủ được “0-switch” (transition đơn) tới “n-switch” (chuỗi transition).

🧠

Mẹo trả lời: “EP/BVA chọn giá trị input; decision table chọn tổ hợp điều kiện; state transition chọn thứ tự sự kiện. Đây là black-box (theo spec); còn coverage là white-box (theo code).”

3. Code coverage — tới MC/DC

Coverage (white-box) đo “test đã chạy qua bao nhiêu phần code”. Mức tăng dần độ nghiêm ngặt — mức mạnh hơn bao trùm (subsumes) mức yếu hơn:

Subsumption. MC/DC bao trùm Branch, Branch bao trùm Statement. Với if(A && B): 1 / 2 / 3 test — MC/DC cần n+1 (rẻ hơn nhiều so với Multiple Condition Coverage = 2ⁿ).
MứcYêu cầuSố test cho if(A && B)
StatementMỗi dòng lệnh chạy ≥1 lần1 (A=T,B=T)
Branch / DecisionMỗi nhánh true & false đều chạy2 (kết quả T và F)
MC/DCMỗi điều kiện con độc lập ảnh hưởng kết quả3 (n+1)

3.1 MC/DC là gì — 4 điều kiện & ví dụ

MC/DC (Modified Condition/Decision Coverage) đòi đồng thời 4 điều kiện (theo định nghĩa Chilenski–Miller, gốc DO-178B):

  1. Mỗi entry/exit point được gọi.
  2. Mỗi decision nhận đủ true & false.
  3. Mỗi condition con nhận đủ true & false.
  4. Mỗi condition con tự nó độc lập lật được kết quả (giữ các điều kiện khác cố định — chỉ đổi một điều kiện tại một thời điểm).
// decision: result = A && B  -> MC/DC cần 3 test (n+1)
//  TC1: A=1, B=1  -> result=1
//  TC2: A=0, B=1  -> result=0   (đổi A, giữ B=1 -> chứng minh A độc lập tác động)
//  TC3: A=1, B=0  -> result=0   (đổi B, giữ A=1 -> chứng minh B độc lập tác động)
// So sánh: Multiple Condition Coverage cần 2^n = 4 test. MC/DC chỉ n+1 = 3.
TestABresultChứng minh
TC1111baseline
TC2010đổi A (giữ B=1) → A độc lập
TC3100đổi B (giữ A=1) → B độc lập
🛡️
Vì sao automotive bắt buộc MC/DC ở ASIL cao?

Theo ISO 26262: ở unit-level, branch coverage đủ cho ASIL A–C; còn MC/DC được “highly recommended” cho ASIL D. Lý do: branch chỉ cần decision đạt true/false, một điều kiện con có thể không bao giờ được test độc lập → che giấu lỗi logic. MC/DC bắt mỗi điều kiện tự nó được kiểm chứng. MC/DC có gốc từ DO-178B/C (hàng không, DAL A). Xem bài H.

4. Mocking & Stubbing — cô lập phụ thuộc

Stub

Thay thế phụ thuộc bằng phiên bản “giả” trả về giá trị định sẵn. Mục đích: điều khiển input để unit chạy được độc lập. Kiểm tra state — quan tâm “trả về gì”.

Mock

Như stub nhưng còn kiểm tra tương tác: hàm có được gọi không, gọi mấy lần, với tham số gì. Kiểm tra behavior — quan tâm “được gọi thế nào”.

4.1 Vì sao cần — và cơ chế của Cantata

Driver MCAL gọi xuống thanh ghi/HW. Khi unit test không có HW, ta stub các hàm phần cứng để kiểm soát đầu vào và mock để kiểm tra driver gọi đúng. Cantata sinh khung test C/C++, cho phép wrap/stub hàm phụ thuộc, kiểm tra call sequence, và đo coverage tới MC/DC.

// Ý tưởng (giả lược): test driver đọc ADC mà không cần phần cứng
uint16_t Adc_ReadChannel(uint8_t ch);     // hàm cần test
uint16_t Hw_ReadRegister(uint32_t addr);  // phụ thuộc HW -> sẽ STUB

// Trong test:
//  - STUB Hw_ReadRegister() để trả 0x0ABC
//  - gọi Adc_ReadChannel(2)
//  - EXPECT kết quả map đúng; EXPECT Hw_ReadRegister được gọi 1 lần với addr kênh 2 (MOCK)
void test_Adc_ReadChannel_returns_mapped_value(void) {
    stub_set_return(Hw_ReadRegister, 0x0ABC);
    uint16_t v = Adc_ReadChannel(2);
    CHECK_EQUAL(0x0ABC, v);
    CHECK_CALLED_ONCE(Hw_ReadRegister);
}

5. Fault injection — test đường lỗi

Happy path là chưa đủ. Phải chủ động tạo lỗi để kiểm tra error-handling — chính là điều bạn làm trong SENT automation (CRC sai, nibble ngoài dải, timing lệch).

  • Input lỗi: giá trị ngoài dải, NULL pointer, buffer rỗng/tràn.
  • Phụ thuộc lỗi: stub trả mã lỗi (vd HW báo timeout) → kiểm tra code xử lý đúng.
  • Trạng thái lỗi: đưa state machine vào tổ hợp bất thường.
  • Protocol lỗi: khung sai CRC, sai timing → kiểm tra phát hiện & báo lỗi.
💡

Quy tắc: với mỗi requirement “khi X xảy ra thì hệ thống phải Y”, hãy tạo X bằng fault injection để chứng minh Y. Đó là bằng chứng mạnh cho ASPICE (test cả negative requirement).

6. Bộ công cụ (must-tell)

Cantata

Unit/Component test C/C++ với stub/mock & coverage tới MC/DC. Dùng cho test driver MCAL.

ECU-Test

Test tự động ở mức tích hợp/hệ thống, kịch bản test, kết nối nhiều công cụ/thiết bị (tracetronic).

Pytest

Khung test Python cho automation framework & scripting test (data-driven, fixture, parametrize).

VECU (Virtual ECU)

Mô phỏng ECU để chạy test không cần target thật → chạy sớm, song song, CI-friendly.

CANoe

Mô phỏng/giám sát mạng CAN/LIN/Ethernet; kích thích & quan sát bus trong integration/system test (Vector).

TRACE32 / UDE

Debug phần cứng: soi register/memory, breakpoint, trace; UDE cho debug timing SENT. Xem bài F.

7. ASPICE — work product SWE.4/5/6

Các process SWE bên nhánh phải V-model gắn với test level (tên đối chiếu chuẩn Automotive SPICE):

SWE.4
Software Unit Verification — verify unit so với detailed design + non-functional req; nơi áp EP/BVA + coverage (statement/branch/MC-DC).
SWE.5
Software Integration & Integration Test — ghép unit/component, verify tương tác so với SW architecture.
SWE.6
Software Qualification Test — verify phần mềm tích hợp so với software requirements (SWE.1).

Mỗi mức cần work product: test spec, test case, kết quả, và traceability requirement↔test hai chiều. Đây là lý do report automation (bài D) phải tự map requirement↔test.

9. Static Analysis & Sanitizers

JD xếp static analysis/sanitizer là nice-to-have. Đây là lớp kiểm thử tự động, không cần viết test case — bắt các lỗi mà unit test dễ bỏ sót (undefined behavior, data race, memory bug).

9.1 Static analysis — soi code, không chạy

Phân tích mã nguồn không thực thi (compile-time). Phát hiện: null dereference, buffer overflow, biến chưa init, dead code, integer overflow, và vi phạm MISRA (xem bài G).

9.2 Sanitizers — kiểm tra lúc chạy (runtime)

Biên dịch với cờ -fsanitize= của GCC/Clang (MSVC có /fsanitize=address), chèn kiểm tra vào binary rồi chạy — bắt lỗi ngay tại thời điểm nó xảy ra.

ASan
AddressSanitizer — heap/stack buffer overflow, use-after-free, use-after-return.
UBSan
UndefinedBehaviorSanitizer — hành vi không xác định (overflow có dấu, dịch bit quá mức, deref lệch alignment…).
TSan
ThreadSanitizer — phát hiện data race; cực hữu ích cho vECU đa luồng (xem bài M).
MSan
MemorySanitizer — đọc bộ nhớ chưa khởi tạo.
LSan
LeakSanitizer — rò rỉ bộ nhớ (memory leak).

Valgrind (memcheck/helgrind): không cần biên dịch lại nhưng chậm (mô phỏng CPU) — tiện khi không sửa được build.

Khuyến nghị: kết hợp — static quét toàn bộ code (kể cả nhánh chưa test), sanitizer bắt lỗi thật khi chạy test. Đưa cả hai thành CI gate (fail build khi có finding mới) — xem bài J.

10. Deterministic & Trace-based Validation

10.1 Deterministic testing — kết quả lặp lại được

JD yêu cầu deterministic tests: test cho cùng kết quả mỗi lần chạy. Muốn vậy phải kiểm soát mọi nguồn bất định:

  • Thời gian: đừng đọc đồng hồ thật — inject clock / virtual time để điều khiển (khớp mô hình vECU, xem bài K).
  • Ngẫu nhiên: cố định seed để chuỗi random tái lập.
  • Lịch luồng: tránh test phụ thuộc timing/thứ tự luồng (dễ cho kết quả khác nhau).
  • I/O: mock/stub file, mạng, bus để loại phụ thuộc bên ngoài.
⚠️

Flaky test = test lúc pass lúc fail dù code không đổi (thường do timing/random/thứ tự luồng). Xấu vì làm mất niềm tin vào CI: người ta bắt đầu bỏ qua fail đỏ, che luôn cả lỗi thật.

10.2 Trace-based validation — so trace với golden

Thay vì chỉ assert giá trị trả về, ta ghi lại hành vi quan sát (trace) rồi so khớp với golden/reference trace kỳ vọng. Hợp với hệ thời gian thực / giao tiếp bus:

  • CAN frame trace: so ID, DLC, payload, timestamp, chu kỳ khung.
  • Chuỗi UDS: so trình tự request/response chẩn đoán (xem bài B4).
  • Signal log: so tín hiệu đã giải mã theo thời gian.

Công cụ ghi/so: CANoe xuất trace .blf/.asc, phân tích offline so với reference.

🔍

Khác assertion-based unit test: unit test kiểm một điểm (giá trị/tương tác) tại chỗ; trace-based kiểm cả chuỗi hành vi theo thời gian (thứ tự, timing, chu kỳ) — bắt lỗi mà assert đơn lẻ không thấy.

11. Tooling: CANoe + CAPL, Wireshark

11.1 CANoe

Công cụ Vector để mô phỏng & giám sát CAN/LIN/Ethernet/FlexRay. Thành phần chính: simulation node (mô phỏng ECU), panels (nút/đèn điều khiển), test module/test unit (kịch bản test tự động). Dùng để kích thích (stimulate) và quan sát bus trong integration/system test.

11.2 CAPL — CAN Access Programming Language

Ngôn ngữ event-driven của CANoe/CANalyzer, cú pháp giống C; dùng để mô phỏng node, phát/nhận frame, viết test case. Code chạy theo handler:

  • on message — khi nhận một frame CAN.
  • on timer — hết chu kỳ timer (gửi định kỳ).
  • on key — khi nhấn phím.
  • on sysvar — khi biến hệ thống đổi.
  • on start — khi bắt đầu measurement.
// CAPL: mô phỏng một node — phản hồi frame và gửi định kỳ
variables {
    message 0x100 msgTx;   // frame sẽ gửi
    msTimer  tHeartbeat;   // timer chu kỳ
}

on start {
    setTimer(tHeartbeat, 100);       // 100 ms
}

on timer tHeartbeat {
    msgTx.byte(0) = 0xA5;
    output(msgTx);                   // gửi frame lên bus
    setTimer(tHeartbeat, 100);       // nạp lại -> chu kỳ 100 ms
}

on message 0x200 {                   // khi nhận frame ID 0x200
    if (this.byte(0) == 0x01) {
        msgTx.byte(1) = this.byte(0);
        output(msgTx);               // đáp lại request
    }
}

11.3 Wireshark

Phân tích gói Ethernet/IP/UDP/TCP và các giao thức automotive DoIP/SOME-IP. Cơ chế: capture gói + dissector giải mã theo tầng. Hữu ích cho automotive Ethernet — bổ trợ CANoe khi debug giao tiếp service-oriented.

12. Tự kiểm tra

Stub khác Mock thế nào? Định nghĩa▾

Stub: cấp input định sẵn (quan tâm “trả về gì” — kiểm tra state). Mock: ngoài ra còn verify tương tác (được gọi không, mấy lần, tham số gì — kiểm tra behavior).

Interviewer đào tiếp
  • Cantata cô lập phụ thuộc bằng cơ chế gì? (wrap/stub hàm + check call)
  • Over-mocking có hại gì? (test giòn, gắn chặt implementation)
Cho if(A || B), MC/DC cần mấy test và là những test nào? Áp dụng▾

3 test (n+1): (A=0,B=0)→F; (A=1,B=0)→T chứng minh A; (A=0,B=1)→T chứng minh B. Mỗi điều kiện độc lập lật kết quả khi giữ điều kiện kia ở giá trị không che (ở đây =0).

Interviewer đào tiếp
  • Với A&&B thì “giá trị không che” là gì? (giữ điều kiện kia =1)
  • Short-circuit evaluation ảnh hưởng MC/DC ra sao?
Khi nào dùng VECU thay vì target thật? Áp dụng▾

Khi cần chạy sớm, song song, trong CI (shift-left) để bắt lỗi logic nhanh và rẻ. Nhưng lỗi liên quan timing/HW thật (vd SENT) vẫn phải xác nhận trên target.

Interviewer đào tiếp
  • VECU không bắt được loại lỗi nào? (timing HW, đặc tính điện, ngắt thật)
Vì sao branch coverage 100% vẫn có thể sót lỗi? Áp dụng▾

Branch chỉ cần decision đạt true/false, không bắt mỗi điều kiện con độc lập tác động. Một điều kiện luôn bị “che” bởi điều kiện khác có thể sai mà test không phát hiện → cần MC/DC (đó là lý do ASIL D yêu cầu MC/DC).

Interviewer đào tiếp
  • Cho ví dụ một lỗi mà branch 100% bỏ sót.
Bạn thiết kế test cho một driver MCAL như thế nào? Kinh nghiệm▾

Từ requirement → dùng EP/BVA chọn giá trị input (kênh, dải giá trị, biên), stub truy cập thanh ghi để cô lập HW, mock để verify driver gọi đúng (đúng addr/đúng số lần), thêm fault injection (HW trả lỗi/timeout) cho error path, đo coverage tới MC/DC, và map test↔requirement (ASPICE). Chạy trên VECU sớm + target để xác nhận.

Interviewer đào tiếp
  • Làm sao đạt MC/DC cho một hàm nhiều điều kiện?
  • Test một ISR/critical section thế nào?
ASan, TSan và static analysis khác nhau ra sao? Định nghĩa▾

Static analysis: soi code lúc compile, không chạy — bắt null deref/overflow/MISRA, quét cả nhánh chưa test (nhưng nhiều false positive). ASan: runtime, bắt lỗi bộ nhớ (buffer overflow, use-after-free). TSan: runtime, bắt data race giữa các luồng. Sanitizer báo lỗi thật đã xảy ra nhưng chỉ trên đường code được chạy → nên kết hợp cả hai.

Interviewer đào tiếp
  • Vì sao TSan quan trọng với vECU đa luồng?
  • Valgrind khác sanitizer chỗ nào? (không cần build lại, nhưng chậm)
Làm sao test deterministic khi code phụ thuộc thời gian? Áp dụng▾

Inject clock / virtual time: không đọc đồng hồ thật mà truyền nguồn thời gian vào (interface/mock), test tự điều khiển “giờ hiện tại” và cho nhảy tới thời điểm mong muốn. Tương tự: cố định seed random, mock I/O, tránh phụ thuộc lịch luồng. Nhờ vậy test lặp lại được, không flaky.

Interviewer đào tiếp
  • Flaky test là gì và vì sao nguy hiểm?
  • Test một timeout 5 phút mà không chờ thật thì làm sao?
CAPL dùng để làm gì? Định nghĩa▾

CAPL là ngôn ngữ event-driven (cú pháp giống C) của CANoe/CANalyzer để mô phỏng node, phát/nhận frame và viết test case trên bus. Code tổ chức theo handler: on message, on timer, on key, on sysvar, on start. Vd: on timer gửi heartbeat định kỳ, on message đáp lại một request.

Interviewer đào tiếp
  • Trace-based validation với CAN/UDS làm thế nào?
  • Khi nào dùng Wireshark thay vì CANoe? (automotive Ethernet/DoIP/SOME-IP)

13. Cheat-sheet 1 trang

Test levels

  • Unit → Component → Integration → System
  • Xuống: cô lập/rẻ/nhanh · Lên: thực tế/đắt
  • Pyramid: nhiều unit, ít system
  • ASPICE: SWE.4 / SWE.5 / SWE.6

Test design (ISTQB)

  • EP: chọn lớp tương đương
  • BVA: test biên (-1,0,1,…)
  • Decision table: tổ hợp điều kiện
  • State transition: thứ tự sự kiện

Coverage

  • Statement ⊂ Branch ⊂ MC/DC
  • MC/DC: mỗi điều kiện độc lập lật kết quả
  • n điều kiện → n+1 test (MCC = 2ⁿ)
  • ISO 26262: branch A–C · MC/DC highly rec. cho D

Mock/Stub/Fault

  • Stub = state (trả về gì)
  • Mock = behavior (gọi thế nào)
  • Fault injection: input/dependency/state/protocol
  • Mỗi negative req → 1 fault injection

Tools

  • Cantata: unit C/C++ + MC/DC
  • ECU-Test: integration/system
  • Pytest: automation/scripting
  • VECU: shift-left CI · CANoe: bus

Static/Sanitizer/Trace

  • Static: cppcheck·Clang-Tidy·Coverity·Polyspace (MISRA)
  • Sanitizer: ASan·UBSan·TSan·MSan·LSan
  • TSan = data race · Valgrind = chậm, không build lại
  • Deterministic: inject clock, fix seed, mock I/O
  • Trace-based: so trace CAN/UDS với golden (.blf/.asc)

Câu chốt

  • Black-box = theo spec · White-box = theo code
  • MC/DC bắt lỗi Boolean phức tạp
  • Test cả negative path (fault injection)
  • Traceability requirement ↔ test (ASPICE)
