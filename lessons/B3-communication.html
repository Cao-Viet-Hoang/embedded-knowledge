B3 Core AUTOSAR — Module (đào sâu)

Communication Stack (CAN)

Từ signal của app xuống bit trên bus: COM (signal↔PDU) → PduR (route) → CanIf (abstraction) → Can (MCAL) → bus; cộng CanTp (segment), CanSM (state + bus-off), CanNm (sleep/wakeup mạng), ComM (điều phối). Mỗi module một mục đầy đủ.

Độ ưu tiên: 🟠 Core Gắn: CAN/UDS (bài E), Diag (B4) Tổng quan: bài B
📌

Nguồn: tên module/API/PDU đối chiếu AUTOSAR Classic SWS (Com, PduR, CanIf, CanTp, CanSM, CanNm, ComM) & ISO 15765-2 (CAN-TP) — xem cuối bài. Lớp protocol CAN/UDS ở bài E.

Luồng dữ liệu. Tín hiệu app: COM↔PduR↔CanIf↔Can↔bus. Gói lớn (diag) đi nhánh CanTp↔Dcm. Mặt điều khiển ComM/CanSM/CanNm lo mode, bus-off, sleep/wakeup.

1. COM (Communication Services)

Vai trò: cầu nối giữa RTE (signal) và lớp PDU — đóng gói signal vào I-PDU lúc gửi, giải gói lúc nhận, kèm giám sát thời hạn.

1.1 Khái niệm cốt lõi

Signal ↔ I-PDU (packing)
Nhiều signal (vd tốc độ 16-bit, cờ 1-bit) được pack vào một I-PDU (gói dữ liệu, vd 8 byte) theo vị trí bit cấu hình; phía Rx unpack ngược lại cho RTE. COM lo bố trí bit, không lo bus.
Byte order & bit position
Mỗi signal có start bit, bit size, endianness (big/little). Sai endianness giữa hai ECU là lỗi tích hợp kinh điển (giá trị đảo byte) — thường lộ khi test integration.
Transmission mode
CYCLIC (gửi định kỳ), DIRECT/event (gửi khi signal đổi/được trigger), MIXED (cả hai). TMS (Transmission Mode Selector) đổi mode runtime theo điều kiện (vd chỉ gửi nhanh khi có sự kiện).
Minimum delay time
Khoảng tối thiểu giữa 2 lần gửi cùng I-PDU → chống “spam” bus khi signal đổi liên tục.
Deadline monitoring (Rx)
Nếu một I-PDU/signal không tới đúng hạn (timeout) → COM thay bằng init/replacement value & gọi notification → app biết mất gói (vd cảm biến mất tín hiệu). Đây là cơ chế phát hiện lỗi giao tiếp ở mức signal.
Update bit
Một bit kèm signal báo “signal này có dữ liệu mới trong PDU lần này không” → phía Rx phân biệt giá trị mới vs giá trị cũ lặp lại.
Signal gateway
COM (cùng PduR) có thể route signal giữa các bus mà không cần lên app (gateway tín hiệu).
MainFunction Tx/Rx
Com_MainFunctionTx xử lý gửi cyclic & minimum delay; Com_MainFunctionRx xử lý deadline monitoring. Com_IpduGroup bật/tắt nhóm PDU (vd tắt giao tiếp khi sleep).

API: Com_SendSignal/Com_ReceiveSignal/Com_TriggerIPDUSend/Com_MainFunctionTx/Rx/Com_IpduGroupControl. Bẫy: sai endianness/start-bit; thiếu update bit gây hiểu nhầm giá trị; deadline quá chặt/lỏng.

2. PduR (PDU Router)

Vai trò: định tuyến PDU giữa các module (COM, Dcm, CanIf, CanTp, IpduM) theo bảng routing tĩnh — “tổng đài” của stack.

Routing path table
Bảng tĩnh (cấu hình) ánh xạ nguồn PDU → đích PDU. PduR chỉ chuyển tiếp theo bảng, không hiểu nội dung. Có thể multicast (một PDU tới nhiều đích).
IF routing vs TP routing
IF (Interface) routing: PDU vừa một frame, chuyển một phát (COM↔CanIf). TP (Transport) routing: PDU lớn cần phân mảnh, đi qua CanTp (Dcm↔CanTp↔CanIf). PduR phân biệt hai loại.
Gateway
Route PDU bus ↔ bus (vd CAN1↔CAN2) không lên tới app — ECU gateway dùng nhiều; có thể gateway-on-the-fly (chuyển từng phần khi nhận).

API: PduR_ComTransmit/PduR_DcmTransmit/PduR_CanIfRxIndication/PduR_CanIfTxConfirmation. Bẫy: routing path cấu hình thiếu/sai đích.

3. CanIf (CAN Interface)

Vai trò: lớp ECU Abstraction giữa PduR/COM/CanTp/CanNm và CAN driver (MCAL) — che chi tiết controller, ánh xạ PDU↔mailbox HW.

L-PDU ↔ I-PDU + HRH/HTH
CanIf ánh xạ giữa I-PDU (lớp trên) và L-PDU (CAN frame có CAN ID + DLC). HRH (Hardware Receive Handle) & HTH (Hardware Transmit Handle) = tham chiếu tới mailbox/hardware object của controller cho Rx/Tx.
Controller mode
STARTED / STOPPED / SLEEP. CanIf đổi mode controller (qua Can driver) theo yêu cầu CanSM. STOPPED không tham gia bus.
PDU mode
ONLINE/OFFLINE (và OFFLINE_ACTIVE): kiểm soát có cho phép Tx/Rx PDU không — vd tắt Tx khi đang vào bus-off recovery.
Tx buffer
Khi mailbox HW bận, CanIf đệm PDU Tx (theo PDU hoặc theo độ ưu tiên) rồi gửi khi rảnh → tránh mất frame; quản lý thứ tự/ưu tiên.
Software filtering
Nếu HW không lọc đủ, CanIf lọc CAN ID ở phần mềm để chỉ nhận PDU quan tâm.

API: CanIf_Transmit/CanIf_RxIndication/CanIf_TxConfirmation/CanIf_SetControllerMode/CanIf_SetPduMode.

4. CanTp (Transport — ISO 15765-2)

Vai trò: truyền gói lớn hơn một CAN frame (CAN cổ điển ≤8 byte; CAN FD ≤64) bằng cách phân mảnh — nền cho UDS qua CAN.

CanTp (ISO-TP). SF cho gói nhỏ; gói lớn = FF → receiver gửi FC (CTS + block size + STmin) → sender gửi CF theo block, cách nhau STmin.
4 loại frame
SF (Single Frame): gói ≤7 byte (CAN cổ điển) trong một frame. FF (First Frame): frame đầu gói lớn, chứa tổng độ dài (12-bit, hoặc 32-bit escape cho gói rất lớn). CF (Consecutive Frame): các frame tiếp theo mang data, có sequence number. FC (Flow Control): receiver điều khiển sender.
Flow Status (FC)
CTS (Clear To Send — cho gửi tiếp), WAIT (chờ, receiver bận), OVFLW (overflow — buffer receiver không đủ, huỷ). Cơ chế back-pressure để receiver không bị tràn.
Block Size (BS)
Số CF receiver cho phép gửi trước khi cần một FC mới. BS=0 = gửi hết không cần FC giữa chừng. Điều tiết theo khả năng nhận.
STmin (Separation Time)
Khoảng cách tối thiểu giữa 2 CF mà receiver yêu cầu (vd 0–127 ms, hoặc 100–900 µs mã hoá riêng) → cho receiver kịp xử lý. Sender phải tôn trọng.
Timing N_As/N_Ar/N_Bs/N_Cr
Các timeout chuẩn ISO 15765-2: N_As/N_Ar (thời gian gửi một frame Tx/Rx), N_Bs (sender chờ FC), N_Cr (receiver chờ CF). Quá hạn → abort + báo lỗi.
Padding
Frame chưa đủ 8 (hoặc DLC cố định) được pad (vd 0xCC/0x00) — phải khớp giữa hai bên.

API: CanTp_Transmit/CanTp_RxIndication; CanTp_MainFunction. Dùng cho UDS (request/response >7 byte) — bài E & B4.

5. CanSM (CAN State Manager)

Vai trò: quản lý trạng thái giao tiếp của một network & xử lý bus-off recovery.

Communication state
FULL_COM (Tx+Rx bình thường), SILENT_COM (chỉ nghe, không gửi — chuẩn bị ngủ), NO_COM (ngắt giao tiếp/controller STOPPED). CanSM đổi state theo yêu cầu ComM.
Bus-off recovery
Khi controller vào bus-off (TEC>255), CanSM nhận thông báo → chờ một khoảng (cấu hình) rồi restart controller. Mục đích: tránh node lỗi liên tục restart phá bus; có thể giới hạn số lần recovery rồi escalate. (Cơ chế bus-off ở phần CAN, bài E & B: phục hồi sau 128×11 bit recessive.)
Phối hợp
CanSM điều phối CanIf (controller/PDU mode) + CanNm (sleep) + báo ComM. Là “bộ não trạng thái” của một network CAN.

API: CanSM_RequestComMode/CanSM_GetCurrentComMode/CanSM_ControllerBusOff.

6. CanNm (Network Management)

Vai trò: phối hợp sleep/wakeup toàn mạng — để cả mạng ngủ đồng bộ (tiết kiệm điện) & thức cùng nhau, bằng cách trao đổi NM-PDU.

CanNm states. Có yêu cầu → Repeat Message → Normal Operation; hết yêu cầu → Ready Sleep → Bus Sleep. Bất kỳ NM-PDU/NetworkRequest nào kéo cả mạng thức lại.
NM-PDU
Bản tin NM định kỳ mỗi node phát để báo “tôi còn cần mạng”. Còn ai phát/nhận NM-PDU → mạng giữ thức; im lặng đủ lâu → cả mạng đồng thuận ngủ.
4 trạng thái
Repeat Message (phát dồn NM-PDU để đồng bộ khi mới thức), Normal Operation (đang dùng mạng), Ready Sleep (không còn ai cần, chờ timeout), Bus Sleep (ngủ). Chuyển bằng CanNm_NetworkRequest/NetworkRelease & timeout.
Coordinator
Khi ECU nối nhiều mạng, NM coordinator đồng bộ để các mạng ngủ/thức nhất quán (không để một mạng ngủ trong khi mạng kia còn dùng gateway).

API: CanNm_NetworkRequest/NetworkRelease/PassiveStartUp.

7. ComM (Communication Manager)

Vai trò: gom yêu cầu “cần giao tiếp” từ nhiều user (app, Dcm, Nm) và quyết định mode cho từng channel, rồi điều phối CanSM/Nm.

User & mode
Mỗi user gọi ComM_RequestComMode. ComM lấy mức cao nhất trong các yêu cầu: FULL_COMMUNICATION (cần Tx+Rx), SILENT_COMMUNICATION (chỉ nghe), NO_COMMUNICATION (cho phép ngủ). Mạng chỉ ngủ khi không user nào còn cần.
Điều phối
ComM dịch mode thành lệnh cho CanSM (đổi communication state) & Nm (request/release network) — là “công tắc tổng” của giao tiếp một channel.
Channel
Quản lý theo từng communication channel (network); một ECU nhiều channel độc lập.

API: ComM_RequestComMode/ComM_GetCurrentComMode. Nhắc: SecOC (MAC+freshness, bài B), IpduM (multiplex nhiều PDU vào một), LdCom (large data, ít overhead) cũng trong nhóm communication.

8. Trước (~2020) → Nay

🌐 Communication stack: Ethernet, security, SDV
⏪ Trước (~2020)

CAN stack (CanIf/CanTp/CanSM/CanNm) là trung tâm; UDS-on-CAN.

⏩ Nay

Thêm stack Ethernet (EthIf/SoAd/SOME-IP/DoIP) song song; SecOC bắt buộc trên PDU nhạy; CAN FD/XL; UDS-on-IP (DoIP); PduR route đa-bus cho zonal/SDV.

Vì sao quan trọng: nói được “PduR là tổng đài route giữa CAN/Ethernet, CanTp cho diag-on-CAN còn DoIP cho diag-on-IP” cho thấy bạn hiểu kiến trúc mạng hiện đại.

9. Tự kiểm tra

Một signal đi từ app xuống bus qua những module nào? Định nghĩa▾

RTE → COM (pack signal↔I-PDU) → PduR (route) → CanIf (I-PDU↔L-PDU, HTH) → Can (MCAL, mailbox) → bus. Chiều Rx ngược lại. Gói lớn (diag) đi nhánh CanTp (segment) ↔ Dcm. Mặt điều khiển: ComM/CanSM/CanNm.

Đào tiếp
  • HRH/HTH là gì?
  • IF routing vs TP routing?
CanTp phân mảnh thế nào? Flow control, block size, STmin là gì? Áp dụng▾

Gói ≤7 byte = SF. Gói lớn: FF (có tổng độ dài) → receiver gửi FC (CTS/WAIT/OVFLW + block size BS + STmin) → sender gửi CF theo block, cách nhau ≥STmin. BS = số CF trước khi cần FC mới; STmin = khoảng tối thiểu giữa 2 CF. Timeout N_Bs/N_Cr bảo vệ. Dùng cho UDS.

Đào tiếp
  • OVFLW xảy ra khi nào?
  • BS=0 nghĩa là gì?
Bus-off recovery do ai xử lý? CanSM làm gì? Áp dụng▾

Controller vào bus-off (TEC>255) → báo CanSM → CanSM chờ một khoảng rồi restart controller (qua CanIf), có thể giới hạn số lần rồi escalate. Mục đích: tránh node lỗi liên tục phá bus. CanSM cũng quản lý FULL/SILENT/NO_COM theo yêu cầu ComM.

Đào tiếp
  • Vì sao cần delay trước restart?
  • SILENT_COM dùng khi nào?
Cả mạng ngủ/thức đồng bộ nhờ gì? ComM & CanNm phối hợp ra sao? Áp dụng▾

ComM gom yêu cầu user → nếu không ai cần FULL/SILENT thì cho NO_COM. CanNm trao đổi NM-PDU: còn ai phát/nhận → mạng thức; im đủ lâu (Ready Sleep timeout) → Bus Sleep. Bất kỳ NetworkRequest/NM-PDU nào kéo cả mạng thức lại. Coordinator đồng bộ nhiều mạng.

Đào tiếp
  • 4 trạng thái CanNm?
  • Repeat Message để làm gì?
Một signal nhận sai giá trị — bạn debug từ đâu? Kinh nghiệm▾

Soi từ dưới lên: bus (CANoe/oscilloscope) → CAN ID/DLC đúng PDU? → CanIf mapping (HRH) → PduR routing → COM signal packing (start bit/bit size/endianness — lỗi kinh điển) → update bit/deadline monitoring (có thay bằng replacement value không). Dùng TRACE32 soi buffer PDU, đối chiếu ARXML.

Đào tiếp
  • Deadline monitoring ảnh hưởng giá trị thế nào?

10. Cheat-sheet 1 trang

Luồng

  • COM↔PduR↔CanIf↔Can↔bus
  • Diag: Dcm↔CanTp↔PduR↔CanIf
  • Control: ComM/CanSM/CanNm

COM

  • Signal↔I-PDU (start bit/size/endianness)
  • Tx mode: cyclic/direct/mixed + TMS
  • Deadline monitoring → replacement value
  • Update bit · MainFunctionTx/Rx

PduR / CanIf

  • PduR: routing table, gateway, IF vs TP
  • CanIf: L-PDU↔I-PDU, HRH/HTH
  • Controller/PDU mode, Tx buffer
  • Software filtering

CanTp (ISO 15765-2)

  • SF / FF / CF / FC
  • FC: CTS/WAIT/OVFLW
  • Block size BS · STmin
  • N_Bs/N_Cr timeout · cho UDS

CanSM / CanNm

  • CanSM: FULL/SILENT/NO_COM + bus-off recovery
  • CanNm: NM-PDU đồng bộ ngủ/thức
  • States: RepeatMsg/Normal/ReadySleep/BusSleep
  • Coordinator đa mạng

ComM / nay

  • ComM: FULL/SILENT/NO_COMMUNICATION
  • Gom user → CanSM/Nm
  • SecOC/IpduM/LdCom
  • Nay: Ethernet/SOME-IP/DoIP song song
