B4 Core AUTOSAR — Module (đào sâu)

Diagnostics — Dcm / Dem / UDS / DTC

Chẩn đoán theo UDS (ISO 14229): Dcm (dispatcher: session, security, route service) và Dem (quản lý event lỗi & DTC: debounce, aging, freeze frame). Cộng FiM (vô hiệu hoá chức năng khi lỗi). Trọng tâm: DTC status byte & vòng đời DTC.

Độ ưu tiên: 🟠 Core Gắn: UDS/SID (bài E), CanTp (B3) Tổng quan: bài B
📌

Nguồn: Dcm/Dem đối chiếu AUTOSAR Classic SWS; dịch vụ & DTC status byte theo ISO 14229 (UDS) — xem cuối bài. Danh sách SID/NRC đầy đủ ở bài E.

Luồng chẩn đoán. Tester → transport (CanTp/DoIP) → Dcm (DSL kiểm session/security/timing → DSD route SID → DSP xử lý). DSP gọi app (đọc/ghi DID, routine) hoặc Dem (đọc DTC 0x19).

1. Dcm (Diagnostic Communication Manager)

Vai trò: dispatcher UDS — nhận request từ tester, kiểm điều kiện (session/security/timing), route tới đúng service handler, trả response. Gồm 3 sub-module.

1.1 Khái niệm cốt lõi

DSL / DSD / DSP
DSL (Diagnostic Session Layer): quản lý session, security, protocol, timing & TesterPresent. DSD (Diagnostic Service Dispatcher): kiểm SID có được phép ở session/security hiện tại không rồi route. DSP (Diagnostic Service Processing): xử lý từng service (đọc/ghi DID, routine, đọc DTC…).
Diagnostic session (0x10)
Server luôn ở một session: default (01), programming (02 — để flash/lập trình), extended (03 — mở thêm service). Nhiều service chỉ chạy ở extended/programming. Hết hoạt động → tự về default.
Security access (0x27)
Mở khoá service nhạy bằng seed → key: tester xin seed (27 01) → ECU trả seed (67 01) → tester tính key=f(seed) (thuật toán bí mật OEM) → gửi key (27 02) → đúng thì mở. Chống brute-force bằng attempt counter (sai nhiều lần → khoá) & delay timer (phải chờ sau số lần sai, hoặc sau power-on).
P2 / P2* timing & response pending
P2 = thời gian tối đa ECU phải trả response sau request. Nếu cần xử lý lâu hơn, ECU gửi negative response 0x78 (responsePending) để gia hạn tới P2* (lớn hơn) — giữ tester chờ thay vì timeout. Cơ chế quan trọng cho routine/flash chậm.
Service table
Bảng cấu hình: mỗi SID + sub-function ↔ điều kiện (session/security cho phép) + handler. Dcm dùng bảng này để DSD kiểm & route; service không hỗ trợ → NRC 0x11.
TesterPresent (0x3E) & S3 timeout
Tester gửi 3E định kỳ để giữ session khác default sống; nếu im lặng quá S3 (~5 s) → ECU tự về default session (an toàn).

1.2 Dịch vụ UDS chính (Dcm route)

SIDDịch vụÝ nghĩa
0x10SessionControlĐổi session (default/programming/extended)
0x27SecurityAccessSeed→key mở khoá
0x22 / 0x2ERead/WriteDataByIdentifierĐọc/ghi theo DID
0x31RoutineControlstart/stop/requestResults routine
0x19ReadDTCInformationĐọc DTC (từ Dem)
0x14 / 0x85Clear / ControlDTCSettingXoá DTC / bật-tắt ghi DTC
0x34/36/37Request/Transfer/Exit DownloadNạp firmware (programming)
0x3ETesterPresentGiữ session sống

Positive response = SID|0x40; negative = 7F <SID> <NRC>. Danh sách SID/NRC đầy đủ ở bài E. API Dcm: Dcm_GetSesCtrlType, Dcm_GetSecurityLevel; handler do app/RTE cung cấp. Bẫy: service ở sai session/security → NRC 0x7F (0x33 securityAccessDenied, 0x22 conditionsNotCorrect); quên 0x78 cho routine chậm → tester timeout.

2. Dem (Diagnostic Event Manager)

Vai trò: nhận event lỗi từ BSW/SWC (monitor), quyết định khi nào thành DTC (confirmed), lưu vào event memory kèm dữ liệu chụp. Dcm đọc DTC từ Dem khi tester yêu cầu (0x19).

DTC status byte. 8 bit mô tả trạng thái mỗi DTC (testFailed, pending, confirmed, …, warningIndicator). Tester đọc bằng 0x19; mask khả dụng qua sub-function 0x01.

2.1 Khái niệm cốt lõi

Event ↔ DTC
Một monitor (BSW/SWC) báo trạng thái event (PASSED/FAILED) qua Dem_SetEventStatus. Dem ánh xạ event → DTC (Diagnostic Trouble Code, vd P0123) hiển thị cho tester. Nhiều event có thể map một DTC.
DTC status byte (8 bit)
Mỗi DTC có byte trạng thái (xem sơ đồ): testFailed, testFailedThisOperationCycle, pendingDTC, confirmedDTC, testNotCompletedSinceLastClear, testFailedSinceLastClear, testNotCompletedThisOperationCycle, warningIndicatorRequested (bật đèn MIL). Tester lọc DTC theo các bit này.
Debouncing
Lỗi phải “đủ độ tin” mới chuyển trạng thái — chống báo nhầm do nhiễu thoáng qua. Counter-based: mỗi lần FAILED +N, PASSED −M; vượt ngưỡng → failed. Time-based: phải FAILED liên tục trong một khoảng thời gian.
Operation cycle & confirmation
Operation cycle (vd một chu kỳ lái/ignition cycle) là đơn vị đếm. DTC chỉ confirmed sau khi failed đủ số operation cycle (confirmation threshold) → tránh confirm vội.
Aging & aged
Khi DTC không còn failed qua đủ số operation cycle “tốt” liên tiếp → healing; tiếp tục → aged → bị xoá khỏi memory. Tự dọn DTC cũ không còn lỗi.
Event memory
Primary (chính, cho emission/OBD) & secondary (phụ). Khi đầy → áp displacement (đẩy DTC ưu tiên thấp ra cho DTC quan trọng hơn).
Freeze frame / snapshot & extended data
Khi DTC xảy ra, Dem chụp điều kiện môi trường tại thời điểm lỗi (snapshot/freeze frame: tốc độ, nhiệt độ, RPM…) & extended data (số lần lỗi, aging counter…) → tester đọc để chẩn đoán nguyên nhân.
Enable conditions
DTC chỉ được đánh giá khi điều kiện cho phép (vd điện áp/nhiệt độ trong dải) — tránh báo lỗi giả khi điều kiện bất thường. Dùng cả ControlDTCSetting (0x85) để tạm tắt ghi DTC khi đang test.
Vòng đời DTC. FAILED (debounce) → pending → confirmed (lưu + freeze frame + đèn) → khi PASSED đủ lâu → healing → aged (xoá). Đây là cơ chế tránh báo nhầm & tự dọn.

API Dem: Dem_SetEventStatus, Dem_GetEventStatus, Dem_GetDTCStatusAvailabilityMask, Dem_GetDTCOfEvent. Cấu hình: DemEventParameter (event↔DTC, debounce algorithm, operation cycle, confirmation threshold), DemDTCAttributes (memory, snapshot, extended data). Bẫy: debounce sai (báo nhầm/bỏ sót); confirmation threshold không khớp OEM; freeze frame thiếu trường tester cần.

3. FiM (Function Inhibition Manager)

Vai trò: vô hiệu hoá (inhibit) một chức năng phần mềm khi có event lỗi liên quan — để chức năng không chạy với dữ liệu/điều kiện không tin cậy.

Function inhibition
Một FID (Function Identifier) gắn với các event của Dem qua điều kiện (permission). Khi event lỗi → FiM cập nhật permission → function hỏi FiM_GetFunctionPermission trước khi chạy; không cho phép thì bỏ qua (vd tắt một tính năng điều khiển khi cảm biến lỗi).
Quan hệ Dem ↔ FiM
Dem báo trạng thái event → FiM dịch thành permission. Đây là cách lỗi chẩn đoán tác động tới hành vi chức năng một cách có kiểm soát (degradation/limp-home).

4. Trước (~2020) → Nay

🩺 Diagnostics: DoIP, OTA, security
⏪ Trước (~2020)

UDS-on-CAN (CanTp); Dcm/Dem theo OBD/emission là chính.

⏩ Nay

UDS-on-IP (DoIP) qua Ethernet (chẩn đoán & flash OTA nhanh); security access mạnh hơn (gắn 21434, có thể certificate-based thay seed-key cố định); diagnostics phối hợp UCM cho cập nhật phần mềm.

Vì sao quan trọng: nói được “UDS chạy trên cả CanTp lẫn DoIP, security access đang chuyển sang cơ chế mạnh hơn theo ISO 21434” cho thấy bạn cập nhật.

5. Tự kiểm tra

Dcm gồm những sub-module nào? Một request UDS được xử lý ra sao? Định nghĩa▾

DSL (session/security/timing/TesterPresent) → DSD (kiểm SID có được phép ở session/security hiện tại rồi route) → DSP (xử lý: đọc/ghi DID, routine, hoặc gọi Dem đọc DTC). Trả positive (SID|0x40) hoặc negative (7F SID NRC). Nếu xử lý lâu → 0x78 responsePending (gia hạn P2→P2*).

Đào tiếp
  • P2 vs P2* & 0x78 để làm gì?
  • S3 timeout của TesterPresent?
Security access 0x27 chống brute-force thế nào? Áp dụng▾

Seed→key (key=f(seed) bí mật OEM). Chống brute-force bằng attempt counter (sai N lần → khoá) + delay timer (phải chờ sau số lần sai hoặc sau power-on mới được thử lại). Sai key → NRC 0x35 (invalidKey); vượt số lần → 0x36 (exceedNumberOfAttempts); đang khoá → 0x37 (requiredTimeDelayNotExpired).

Đào tiếp
  • Vì sao tách requestSeed/sendKey thành 2 sub-function?
DTC status byte gồm gì? Debounce & aging để làm gì? Áp dụng▾

8 bit: testFailed, testFailedThisOpCycle, pending, confirmed, testNotCompletedSinceClear, testFailedSinceClear, testNotCompletedThisCycle, warningIndicator (MIL). Debounce (counter/time-based) chống báo nhầm do nhiễu — lỗi phải đủ tin mới đổi trạng thái. Aging tự xoá DTC khi hết lỗi qua đủ operation cycle tốt.

Đào tiếp
  • Confirmed cần điều kiện gì? (đủ operation cycle)
  • Freeze frame chứa gì?
Dcm khác Dem thế nào? FiM làm gì? Định nghĩa▾

Dcm = giao tiếp chẩn đoán (dispatch UDS: session/security/route). Dem = quản lý event lỗi & DTC (debounce/aging/freeze frame/event memory). Dcm đọc DTC từ Dem khi tester gửi 0x19. FiM vô hiệu hoá chức năng khi có event lỗi (degradation), qua FID + permission từ Dem.

Đào tiếp
  • 0x14 ClearDTC xoá gì? (DTC + freeze frame + extended data)

6. Cheat-sheet 1 trang

Dcm

  • DSL (session/security/timing) → DSD (route) → DSP (xử lý)
  • Session: default/programming/extended
  • 0x27 seed→key + attempt/delay
  • 0x78 responsePending (P2→P2*)

UDS SID

  • 10 session · 27 security · 22/2E DID
  • 31 routine · 19 DTC · 14 clear · 85 control
  • 34/36/37 download · 3E present
  • Pos = SID|0x40 · Neg = 7F SID NRC

Dem — DTC

  • Event ↔ DTC (Dem_SetEventStatus)
  • Status byte 8-bit (confirmed, warnInd…)
  • Debounce counter/time-based
  • Confirmed sau đủ operation cycle

Dem — lưu trữ

  • Event memory primary/secondary + displacement
  • Freeze frame/snapshot + extended data
  • Aging → aged (tự xoá)
  • Enable conditions + 0x85

FiM

  • FID + permission
  • Inhibit function khi event lỗi
  • Dem → FiM → degradation/limp-home

Nay

  • UDS-on-IP (DoIP) qua Ethernet
  • Security access mạnh hơn (21434)
  • Diag phối hợp UCM/OTA
