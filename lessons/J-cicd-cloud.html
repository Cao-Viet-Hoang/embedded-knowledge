1. CI/CD — khái niệm nền

CI
Continuous Integration — tự động build + test mỗi khi push code, bắt lỗi sớm.
CD
Continuous Delivery (sẵn sàng deploy, có cổng duyệt) / Deployment (tự động ra production).
Pipeline
Chuỗi bước tự động: build → test → package → publish/deploy.
🗣️

Kể được: “Tôi tích hợp build/package/test bằng Azure Pipelines + Conan cho SENT automation — biến chu kỳ test thủ công thành pipeline chạy tự động, tái lập được, chạy song song trên nhiều agent.”

2. Azure Pipelines

CI/CD của Azure DevOps, định nghĩa bằng YAML. Phân cấp Pipeline → Stage → Job → Step; job chạy trên Agent, sinh Artifact.

Phân cấp Azure Pipelines. Stage chạy tuần tự theo dependsOn (mặc định theo thứ tự khai báo); job trong stage chạy song song trừ khi có dependsOn; mỗi agent chạy 1 job tại một thời điểm. Artifact truyền sản phẩm giữa stage.
trigger: [ main ]                 # chay khi push vao main
pool: { vmImage: ubuntu-latest }  # agent

stages:
- stage: Build
  jobs:
  - job: build_test
    steps:
    - script: conan install . --build=missing   # lay dependency
    - script: cmake --build build               # build
    - script: ctest --output-on-failure          # test
    - publish: build/artifacts                    # luu artifact
      artifact: app
- stage: Deploy
  dependsOn: Build
  jobs:
  - deployment: deploy_app
    environment: production

3. Conan — package manager C/C++

Quản lý thư viện & dependency C/C++ theo version & cấu hình build (OS/arch/compiler), build tái lập. Conan quản lý binary cho từng configuration; thiếu binary thì build từ source on-demand. Đây là chìa khoá để pipeline SENT không “flaky”.

Recipe (conanfile)
Mô tả package: dependency, cách build, options.
Profile
Chứa settings/options/env/build_requires — cố định OS, arch, build_type, compiler (vd cross-compile cho target). Đổi target chỉ bằng đổi --profile.
Lockfile
Khoá chính xác version dependency (conan.lock) → reproducible build.
Remote
Kho package (vd JFrog Artifactory) để chia sẻ binary đã build.
💡

Vì sao quan trọng cho bài D: SENT nhạy môi trường/toolchain. Conan cố định dependency + profile → “chạy trên CI giống hệt máy local”, loại bỏ lỗi “máy tôi thì chạy”.

4. Docker — container hoá

Đóng gói app + dependency vào image bất biến (xếp chồng nhiều layer), chạy thành container cô lập. Mỗi lệnh Dockerfile sửa filesystem (RUN/COPY/ADD) tạo một layer mới; layer được cache & chia sẻ.

Image layers. Layer dưới (base, dependency) read-only & được cache/chia sẻ; container thêm một layer R/W mỏng ở trên (đổi trong container không sửa image). Union filesystem (Overlay2) gộp các layer thành một view.
FROM python:3.12-slim          # base layer
WORKDIR /app
COPY requirements.txt .         # layer rieng -> tan dung cache
RUN pip install -r requirements.txt
COPY . .                        # source thay doi nhieu -> de cuoi
CMD ["python", "app.py"]
📦

Mẹo layer caching: đặt phần ít đổi (cài dependency) trước phần hay đổi (copy source) → build lại nhanh. Container vs VM: container chia sẻ kernel host → nhẹ & nhanh hơn VM (mỗi VM có OS riêng).

5. Kubernetes (tổng quan)

Điều phối container ở quy mô lớn: tự scale, self-heal, rolling update. Các đối tượng cốt lõi:

Kubernetes. Ingress → Service (load-balance) → Pods do Deployment/ReplicaSet quản lý. ConfigMap tách cấu hình khỏi image (không bảo mật — dữ liệu nhạy dùng Secret). Đổi ConfigMap mount dạng volume tự sync, nhưng env var không đổi tới khi pod restart.
Đối tượngVai trò
PodĐơn vị chạy nhỏ nhất (1+ container chia sẻ network/storage)
DeploymentQuản lý số bản sao Pod (qua ReplicaSet), rolling update, rollback
ServiceĐiểm truy cập ổn định (load-balance) tới tập Pod (ClusterIP/NodePort/LoadBalancer)
ConfigMap / SecretTách cấu hình/bí mật khỏi image (ConfigMap không mã hoá; Secret cho dữ liệu nhạy)
IngressĐịnh tuyến HTTP/HTTPS từ ngoài vào Service
⚖️

Pod vs Container: container là process đóng gói; Pod là “vỏ” K8s bọc một/vài container cùng vòng đời, chia sẻ IP/volume. K8s scale theo Pod, không theo container lẻ. Lưu ý: sửa ConfigMap không tự restart pod đang chạy.

6. Terraform — Infrastructure as Code

Khai báo hạ tầng bằng code (HCL), Terraform tạo/sửa/xoá tài nguyên cho khớp. Declarative: mô tả “trạng thái mong muốn”, Terraform tự tính các bước. Hỗ trợ Azure/AWS/GCP và 100+ provider.

Terraform workflow. write → plan → apply. State (.tfstate) ánh xạ HCL ↔ tài nguyên thật để tính diff — chứa dữ liệu nhạy nên phải lưu remote, khoá, mã hoá.
resource "azurerm_resource_group" "rg" {
  name     = "rg-ai-platform"
  location = "southeastasia"
}
resource "azurerm_app_service" "app" {
  name                = "ai-internal-app"
  resource_group_name = azurerm_resource_group.rg.name
}
Resource
Một tài nguyên cloud (VM, App Service, DNS…).
Module
Nhóm resource tái sử dụng, tham số hoá (DRY — tạo nhiều instance từ một module).
State
File ánh xạ HCL ↔ ID tài nguyên thật → so để ra plan. Lưu remote, khoá, mã hoá (chứa secret).
plan / apply
plan xem trước (+/~/-); apply thực thi theo đúng thứ tự phụ thuộc.

9. Jenkins & GitLab CI/CD

Cùng ý tưởng pipeline-as-code như Azure, chỉ khác cú pháp & hệ sinh thái. Khái niệm chung cần nắm: runner/agent chạy job; stage/job tổ chức các bước; artifact lưu & truyền sản phẩm; cache tái dùng dependency; trigger (webhook / SCM poll / schedule) khởi động pipeline; quality gate chặn merge khi test/coverage/phân tích không đạt.

⚖️

Azure ↔ Jenkins ↔ GitLab: giống concept, khác cú pháp. Đều là runner + stage/job + artifact + trigger + quality gate. Học một cái, cái còn lại chỉ là ánh xạ từ khoá.

Jenkins

Controller + Agent/Node
Controller điều phối, job thực thi trên agent/node; dùng label để chọn máy phù hợp (OS, toolchain).
Pipeline (Jenkinsfile)
Pipeline-as-code trong repo. Declarative (pipeline{ stages{} }, dễ đọc) vs scripted (Groovy tự do). Cấu trúc stages{} → steps.
Plugins & Blue Ocean
Mở rộng gần như mọi thứ (git, warnings-ng cho static analysis, junit…). Blue Ocean = UI trực quan cho pipeline.
Artifacts & credentials
archiveArtifacts lưu sản phẩm; credentials store giữ secret (token, khoá) tách khỏi code.
Trigger & matrix
Poll SCM / webhook (GitHub, GitLab) / schedule (cron). Matrix build chạy tổ hợp axis (compiler × OS).

GitLab CI

.gitlab-ci.yml
File pipeline ở gốc repo: khai báo stages & các job.
GitLab Runner
Tiến trình chạy job; executor shell hoặc docker (mỗi job một container sạch).
artifacts / cache
artifacts lưu & truyền output giữa stage; cache tái dùng dependency giữa các lần chạy.
needs: (DAG)
Chạy job theo đồ thị phụ thuộc, không phải chờ hết cả stage → pipeline nhanh hơn.
rules / only-except
Điều kiện chạy job (theo branch, MR, biến). environments quản lý deploy; container registry tích hợp sẵn.

Hai pipeline tương đương cho build C/C++ dưới đây: cấu hình → build → chạy ctest + sanitizer & static analysis (bài C), dùng toolchain dựng ở bài M. Không đạt gate thì chặn MR.

stages: [build, test, analyze]

build:
  stage: build
  script:
    - cmake -S . -B build -DCMAKE_BUILD_TYPE=Debug
    - cmake --build build -j
  artifacts:
    paths: [build/]                 # truyen sang stage sau

test:
  stage: test
  needs: [build]                    # DAG: chay ngay khi build xong
  script:
    - ctest --test-dir build --output-on-failure   # xem bai C
    - ./build/tests_asan            # binary build kem -fsanitize=address

analyze:
  stage: analyze
  script:
    - clang-tidy -p build src/*.c   # static analysis = quality gate
  allow_failure: false              # khong dat -> chan MR
pipeline {
  agent { label 'linux-cpp' }        // toolchain o bai M
  stages {
    stage('Build') {
      steps { sh 'cmake -S . -B build && cmake --build build -j' }
    }
    stage('Test') {                  // ctest + sanitizer, bai C
      steps { sh 'ctest --test-dir build --output-on-failure' }
    }
    stage('Analyze') {               // static analysis gate
      steps { sh 'clang-tidy -p build src/*.c' }
    }
  }
  post { always { archiveArtifacts artifacts: 'build/**', fingerprint: true } }
}
🌿

Git workflow: feature branch → mở MR/PR → pipeline chạy trên MR làm quality gate → merge vào protected branch → gắn tag/release. Protected branch chặn push trực tiếp, buộc qua review + pipeline xanh.

10. Python cho Build & Test Automation

Python là lớp orchestrate/glue phổ biến trong CI: nhanh viết, thư viện phong phú, chạy cross-platform — bổ trợ chứ không thay code sản phẩm C.

Gọi build
subprocess gọi cmake/conan, kiểm tra returncode, gom log.
Sinh/parse cấu hình
Đọc ARXML bằng lxml, sinh header/param, biến mô hình thành cấu hình build.
Chạy & tổng hợp test
pytest xuất JUnit XML để CI hiển thị kết quả & xu hướng.
Điều khiển vECU/bus
Lái CANoe qua COM API, hoặc gửi/nhận bus bằng python-can — glue kiểm thử trong CI.
🐍

pytest cho SIL/HIL: fixture (dựng/dọn môi trường), parametrize + data-driven (một test, nhiều bộ dữ liệu), marker (gắn nhãn/lọc, vd @pytest.mark.hil), report JUnit cho CI.

import subprocess, sys

# goi cmake build, kiem tra returncode -> bao CI dat/that bai
r = subprocess.run(["cmake", "--build", "build", "-j"],
                   capture_output=True, text=True)
if r.returncode != 0:
    print(r.stderr, file=sys.stderr)
    sys.exit(r.returncode)          # returncode != 0 -> CI FAIL
print("build OK")
import can

# minh hoa automation kiem thu bus: gui & nhan 1 CAN frame
bus = can.Bus(interface="virtual", channel="A")   # hoac vector/socketcan
msg = can.Message(arbitration_id=0x123,
                  data=[0x11, 0x22, 0x33], is_extended_id=False)
bus.send(msg)                       # gui 1 frame
rx = bus.recv(timeout=1.0)          # nhan (None neu timeout)
print(rx.arbitration_id, list(rx.data))
💡

Vì sao Python phổ biến ở khâu automation: viết nhanh, kho thư viện lớn (lxml, pytest, python-can, requests), chạy cross-platform — lý tưởng làm “glue” nối build/test/bus/CI. Vẫn giữ code sản phẩm nhúng bằng C; Python chỉ điều phối & kiểm thử, không thay thế.

11. Tự kiểm tra

Container khác VM thế nào? Định nghĩa▾

Container chia sẻ kernel host, chỉ cô lập process/filesystem/network → nhẹ, khởi động nhanh, mật độ cao. VM ảo hoá cả phần cứng, mỗi VM có OS riêng → nặng hơn nhưng cách ly mạnh hơn.

Interviewer đào tiếp
  • Image layer là gì, vì sao cần? (cache + chia sẻ + transfer nhanh)
Vì sao Conan giúp pipeline ổn định? Áp dụng▾

Cố định version dependency + profile toolchain (lockfile) → mọi máy/CI build với cùng đầu vào, loại bỏ khác biệt môi trường gây “flaky”/“máy tôi thì chạy”. Thiếu binary thì build từ source on-demand theo đúng profile.

Interviewer đào tiếp
  • Profile chứa gì? (OS/arch/build_type/compiler/options/env)
Terraform state để làm gì? Vì sao phải cẩn thận? Áp dụng▾

State ánh xạ HCL ↔ ID tài nguyên thật để so với thực tế & mong muốn → ra plan. Phải lưu remote + khoá + mã hoá vì state có thể chứa secret (mật khẩu DB…) và nhiều người dùng chung dễ ghi đè nhau.

Interviewer đào tiếp
  • plan vs apply khác gì? Declarative nghĩa là gì?
Phân biệt Stage / Job / Step; agent chạy mấy job cùng lúc? Định nghĩa▾

Stage = giai đoạn lớn (Build/Deploy), tuần tự theo dependsOn; Job = tập step chạy trên một agent (job song song trừ khi có dependsOn); Step = một lệnh/task. Mỗi agent chạy 1 job tại một thời điểm → muốn song song cần nhiều agent. Artifact truyền sản phẩm giữa stage.

Interviewer đào tiếp
  • Microsoft-hosted vs self-hosted agent?
Tại sao đặt cài dependency trước COPY source trong Dockerfile? Áp dụng▾

Layer caching: dependency ít đổi → layer dưới, được cache; source hay đổi → layer trên. Đổi một layer làm invalid cache của layer đó & tất cả layer phía trên, nên để phần ít đổi xuống dưới → khi chỉ sửa code, build nhanh hơn nhiều.

Interviewer đào tiếp
  • ConfigMap khác Secret thế nào? Sửa ConfigMap có restart pod không?
Jenkins vs GitLab CI vs Azure Pipelines khác/giống gì? Áp dụng▾

Giống concept: đều là pipeline-as-code với runner/agent + stage/job + artifact + cache + trigger (webhook/poll/schedule) + quality gate. Khác cú pháp & nơi định nghĩa: Azure dùng azure-pipelines.yml (Pipeline→Stage→Job→Step, agent MS/self-hosted); Jenkins dùng Jenkinsfile Groovy (declarative/scripted, controller + agent theo label, giàu plugin); GitLab dùng .gitlab-ci.yml (stages+jobs, GitLab Runner shell/docker, needs: chạy theo DAG). Học một cái, còn lại chỉ là ánh xạ từ khoá.

Interviewer đào tiếp
  • Declarative vs scripted Jenkinsfile? needs: trong GitLab để làm gì?
Python dùng vào đâu trong quy trình build/test? Áp dụng▾

Làm lớp orchestrate/glue: subprocess gọi cmake/conan & kiểm returncode; đọc/parse ARXML (lxml) sinh cấu hình; chạy pytest xuất JUnit XML cho CI; điều khiển vECU/CANoe (COM API) hoặc bus qua python-can. Ưu điểm: viết nhanh, nhiều thư viện, cross-platform — nhưng chỉ bổ trợ, không thay code sản phẩm nhúng bằng C.

Interviewer đào tiếp
  • pytest fixture/parametrize/marker khác nhau ra sao? Vì sao xuất JUnit XML?
