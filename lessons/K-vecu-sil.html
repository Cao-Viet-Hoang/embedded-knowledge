Virtual ECU (vECU) · MIL/SIL/PIL/HIL · Vector SIL Kit

Mô hình hoá phần mềm ECU chạy trên PC host để shift-left: test sớm, song song, tự động, CI-friendly mà không cần phần cứng thật. 1. vECU là gì & vì sao cần

Định nghĩa: Virtual ECU (vECU) là một mô hình phần mềm của ECU — toàn bộ hoặc một phần code nhúng (ASW/BSW/firmware) được biên dịch & chạy trên PC host (x86/Linux/Windows) thay cho target vi điều khiển thật. Nó cho phép chạy chức năng ECU trong môi trường mô phỏng, ghép với các model khác (plant, ECU khác) mà không cần phần cứng.

Shift-left
Kéo hoạt động test/validate về sớm trong vòng đời phát triển. Thay vì đợi có board/HIL, kỹ sư test ngay trên PC lúc code còn trên bàn → phát hiện lỗi sớm, rẻ hơn nhiều.
Test sớm · song song · tự động
Nhiều kỹ sư chạy vECU song song trên máy riêng (không tranh nhau một bench HIL khan hiếm); test tự động hoá chạy hàng loạt (hàng nghìn case qua đêm); mở rộng scale-out trên cloud/CI.
CI-friendly
vECU là một tiến trình phần mềm → nhét thẳng vào pipeline CI/CD (bài J): mỗi commit build + chạy regression test trên vECU, không cần lab. Đây là mảnh ghép cốt lõi của DevOps ô tô.
Độc lập phần cứng khan hiếm
Prototype/board thường thiếu, đắt, tới muộn. vECU gỡ nút cổ chai đó: bắt đầu tích hợp & test trước khi silicon sẵn sàng.
Bối cảnh SDV & virtualization
Software-Defined Vehicle đẩy giá trị về phần mềm, cập nhật liên tục (OTA), kiến trúc zonal/HPC. Mô phỏng & ảo hoá ECU là nền để phát triển/kiểm thử phần mềm nhanh, tách khỏi chu kỳ phần cứng.
🔑

PoC (Proof of Concept): chứng minh tính khả thi của một ý tưởng/kiến trúc ở quy mô nhỏ trước khi đầu tư lớn. Trong JD, dựng vECU thường ở giai đoạn PoC: chứng minh có thể chạy phần mềm ECU trên host + ghép vào chuỗi mô phỏng, rồi mới scale-up thành hạ tầng test đầy đủ.

2. Các cấp độ vECU (L1–L4)

Vai trò: vECU không phải "một loại" — có nhiều cấp độ trưởng thành tuỳ bao nhiêu tầng phần mềm được đưa vào. Phân loại phổ biến theo prostep iVIP SmartSE chia L1–L4: càng lên cao càng trung thực (fidelity) với target thật nhưng càng chậm & khó dựng.

L1 — chỉ ASW / thuật toán
Chỉ Application Software (thuật toán điều khiển), thường là code sinh từ model (Simulink/TargetLink). Không có BSW/RTE. Dùng cho MIL/SIL sớm — kiểm chứng thuật toán, độc lập kiến trúc AUTOSAR. Nhanh nhất, trung thực thấp nhất.
L2 — ASW + RTE + một phần BSW
Thêm RTE & một phần BSW (thường là stub/mock). Giao tiếp ở mức tín hiệu (signal) chứ chưa phải bit trên bus. Kiểm thử tích hợp SWC↔RTE, hành vi cấu hình. Chưa có driver thật.
L3 — full AUTOSAR stack (host-compiled)
Toàn bộ stack AUTOSAR (ASW+RTE+BSW) biên dịch cho host. Lớp MCAL phụ thuộc phần cứng được thay bằng "virtual MCAL" / HAL ảo trỏ tới mô hình HW ảo hoặc bus ảo. Giao tiếp ở mức PDU/bus (CAN/LIN/Eth ảo). Trung thực cao về mặt phần mềm, nhưng vẫn chạy mã host, không chạy firmware nhị phân của target.
L4 — firmware nhị phân + ISS
Chạy chính binary firmware (đã build cho target) trên Instruction-Set Simulator mô phỏng vi điều khiển (vd QEMU, Synopsys Silver, Vector vVIRTUALtarget). Đây là "virtual target" — trung thực nhất, gần HIL nhất (mô phỏng cả timing/thanh ghi/ngắt ở mức lệnh), nhưng chậm & nặng nhất.

3. Kiến trúc vECU

Vai trò: hiểu tầng nào giữ nguyên, tầng nào bị thay. Điểm mấu chốt: MCAL thật (driver phần cứng) được thay bằng lớp ảo, phía trên (RTE/BSW/ASW) giữ nguyên như trên target → chạy đúng logic phần mềm sản phẩm mà không cần chip.

Kiến trúc vECU. App→RTE→BSW giữ nguyên; Virtual MCAL/HAL thay driver thật, nối qua bus abstraction tới co-simulation bus (CAN/LIN/Eth ảo) để ghép các vECU/model khác + plant model. Một scheduler ảo cấp OS tick & điều phối thời gian mô phỏng.
MCAL thật → lớp ảo
Trên target, MCAL truy cập thanh ghi phần cứng thật. Trên host không có phần cứng đó → thay bằng virtual MCAL / HAL trỏ tới mô hình HW ảo hoặc bus ảo. Ví dụ: gọi "gửi CAN frame" không đẩy ra transceiver mà đẩy vào bus mô phỏng.
Simulated time vs wall-clock
Simulated (virtual) time là "thời gian trong mô phỏng" do scheduler ảo điều khiển — có thể chạy nhanh hơn (faster-than-real-time) hoặc chậm hơn wall-clock (đồng hồ tường thật). Tách biệt hai đồng hồ này là chìa khoá cho determinism (mục 6).
Scheduler ảo tạo OS tick
Trên target, OS tick sinh từ timer phần cứng. Trên host, một scheduler ảo phát tick & điều phối các MainFunction/Runnable theo simulated time → tái tạo hành vi lập lịch của AUTOSAR OS (bài B5) mà không cần HW timer.
Co-simulation
Ghép nhiều đơn vị mô phỏng (nhiều vECU + plant model) chạy cùng nhau, trao đổi dữ liệu & đồng bộ thời gian qua một bus/khung điều phối. Model plant thường đóng gói theo chuẩn FMI/FMU (bài L).

4. X-in-the-Loop: MIL → SIL → PIL → HIL

Vai trò: chuỗi XIL mô tả cùng một chức năng được kiểm thử ở các dạng ngày càng gần thực tế. Câu hỏi cốt lõi mỗi cấp: "code gì chạy ở đâu?"

MIL — Model-in-the-Loop
Cái gì: model (Simulink) của thuật toán chạy trong công cụ mô hình trên host, ghép với model plant. Mục đích: kiểm chứng thuật toán/logic điều khiển ở mức thiết kế. Ưu: sớm nhất, sửa nhanh, không cần code. Nhược: chưa phải mã sản phẩm.
SIL — Software-in-the-Loop
Cái gì: mã nguồn/mã sinh ra (C, đã compile cho host) chạy trên PC host, ghép plant. Mục đích: kiểm chứng chính code sẽ chạy trên xe (không phải model). Ưu: test code thật, nhanh, tự động, CI. Nhược: chạy trên host nên timing/ngắt không giống target bit-chính-xác. vECU chủ yếu nằm ở đây.
PIL — Processor-in-the-Loop
Cái gì: mã biên dịch cho target processor, chạy trên chip target thật (eval board) hoặc ISS, nhưng phần còn lại (plant) vẫn mô phỏng trên host, nối qua debug/comm. Mục đích: kiểm số học/định thời trên đúng bộ xử lý (fixed-point overflow, cycle count). Ưu: bắt lỗi phụ thuộc compiler/CPU. Nhược: chậm hơn SIL, cần chip.
HIL — Hardware-in-the-Loop
Cái gì: ECU thật (phần cứng + firmware production) nối vào một hệ real-time mô phỏng plant qua tín hiệu điện/bus thật. Mục đích: kiểm thử tích hợp cuối, I/O điện, timing thực. Ưu: trung thực nhất trước xe thật. Nhược: đắt, khan hiếm, khó song song/tự động hoá quy mô lớn.

5. Vector SIL Kit

Vai trò: SIL Kit là một middleware / bus mô phỏng phân tán mã nguồn mở (open-source) của Vector. Nó cho phép ghép nhiều participant (vECU, CANoe, model, script test...) vào một virtual bus để đồng-mô phỏng — thay bus vật lý bằng bus phần mềm, trên một máy hoặc trải nhiều máy.

SIL Kit. Nhiều participant (vECU, CANoe, model) nối vào virtual bus; một registry lo khám phá & vòng đời (lifecycle); virtual bus mang CAN/LIN/Eth/FlexRay + publish/subscribe + đồng bộ thời gian.
Participant
Mỗi thành phần tham gia mô phỏng (một vECU, một model, CANoe, script test) là một participant nối vào bus. SIL Kit không quan tâm participant viết bằng gì — miễn dùng API/lib của nó.
Virtual bus (network abstraction)
Mô phỏng các mạng ô tô: CAN / LIN / Ethernet / FlexRay. Participant gửi/nhận frame như trên bus thật, nhưng qua phần mềm → thay hoàn toàn dây/transceiver vật lý.
Publish / Subscribe
Ngoài bus mạng, còn có kênh pub/sub dữ liệu (data) & RPC để trao đổi giá trị tuỳ ý giữa participant (vd tín hiệu plant) không nhất thiết map vào một frame bus.
Registry + lifecycle
Một registry (dịch vụ khám phá) giúp participant tìm nhau & kết nối. Mỗi participant có lifecycle (created → communication ready → running → stopped) & có thể tham gia lifecycle phối hợp để start/stop đồng bộ cả hệ.
Time synchronization (virtual time)
SIL Kit cung cấp đồng bộ thời gian ảo: mọi participant tiến theo cùng một simulated time → mô phỏng tất định & reproducible (chạy lại cho kết quả y hệt), độc lập tốc độ máy. Đây là điểm phân biệt cốt lõi với "chỉ nối socket".

6. Determinism & thời gian mô phỏng

Vai trò: test chỉ hữu ích khi lặp lại được. Nhưng host là OS thường (không real-time) — Windows/Linux có thể trì hoãn tiến trình bất kỳ lúc nào (scheduling jitter, GC, page fault). Nếu để mô phỏng chạy theo đồng hồ tường, kết quả sẽ đổi giữa các lần chạy → không reproducible.

Virtual / simulated time
Giải pháp: dùng một đồng hồ mô phỏng do framework điều khiển, không gắn với đồng hồ tường. Thời gian chỉ tiến khi tất cả participant đã xử lý xong bước hiện tại → thứ tự sự kiện tất định, không phụ thuộc máy nhanh/chậm.
Time synchronization
Các participant phải đồng bộ để không ai "vượt" thời gian của người khác. SIL Kit điều phối bước thời gian (time step) & chỉ cho tiến khi mọi bên sẵn sàng → cùng một chuỗi sự kiện mỗi lần chạy = reproducible (quan trọng cho debug & test hồi quy).
Monotonic vs wall-clock
Monotonic clock chỉ tăng đều, không nhảy lùi (dùng đo khoảng thời gian); wall-clock là giờ thực, có thể bị chỉnh (NTP)/nhảy. Trong mô phỏng, dùng đồng hồ đơn điệu/ảo cho định thời nội bộ, tránh phụ thuộc wall-clock. Liên hệ chi tiết host runtime ở bài M.
Faster / slower than real-time
Vì tách khỏi wall-clock, mô phỏng có thể chạy nhanh hơn thực (batch test qua đêm) hoặc chậm hơn (khi model nặng) mà kết quả logic không đổi — điều HIL (bị ràng buộc real-time) không làm được.
⚠️

Bẫy hay gặp: code vECU vô tình gọi thẳng wall-clock host (time()/QueryPerformanceCounter) thay vì đồng hồ mô phỏng → mất tất định (kết quả đổi theo tải máy). Nguyên tắc: mọi định thời trong vECU phải lấy từ simulated time do framework cấp.

7. Trước (~2020) → Nay

🖥️ Từ HIL nặng → SIL/vECU + CI shift-left (SDV)
⏪ Trước (~2020)

Test tích hợp dựa nhiều vào HIL bench đắt, phần cứng khan hiếm, khó song song; phải đợi board/silicon mới bắt đầu → phản hồi chậm, nghẽn cuối chu kỳ.

⏩ Nay

SIL/vECU chạy trên host + CI shift-left: test tự động mỗi commit, scale-out trên cloud, đồng-mô phỏng nhiều ECU qua SIL Kit. HIL vẫn cần cho I/O điện & tích hợp cuối, nhưng phần lớn regression chuyển sang ảo. Là trụ cột của SDV & virtualization.

Vì sao quan trọng: nói được "đẩy phần lớn test xuống SIL/vECU trong CI để shift-left, chỉ giữ HIL cho cái buộc phải real-time/I/O điện" cho thấy hiểu cả kỹ thuật lẫn chiến lược test hiện đại.

8. Tự kiểm tra

vECU là gì? Khác HIL ở điểm nào? Định nghĩa▾

vECU = mô hình phần mềm của ECU, biên dịch & chạy trên PC host thay cho target thật → cho phép test sớm, song song, tự động, trong CI mà không cần phần cứng (shift-left). HIL ngược lại dùng ECU thật nối hệ real-time mô phỏng plant qua I/O điện — trung thực nhất nhưng đắt, khan hiếm, ràng buộc real-time. vECU về bản chất là công cụ SIL (software trên host, dùng virtual time).

Vì sao cần virtual time / determinism? Áp dụng▾

Khi nào chọn SIL (vECU) vs HIL? Kinh nghiệm▾

Chọn SIL/vECU khi cần test sớm, hàng loạt, tự động trong CI, không có/không cần phần cứng, muốn regression nhanh & reproducible, chạy song song trên nhiều máy/cloud. Chọn HIL khi cần I/O điện thật, timing real-time chính xác, tích hợp cuối với ECU vật lý, hoặc chứng nhận cần phần cứng. Thực tế: kết hợp — đẩy phần lớn functional/regression xuống SIL, giữ HIL cho tích hợp cuối. Virtual target (L4/ISS) là bước trung gian khi cần chạy đúng binary nhưng chưa có/không muốn dùng bench HIL.

9. Cheat-sheet 1 trang

vECU — vì sao

  • Phần mềm ECU chạy trên host (không target)
  • Shift-left: test sớm/song song/tự động
  • CI-friendly · độc lập HW khan hiếm
  • Bối cảnh SDV/virtualization · PoC = chứng minh khả thi

Cấp L1–L4

  • L1 ASW/thuật toán (model)
  • L2 +RTE +BSW một phần (signal)
  • L3 full stack + virtual MCAL (bus ảo)
  • L4 firmware + ISS = virtual target (gần HIL)

XIL

  • MIL: model trên host
  • SIL: mã C trên host (← vECU ở đây)
  • PIL: mã trên target/ISS
  • HIL: ECU thật + plant real-time

SIL Kit

  • Bus mô phỏng phân tán open-source
  • Participant · virtual bus (CAN/LIN/Eth/FlexRay)
  • pub/sub · registry · lifecycle
  • Time sync → tất định; vs CANoe (tool thương mại)

Time / determinism

  • Host không real-time → cần virtual time
  • Time sync → reproducible
  • Monotonic vs wall-clock
  • Faster/slower than real-time

10. Nguồn tham khảo

  • Vector SIL Kit — github.com/vectorgrp/sil-kit & docs (participant, virtual bus, registry/lifecycle, time synchronization, pub/sub).
  • prostep iVIP SmartSE — Recommendation vECU (phân loại cấp độ vECU L1–L4, virtual MCAL, virtual target).
  • ASAM — thuật ngữ MIL/SIL/PIL/HIL & XIL API (test bench framework); FMI/FMU tách ở bài L.
  • ISS: QEMU, Synopsys Silver, Vector vVIRTUALtarget (mô phỏng vi điều khiển cho vECU L4).
