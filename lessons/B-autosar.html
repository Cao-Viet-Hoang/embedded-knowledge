AUTOSAR — Classic & Adaptive

Đây là lõi của 4 năm kinh nghiệm. Interviewer chắc chắn đào kiến trúc tầng, BSW/MCAL bạn integrate, RTE, vòng đời tích hợp, và câu kinh điển “so sánh Classic vs Adaptive”. Bài này đi sâu cơ chế thật (không dừng ở khái niệm) để bạn bảo vệ được khi bị hỏi dồn, kèm phần kiến thức cập nhật 2025–2026.

AUTOSAR là gì (một câu để mở màn)

AUTOSAR (AUTomotive Open System ARchitecture) là chuẩn kiến trúc phần mềm ô tô do consortium các OEM/Tier-1 lập ra, tách application khỏi hardware qua các lớp trừu tượng chuẩn hoá và mô tả cấu hình bằng ARXML, để phần mềm tái sử dụng và di chuyển giữa ECU/nhà cung cấp khác nhau. Hiện có hai nền tảng: Classic Platform (CP) cho điều khiển real-time và Adaptive Platform (AP) cho tính toán hiệu năng cao, dùng chung tầng Foundation (định nghĩa chung: protocol, methodology, requirements).

🚗
Bối cảnh hiện nay: Software-Defined Vehicle (SDV)

Xe hiện đại chuyển từ nhiều ECU nhỏ phân tán sang kiến trúc zonal + vài High-Performance Computer (HPC). AUTOSAR là một mảnh trong bức tranh đó: Classic chạy trên MCU vùng/actuator, Adaptive chạy trên HPC (ADAS/AD, infotainment) và nói chuyện service-oriented qua Ethernet. Nắm được câu chuyện SDV giúp bạn trả lời “AUTOSAR đi về đâu” — câu interviewer hay hỏi để test độ cập nhật.

1. AUTOSAR Classic — kiến trúc tầng

Classic Platform chạy trên MCU (thường không MMU), RTOS tĩnh, real-time (AUTOSAR OS, gốc OSEK/VDX), giao tiếp signal-oriented với liên kết cố định lúc build. Kiến trúc gồm các lớp xếp chồng; mỗi lớp chỉ phụ thuộc lớp ngay dưới qua API chuẩn:

Kiến trúc tầng Classic. BSW chia 3 phân lớp ngang (Services → ECU Abstraction → MCAL) cộng Complex Device Drivers (CDD) cắt dọc — đường “thoát hiểm” cho phần HW chưa được chuẩn hoá hoặc cần timing đặc biệt, truy cập thẳng phần cứng.
SWC
Đơn vị ứng dụng, không biết HW, không biết mình chạy trên ECU nào. Chỉ giao tiếp qua port nối vào RTE.
VFB
Virtual Function Bus — khái niệm trừu tượng: ở giai đoạn thiết kế, mọi SWC “nói chuyện” qua một bus ảo lý tưởng. RTE chính là hiện thực hoá VFB cho một ECU cụ thể.
RTE
Lớp keo sinh tự động, ánh xạ port của SWC thành lời gọi thật (nội ECU = function call; liên ECU = qua COM/bus).
BSW
Dịch vụ nền: OS, communication, memory, diagnostics, mode, crypto…
MCAL
Driver chạm thẳng thanh ghi vi điều khiển; “che” HW cho các lớp trên. Đây là lớp bạn từng test ở giai đoạn Classic.
CDD
Truy cập HW trực tiếp khi cần (sensor đặc thù, timing khắt khe) mà không qua chuẩn — đánh đổi tính khả chuyển lấy hiệu năng/đặc thù.

1.1 MCAL — các module driver

MCAL gom các driver theo nhóm chức năng. Mỗi driver cung cấp API chuẩn (vd Adc_StartGroupConversion, Dio_WriteChannel) nhưng bên trong đụng thẳng thanh ghi của MCU. Khi unit test MCAL không có HW, bạn phải stub các truy cập thanh ghi (xem bài C).

Bản đồ MCAL. Driver nhóm theo chức năng, đứng giữa lớp trừu tượng (trên) và thanh ghi HW (dưới). Cấu hình là tĩnh (ARXML → code), đúng tinh thần real-time tất định của Classic.

Trọng tâm là dependency isolation (stub truy cập thanh ghi), fault injection (ép driver trả mã lỗi/timeout) và edge case để tối đa coverage tới MC/DC.”

1.2 BSW — các stack bạn integrate (CUBAS)

Đây là phần must-tell: bạn là CUBAS integrator tích hợp full BSW stack. Mỗi accordion dưới đi vào cơ chế thật, không chỉ định nghĩa — hãy đọc kỹ phần “hay bị hỏi xoáy”.

COM đóng/mở gói signal ↔ I-PDU: phía Tx pack nhiều signal vào một I-PDU rồi đẩy xuống; phía Rx unpack I-PDU thành signal cho RTE. PduR (PDU Router) định tuyến PDU giữa COM, CanIf/CanTp, Dcm… theo bảng routing tĩnh.

  • Transmission modes: cyclic (định kỳ), event (khi đổi), hoặc mixed. Hỏi xoáy: phân biệt cyclic vs on-change.
  • Deadline monitoring: nếu signal không tới trong hạn → báo timeout, dùng init/replacement value. Đây là cơ chế phát hiện mất gói.
  • Signal gateway: route signal/PDU giữa các bus (vd CAN↔CAN) mà không cần lên tới app.
  • Update bit, byte order (endianness), packing: sai endianness là lỗi tích hợp kinh điển.

Luồng dữ liệu: Can (MCAL, mailbox HW) → CanIf (trừu tượng, L-PDU↔I-PDU) → PduR/CanTp (segment gói lớn theo ISO-TP 15765-2) → COM/Dcm.

  • CanSM: quản lý trạng thái communication của một network (FULL_COM / SILENT / NO_COM) và xử lý bus-off.
  • CanNm: network management — phối hợp sleep/wakeup toàn mạng bằng NM-PDU, để cả mạng ngủ/thức đồng bộ tiết kiệm điện.
⚙️

Bus-off recovery (hay bị hỏi): bộ đếm lỗi TX (TEC) vượt 255 → node vào bus-off, ngắt khỏi bus. CAN controller phục hồi sau khi quan sát đủ 128×11 bit recessive. CanSM điều phối recovery (thường có thời gian chờ trước khi bật lại) để tránh node lỗi quấy nhiễu bus liên tục.

Dcm (Diagnostic Communication Manager) là dispatcher UDS (ISO 14229): nhận request từ tester, kiểm session (0x10) và security access (0x27, cơ chế seed→key), route tới service handler, trả response. Dem (Diagnostic Event Manager) quản lý DTC và bộ nhớ sự kiện lỗi.

  • Service hay gặp: 0x22 ReadDataByIdentifier, 0x2E WriteDataByIdentifier, 0x27 SecurityAccess, 0x31 RoutineControl, 0x19 ReadDTCInformation, 0x14 ClearDTC, 0x10 SessionControl, 0x85 ControlDTCSetting (chi tiết ở bài E).
  • Dem — debounce: lỗi phải “đủ độ tin” (counter/time-based) mới chuyển confirmed; hết lỗi thì aging mới xoá. Tránh báo DTC do nhiễu thoáng qua.
  • Dcm ↔ Dem: khi tester đọc DTC (0x19), Dcm lấy dữ liệu từ Dem.

Lưu dữ liệu không bay hơi theo block. App làm việc với NvM (logic), còn chi tiết phần cứng bị che dần xuống dưới:

Hay bị hỏi: “Vì sao cần Fee?” → flash không ghi đè byte tuỳ ý (phải erase cả sector), nên Fee mô phỏng ngữ nghĩa EEPROM (đọc/ghi block nhỏ) và rải block để cân bằng hao mòn (wear-leveling). NvM lo redundancy/CRC block, write strategy (deferred/immediate).

  • EcuM: “điểm vào” sau reset — init driver theo thứ tự, quản lý wakeup sources, đưa ECU vào/ra các chế độ nguồn (RUN/SLEEP/OFF), giữ RUN request.
  • BswM: cơ chế rules → actions: nhận “mode request” (vd communication on/off, app mode), so với rule (điều kiện logic), thực thi action (bật/tắt PDU group, đổi schedule…). Là trung tâm điều phối hành vi theo trạng thái.
  • ComM: Communication Manager — gom yêu cầu “cần giao tiếp” từ user (app/Dcm/NM), điều phối CanSM bật/tắt bus.

🔎 Đào sâu: xem bài B6 — Mode Management (EcuM & BswM): state machine, chuỗi startup, wakeup validation, engine rule→action, immediate/deferred.

RTOS ưu tiên cố định, tĩnh (mọi task/alarm khai báo lúc cấu hình, không tạo động). Đối tượng:

  • Task: basic (chạy tới khi terminate/preempt) vs extended (có thể WaitEvent → block). Lập lịch preemptive theo priority.
  • Counter / Alarm: Alarm gắn Counter, hết hạn thì kích Task/Event hoặc gọi callback. Cơ chế “định kỳ” cổ điển.
  • Event: đồng bộ cho extended task (set/wait/clear).
  • Resource + Priority Ceiling Protocol: chống priority inversion & deadlock bằng cách nâng priority tạm khi giữ resource.
  • Schedule Table: lịch tĩnh, tất định theo expiry point — ưu việt hơn nhiều alarm rời rạc khi cần đồng bộ thời gian chặt.
  • Conformance classes: BCC1/2, ECC1/2 (basic/extended × số lượng). Memory protection (MPU) & Timing Protection + OS-Application phục vụ an toàn (ISO 26262, bài H).

Hỏi xoáy: “Schedule Table vs Alarm?” → Alarm linh hoạt nhưng khó đảm bảo quan hệ thời gian giữa nhiều sự kiện; Schedule Table cho phép định nghĩa một chuỗi expiry point đồng bộ & tất định, dễ chứng minh timing.

  • SecOC (Secure Onboard Communication): gắn MAC + freshness value vào PDU để chống giả mạo & replay trên bus — bảo vệ tính xác thực/toàn vẹn, không phải mã hoá nội dung.
  • Crypto Stack: Csm (Crypto Service Manager, API dịch vụ) → CryIf → Crypto driver (HW HSM/SHE hoặc SW). KeyM quản lý khoá/chứng chỉ.
  • IdsM (Intrusion Detection System Manager): thu thập “security event”, lọc/đánh giá, báo lên IDS backend — phần khá mới (xem mục “Trước → Nay”).

1.3 RTE — Runtime Environment

RTE là “bus ảo” nối các thành phần và là code sinh tự động riêng cho từng ECU. Hai kiểu giao tiếp port:

RTE như virtual bus. S/R = truyền dữ liệu (phát–nhận); C/S = gọi hàm dịch vụ. RTE che việc đối tác nằm cùng ECU (function call) hay khác ECU (đi qua COM/bus).

Sender / Receiver (S/R)

Truyền dữ liệu/signal phát–nhận, bất đồng bộ. Implicit (RTE copy vào buffer, đọc nhất quán trong runnable) vs explicit (Rte_Read/Rte_Write gọi tường minh). Hỗ trợ queued (event) vs last-is-best (data).

Client / Server (C/S)

Gọi operation (request/response), đồng bộ (chờ kết quả) hoặc bất đồng bộ. Dùng cho service tính toán/diagnostic. Server runnable thực thi khi có lời gọi.

Runnable là đơn vị thực thi nhỏ nhất của SWC, kích bởi RTE event (timing, data received, operation invoked…). RTE map runnable vào OS task theo cấu hình — đây là chỗ nối thế giới “SWC” với thế giới “OS”.

1.4 Quy trình tích hợp CUBAS (must-tell)

  • Configure

    Cấu hình tham số từng BSW module bằng tool cấu hình AUTOSAR; mọi thứ mô tả trong ARXML (ECU configuration). Đây là nơi quyết định signal/PDU, task mapping, NvM block, routing…

  • Generate

    Sinh code BSW config + RTE từ ARXML. RTE generator tạo glue code khớp đúng port/interface đã khai báo.

  • Integrate

    Ghép full BSW stack + MCAL + SWC, biên dịch chéo cho target RH850. Xử lý phụ thuộc init order, linker, memory mapping.

  • Validate

    Chạy trên target; dùng TRACE32 soi register/memory, đặt breakpoint, phân tích trace; đối chiếu requirement, đảm bảo traceability ASPICE. Lỗi tích hợp điển hình: sai endianness, sai task timing, NvM block layout lệch.

1.5 ASPICE & V-model

ASPICE (Automotive SPICE) là khung đánh giá năng lực quy trình phát triển, gắn chặt với V-model: nhánh trái phân tích/thiết kế, nhánh phải test tương ứng, nối bằng traceability hai chiều.

V-model & ASPICE. Mỗi mức thiết kế (trái) có một mức test tương ứng (phải), nối bằng traceability (đường đỏ). Đây chính là lý do report automation của bạn (bài D) phải tự map requirement ↔ test.
🔗

Vì sao quan trọng: ASPICE đòi requirement → design → code → test → kết quả truy vết được hai chiều. Mọi work product (test spec, case, result) phải link tới requirement — nền tảng để nói chuyện “chất lượng quy trình” trong phỏng vấn automotive.

2. AUTOSAR Adaptive Platform (ARA)

Adaptive Platform ra đời cho xe “software-defined”: nhiều tính toán (ADAS/AD, infotainment), cập nhật OTA, triển khai động. Chạy trên SoC mạnh (R-Car, Qualcomm, Nvidia), POSIX OS (Linux/QNX/INTEGRITY, profile PSE51), giao tiếp service-oriented, viết bằng C++ hiện đại.

Adaptive Platform. Khác Classic ở chỗ: process cách ly (MMU), deploy động qua Manifest, và giao tiếp service-oriented với binding (SOME/IP, DDS) ẩn dưới ara::com.

2.2 ara::com — xương sống giao tiếp

Skeleton / Proxy

Skeleton = phía cung cấp service (server). Proxy = phía dùng service (client). Cả hai sinh từ service interface trong ARXML. App code làm việc với proxy/skeleton, không quan tâm transport (SOME/IP hay DDS hay IPC).

3 phần tử của một service

Event
Server phát, client subscribe (1→n, notification). Nhận qua polling hoặc callback.
Method
Client gọi hàm trên server (request/response, có future/async).
Field
Giá trị có trạng thái: getter/setter + notifier khi đổi (= event + method “đóng gói”).

Binding: ara::com trừu tượng hoá transport. Cùng một app có thể bind sang SOME/IP (phổ biến nhất), DDS (data-centric, real-time pub/sub) hoặc IPC (cùng máy) chỉ bằng đổi cấu hình — đây là điểm hay được hỏi để test độ hiểu sâu.

2.3 Execution & State Management + Manifest

Execution Mgmt (EM)
Khởi động/dừng Adaptive Application (mỗi app là process), quản lý vòng đời, startup dependencies, hỗ trợ deterministic execution. Đọc Execution Manifest.
State Mgmt (SM)
Quyết định app/function nào chạy ở trạng thái nào qua Machine State & Function Group State.
Manifest
Mô tả triển khai: Execution Manifest (cách chạy process), Service Instance Manifest (binding service↔transport), Machine Manifest (cấu hình máy/OS). Tương đương “ARXML cho Adaptive”.

2.4 SOME/IP

SOME/IP (Scalable service-Oriented MiddlewarE over IP) là giao thức truyền service trên Ethernet/IP — binding mặc định của ara::com.

SOME/IP-SD & truyền service. Server offer (multicast), client subscribe eventgroup rồi nhận event; method là RPC request/response. Đây là cơ chế “liên kết động” mà Classic không có.
  • Serialization: đóng gói tham số method/event thành byte stream theo wire format SOME/IP (header: message ID, request ID, length, protocol/interface version, message type, return code).
  • Service Discovery (SOME/IP-SD): server “OfferService”, client “FindService/Subscribe” — nền cho liên kết động.
  • Transport: UDP (event/nhỏ/nhanh) hoặc TCP (lớn/tin cậy). So với DDS: SOME/IP service-centric, cấu hình tường minh; DDS data-centric với QoS phong phú, phù hợp pub/sub dữ liệu lớn (vd ADAS).

4. Trước (~2020) → Nay — kiến thức cập nhật

Phần này giúp bạn tránh học theo tài liệu cũ. Nếu interviewer hỏi “có gì mới trong AUTOSAR gần đây”, đây là đạn:

🔄 Lịch release & cấu trúc tài liệu
⏪ Trước (~2020)

Quanh R19-11 / R20-11. CP và AP phát triển khá tách biệt; nhiều người chỉ biết Classic.

⏩ Nay (2025–2026)

Chu kỳ release năm “Rxx-11” đều đặn (…R22-11, R23-11, R24-11). CP, AP & Foundation đồng bộ; Foundation gom các định nghĩa dùng chung (protocol, methodology).

Vì sao quan trọng: nói được “release mới nhất khoảng R24-11, dùng chung Foundation” cho thấy bạn theo dõi chuẩn, không kẹt ở kiến thức 5 năm trước.
🔐 Cybersecurity trở thành bắt buộc
⏪ Trước (~2020)

SecOC & Crypto stack đã có nhưng cybersecurity thường là “nice to have”; nhiều dự án chưa bắt buộc.

⏩ Nay (2025–2026)

ISO/SAE 21434 + UNECE R155/R156 khiến security là điều kiện type approval. IdsM (Intrusion Detection) là cluster/module tương đối mới ở cả CP & AP; SecOC/Key management được dùng rộng.

Vì sao quan trọng: “SecOC bảo vệ authenticity/integrity (MAC + freshness), không mã hoá payload; IdsM lo phát hiện xâm nhập” là câu trả lời ăn điểm — và phản ánh xu hướng hiện tại.
🧩 Adaptive trưởng thành & đa binding
⏪ Trước (~2020)

AP còn mới, ít triển khai loạt; ara::com gần như đồng nghĩa SOME/IP.

⏩ Nay (2025–2026)

AP đã vào sản xuất cho ADAS/AD & HPC. ara::com hỗ trợ DDS binding bên cạnh SOME/IP; UCM (OTA), Diagnostics ara::diag, Persistency… chín hơn.

Vì sao quan trọng: phân biệt được SOME/IP vs DDS và biết binding là cấu hình → thể hiện hiểu sâu kiến trúc, không chỉ thuộc lòng.
🚘 SDV · Zonal · Virtualization
⏪ Trước (~2020)

Kiến trúc “nhiều ECU theo domain”, mỗi chức năng một hộp; phần mềm gắn chặt phần cứng.

⏩ Nay (2025–2026)

Software-Defined Vehicle: kiến trúc zonal + vài HPC, service-oriented toàn xe, OTA. Xu hướng virtualization/hypervisor và sáng kiến như SOAFEE (cloud-native trên xe) nổi lên; AP là mảnh ghép quan trọng.

Vì sao quan trọng: đây là câu chuyện “AUTOSAR đi về đâu” — gắn được với mạch automation/AI trong CV của bạn càng tốt.

5. ARXML, Methodology & Configuration

Bạn integrate BSW/MCAL bằng cách cấu hình chứ không viết lại code — và toàn bộ cấu hình đó sống trong ARXML. JD ghi rõ “ARXML / configuration concepts”, nên phần này bổ sung nền tảng: ARXML là gì, các loại mô tả, luồng methodology và các lớp cấu hình theo thời điểm.

📦
ARXML là gì?

ARXML = AUTOSAR XML — định dạng trao đổi (exchange format) chuẩn hoá theo AUTOSAR meta-model (ràng buộc bởi schema .xsd), tool-independent. Nó mô tả mọi artefact của dự án: thiết kế SWC, giao diện, topology hệ thống, cấu hình BSW… ARXML không phải code — nó là dữ liệu để tool sinh ra code (RTE, BSW config). Nhờ chuẩn hoá theo meta-model, một mô tả tạo bởi tool này có thể được tool khác đọc lại.

5.1 Các loại mô tả (templates)

AUTOSAR chia ARXML thành nhiều “template” theo vai trò. Nắm bảng này giúp bạn biết mỗi thông tin nằm ở đâu:

Mô tả (template)Chứa gìAi/giai đoạn dùng
SWC DescriptionSoftware Component: PortPrototype, PortInterface, Runnable, InternalBehavior, RTEEventThiết kế ứng dụng · đầu vào RTE generator
PortInterfaceDataElement (Sender-Receiver) & Operation (Client-Server) — hợp đồng giữa các portĐịnh nghĩa contract giao tiếp
System DescriptionTopology: ECU instances, kết nối, mapping SWC→ECU, signal→PDU→frameThiết kế hệ thống / mạng
ECU ExtractPhần System dành riêng cho một ECU (trích ra từ System Description)Đầu vào cấu hình 1 ECU
BSW Module DescriptionMô tả 1 module BSW (do nhà cung cấp BSW phát hành): API & cấu hình có thể chỉnhNhà cung cấp BSW
ECU Configuration (EcuC)Cấu hình mọi BSW module dưới dạng container/parameter — chính là thứ được mô tả ở từng MCAL trong bài nàyIntegrator (bạn) · đầu vào generate BSW config

5.2 AUTOSAR Methodology — từ mô tả tới code

Methodology là luồng chuẩn biến các mô tả (ARXML) thành phần mềm chạy được. Vai trò trung tâm là tool cấu hình: bạn chỉnh tham số, tool sinh code.

AUTOSAR Methodology. Mô tả (ARXML) chảy từ System → ECU Extract → cấu hình EcuC; tool generate sinh RTE + BSW config C code, rồi compile & link thành image. Đây chính là các bước “Configure → Generate → Integrate” ở mục 1.4, nhìn dưới góc dữ liệu.

5.3 Configuration classes — thời điểm “chốt” cấu hình

Một tham số BSW có thể được “chốt” ở các thời điểm khác nhau. AUTOSAR định nghĩa 3 lớp cấu hình, đánh đổi giữa tốc độ/kích thước và tính linh hoạt:

ClassCơ chếChốt lúc nàoƯu / nhược & khi nào dùng
Pre-compileMacro / #define (điều kiện biên dịch)Biên dịch (compile)Nhanh & nhỏ nhất, tối ưu tốt; nhưng cố định — đổi phải build lại. Dùng cho tham số không đổi sau build.
Link-timeBiến const trong object/module riêngLinkĐổi được ở bước link (thay object) mà không build lại toàn bộ; linh hoạt vừa. Dùng khi giao cho bên khác link (vd BSW dạng object).
Post-buildCấu hình trong khối dữ liệu riêng (loadable / selectable)Sau khi build (nạp lại)Linh hoạt nhất — đổi cấu hình không cần compile lại (vd variant coding, đổi tham số CAN, nạp lại config). Đổi lại: tốn RAM/flash & overhead truy cập gián tiếp.
⚙️

Post-build có 2 kiểu: loadable = nạp một khối config mới sau build; selectable = build sẵn nhiều variant, chọn 1 lúc chạy. Hỏi xoáy “vì sao dùng post-build?” → cùng một image chạy cho nhiều biến thể xe / nhiều cấu hình mạng CAN mà không phải build lại từng cái.

5.4 Công cụ & liên hệ trong bài

Liên hệ với các mục khác

6. Tự kiểm tra — Q&A như interviewer

5 lớp của AUTOSAR Classic từ trên xuống? RTE đóng vai trò gì? Định nghĩa▾

Application (SWC) → RTE → BSW → MCAL → Microcontroller (HW). RTE là “virtual bus” hiện thực hoá VFB cho một ECU: nối SWC↔SWC và SWC↔BSW, sinh tự động từ cấu hình, ánh xạ port thành function call (nội ECU) hoặc đường COM (liên ECU).

Interviewer đào tiếp
  • BSW gồm những phân lớp nào? (Services, ECU Abstraction, MCAL + CDD cắt dọc)
  • VFB khác RTE thế nào? (VFB = khái niệm thiết kế; RTE = hiện thực cho ECU cụ thể)
Phân biệt S/R và C/S; implicit vs explicit access? Định nghĩa▾

S/R truyền dữ liệu/signal (phát–nhận, bất đồng bộ; queued hoặc last-is-best). C/S gọi operation (request/response, đồng bộ/bất đồng bộ). Implicit: RTE copy dữ liệu vào buffer cục bộ để runnable đọc/ghi nhất quán trong suốt lần chạy; explicit: gọi Rte_Read/Rte_Write tường minh, lấy giá trị tại thời điểm gọi.

Interviewer đào tiếp
  • Khi nào chọn implicit? (cần data consistency/atomicity trong runnable, tránh đọc giá trị đổi giữa chừng)
  • Runnable map vào OS thế nào? (RTE map runnable → OS task theo cấu hình)
Mô tả memory stack Classic từ ứng dụng xuống flash. Vì sao cần Fee? Áp dụng▾

NvM (block cho app, lo CRC/redundancy/write strategy) → MemIf (trừu tượng) → Fee (giả lập EEPROM trên flash) / Ea (trên EEPROM) → Fls/Eep (driver HW, MCAL). Cần Fee vì flash không ghi đè byte tuỳ ý — phải erase cả sector; Fee cung cấp ngữ nghĩa đọc/ghi block nhỏ và rải block để wear-leveling.

Interviewer đào tiếp
  • Write strategy deferred vs immediate? Hệ quả khi mất điện đột ngột?
  • Làm sao đảm bảo toàn vẹn block? (CRC + redundant block + read-back)
Bus-off recovery của CAN xảy ra thế nào? Ai điều phối? Áp dụng▾

CAN controller có TEC/REC (Tx/Rx error counter). TEC vượt 255 → node vào bus-off (ngắt khỏi bus). Phục hồi khi controller quan sát đủ 128 × 11 bit recessive (mạng rảnh). Trong AUTOSAR, CanSM điều phối recovery — thường chờ một khoảng (cấu hình) trước khi bật lại để tránh node lỗi liên tục phá bus.

Interviewer đào tiếp
  • Phân biệt error-active / error-passive / bus-off theo TEC/REC.
  • Vì sao cần delay trước khi re-init bus?
Dcm và Dem khác nhau thế nào? Debounce DTC là gì? Áp dụng▾

Dcm xử lý giao tiếp chẩn đoán (dispatcher UDS: session 0x10, security access 0x27 seed→key, route service 0x22/0x2E/0x31…). Dem quản lý sự kiện lỗi & DTC (lưu/đếm/trạng thái). Debounce: lỗi phải đủ độ tin (counter- hoặc time-based) mới chuyển confirmed; hết lỗi thì aging mới xoá — tránh báo DTC do nhiễu thoáng qua. Khi tester đọc 0x19, Dcm lấy DTC từ Dem.

Interviewer đào tiếp
  • Seed/key trong 0x27 hoạt động ra sao? Vì sao cần?
  • Sự khác nhau giữa “failed”, “confirmed”, “aged” DTC?
Schedule Table vs Alarm trong AUTOSAR OS — chọn cái nào, khi nào? Áp dụng▾

Alarm gắn Counter, hết hạn kích Task/Event/callback — linh hoạt nhưng nhiều alarm rời rạc khó đảm bảo quan hệ thời gian giữa chúng. Schedule Table định nghĩa một chuỗi expiry point đồng bộ, tất định, dễ chứng minh timing và đồng bộ nhiều hành động — ưu tiên khi cần lịch chặt (vd kích các runnable theo pha).

Interviewer đào tiếp
  • Priority Ceiling Protocol giải quyết vấn đề gì? (priority inversion, deadlock)
  • Basic vs Extended task?
So sánh Classic vs Adaptive (câu kinh điển). Áp dụng▾

Trục so sánh: mục tiêu (real-time cứng vs tính toán cao/OTA), OS (OSEK static vs POSIX), giao tiếp (signal vs service-oriented), liên kết (tĩnh build-time vs động/service discovery), ngôn ngữ (C vs C++), bộ nhớ (không MMU/một image vs MMU/process cách ly), deploy (ARXML tĩnh vs Manifest động). Chốt: bổ sung chứ không thay thế, cùng tồn tại trong xe, nói chuyện qua gateway/SOME/IP, hội tụ trong SDV/zonal.

Interviewer đào tiếp
  • Vì sao Adaptive cần service discovery còn Classic thì không?
  • Khi nào KHÔNG nên dùng Adaptive cho một chức năng? (real-time cứng/an toàn cao, tài nguyên nhỏ)
Vì sao Adaptive cần service discovery còn Classic thì không? Áp dụng▾

Classic liên kết tĩnh lúc build (signal/PDU cố định) nên đối tác đã biết trước, không cần khám phá. Adaptive liên kết động: app có thể cài/gỡ, service xuất hiện/biến mất runtime → cần SOME/IP-SD để client tìm và subscribe service đang “offer”.

Interviewer đào tiếp
  • Offer/Find/Subscribe diễn ra thế nào? Dùng multicast hay unicast?
ara::com: Event / Method / Field khác nhau? Binding là gì? Định nghĩa▾

Event: server phát, client subscribe (notification 1→n). Method: client gọi hàm trên server (request/response, hỗ trợ future). Field: giá trị có trạng thái với getter/setter + notifier (event + method gói lại). Binding: lớp transport thật dưới ara::com (SOME/IP, DDS, IPC) — đổi binding bằng cấu hình, app code không đổi.

Interviewer đào tiếp
  • Nhận event qua polling vs callback khác gì về latency/CPU?
  • SOME/IP vs DDS chọn khi nào?
SecOC bảo vệ điều gì? Có mã hoá payload không? Áp dụng▾

SecOC bảo vệ tính xác thực & toàn vẹn của PDU bằng MAC + freshness value (chống replay), không mã hoá nội dung (không bảo mật confidentiality). Khoá/dịch vụ crypto đi qua Csm→CryIf→Crypto driver (HSM/SHE nếu có). Việc phát hiện xâm nhập là của IdsM.

Interviewer đào tiếp
  • Freshness value chống tấn công gì? (replay)
  • ISO/SAE 21434 & UNECE R155 liên quan thế nào?
Kể một lần bạn debug một lỗi tích hợp BSW khó (vai trò CUBAS). Kinh nghiệm▾

Khung STAR: Tình huống (tích hợp full BSW + MCAL + SWC trên RH850, một signal nhận sai giá trị) → Nhiệm vụ (tìm gốc rễ, đảm bảo traceability) → Hành động (dùng TRACE32 soi memory/PDU buffer, đối chiếu ARXML packing/endianness, kiểm tra task timing & deadline monitoring, thu hẹp tới sai byte order trong COM config) → Kết quả (sửa cấu hình, thêm test fault-injection để regression, cập nhật trace tới requirement). Nhấn: lỗi tích hợp hay nằm ở cấu hình (endianness, mapping) chứ không phải code.

Interviewer đào tiếp
  • Bạn dùng công cụ gì để cô lập? (TRACE32, log, so ARXML)
  • Làm sao tránh tái diễn? (test tự động, review config, traceability)
Có gì mới trong AUTOSAR gần đây? (test độ cập nhật) Kinh nghiệm▾

Ba mạch: (1) Cybersecurity bắt buộc — ISO/SAE 21434, UNECE R155/R156, IdsM (Intrusion Detection) + SecOC/Crypto dùng rộng. (2) Adaptive trưởng thành — vào sản xuất ADAS/AD, ara::com hỗ trợ DDS bên cạnh SOME/IP, UCM/OTA chín. (3) SDV & zonal — service-oriented toàn xe, virtualization/hypervisor, sáng kiến cloud-native như SOAFEE. Release mới nhất quanh R24-11, dùng chung Foundation.

Interviewer đào tiếp
  • SDV ảnh hưởng vai trò embedded engineer thế nào?
  • Bạn liên hệ xu hướng này với mảng automation/AI của mình ra sao?
ARXML là gì? Gồm những loại mô tả nào? Định nghĩa▾

ARXML = AUTOSAR XML — định dạng trao đổi chuẩn hoá theo AUTOSAR meta-model (schema .xsd), tool-independent; nó là dữ liệu mô tả artefact, không phải code — tool đọc ARXML để sinh RTE/BSW config. Các loại mô tả chính: SWC Description (port/interface/runnable/internal behavior), PortInterface (S/R DataElement & C/S Operation), System Description (topology, mapping SWC→ECU, signal→PDU→frame), ECU Extract (phần System của 1 ECU), BSW Module Description, và ECU Configuration (EcuC) — cấu hình mọi BSW module dạng container/parameter.

Interviewer đào tiếp
  • EcuC chứa gì? (cấu hình từng BSW/MCAL dạng container/parameter — thứ bạn chỉnh khi integrate)
  • ECU Extract khác System Description thế nào? (Extract = phần System trích riêng cho 1 ECU)
Pre-compile vs post-build configuration — khác gì, khi nào dùng? Áp dụng▾

Pre-compile: tham số là macro/#define, chốt lúc biên dịch — nhanh & nhỏ nhất, tối ưu tốt, nhưng đổi phải build lại; dùng cho thứ không đổi sau build. Post-build: cấu hình nằm trong khối dữ liệu riêng, chốt sau khi build (loadable/selectable) — đổi cấu hình không cần compile lại (variant coding, đổi tham số CAN, nạp lại config), đổi lại tốn RAM/flash & truy cập gián tiếp. (Ở giữa là link-time: biến const đổi được lúc link.)

Interviewer đào tiếp
  • Loadable vs selectable post-build khác gì? (nạp khối mới vs build sẵn nhiều variant rồi chọn)
  • Vì sao post-build tốn tài nguyên hơn? (dữ liệu cấu hình ở RAM/flash + truy cập qua con trỏ thay vì hằng số biên dịch)
